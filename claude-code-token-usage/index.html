Summary

結論を先に：コストは「コンテキストの大きさ × リクエスト回数」

仕組み

  • Claude Code は毎リクエストで会話全体を送る。ツールを使うたびにリクエストが 1 回増える。
  • プロンプトキャッシュにより、変わっていない先頭部分はキャッシュ価格（入力の 0.1 倍、Fable 5.1 は 0.025 倍）で再読込される。

Mechanism ①

トークンはどう消費されるか：エージェントループとリクエスト

公式の説明

  • 「Claude Code は毎リクエストで会話全体を送信し、Claude がツールを使うたびに、そのツール結果を載せたもう 1 回のリクエストを送る」
  • 「一日中開いていたセッションでの 1 行の質問でも、会話全体分の使用量を引く」
  • モデルはリクエスト間で何も記憶しないので、Claude Code はシステムプロンプト、プロジェクトコンテキスト、過去の全メッセージとツール結果、新しいメッセージを毎回送り直す。

参考：平均コスト

エンタープライズ利用の平均は1 開発者あたり 1 稼働日 約 $13、月 $150–250。90% のユーザーは 1 稼働日 $30 未満。モデル選択・コードベース規模・並列インスタンスや自動化の有無で大きく変動する。

Prompt caching ①

プロンプトキャッシュ：先頭一致（プレフィックス）で再利用される

公式の要点

  • API はリクエストの先頭（プレフィックス）を最近処理した内容と照合する。一致は完全一致で、プレフィックスのどこかが変わるとそれ以降すべて再計算。ファイル単位・セグメント単位のキャッシュはない。
  • 会話層の変化はシステムプロンプト層・プロジェクト層のキャッシュを保つ。システムプロンプト層の変化はすべてを無効化する。
  • 計画モードやスキル読込は会話メッセージとして末尾に追加されるので、キャッシュ済みプレフィックスは保たれる。

公式の Tip

「モデルと effort レベルはセッションの最初に決め、/compact はタスク間の自然な区切りに取っておく。タスク途中の変更が少ないほどキャッシュヒット率は高い」

Prompt caching ④ · TTL

キャッシュ寿命（TTL）：サブスク・プラン内は 1 時間、それ以外は 5 分

リクエストの種類ごとのデフォルト TTL

バケットサブスク（プラン内利用）利用クレジット / API キー / クラウド
メイン会話
対話ターン、-p、Agent SDK		1 時間5 分
それ以外
サブエージェント、ワークフロー、チームメイト、fork、compact、セッションタイトル		5 分

プラン上限を超えて利用クレジットを消費し始めると、メイン会話は自動的に 5 分へ落ちる（課金対象になるため）。

どちらの TTL が得か（公式）

  • 1 時間 TTL は席を外して戻る使い方で有利（期限切れの再処理を避けられる）。
  • 5 分以上空けない短い連続作業では、書込単価が高い分1 時間 TTL は割高。
  • 確認：claude -p "hello" --output-format json の usage.cache_creation に ephemeral_1h_input_tokens / ephemeral_5m_input_tokens が出る。

自分で TTL を選ぶ（v2.1.242〜、値は 5m か 1h）

Reduce ① · context

削減策①：コンテキストを能動的に管理する

タスクの切れ目で /clear

  • 無関係な作業に移るときは /clear で新規開始。古いコンテキストは以降の全メッセージでトークンを浪費する。
  • 後で戻れるように /rename してから clear し、/resume で復帰。
  • API / クラウド課金で想定外に高い場合、原因は大抵「clear されなかった長いセッション」か「Opus が既定のまま」。

/compact は指示付きで、区切りに

  • /compact Focus on code samples and API usage のように何を残すかを指定できる。
  • CLAUDE.md に # Compact instructions セクションを置くと自動コンパクトにも適用。
  • 自動コンパクトを待つより、タスク間の自然な区切りで自分で実行する方がオーバーヘッドの発生時点を選べる。捨てたい経路なら /rewind の方が安い。
  • ウォームなら要約リクエストはキャッシュを読むので安いが、長い休止後の compact は最も高い。

自動コンパクトの窓を調整

> /autocompact 500k # 既定として保存 $ claude --autocompact 200k # 今回だけ CLAUDE_CODE_AUTO_COMPACT_WINDOW=750000 # 範囲 100K〜1M。既定は 200K モデルで 200K、1M モデルで約 967K

Reduce ② · model / effort / thinking

削減策②：モデル・effort・extended thinking を仕事に合わせる

適切なモデルを選ぶ

  • Sonnet はほとんどのコーディング作業を十分にこなし、Opus より安い。Opus は複雑なアーキテクチャ判断や多段推論に取っておく。
  • /model で途中切替（ただしキャッシュは切れる）、/config で既定を設定。
  • 単純なサブエージェント作業には model: haiku。
  • エージェントチームのチームメイトは Sonnet を推奨。
エイリアス意味
defaultMax/Team/Enterprise/API は Opus 5、Pro は Sonnet 5
opusplan計画モードは Opus、実行は Sonnet（切替ごとにキャッシュ再構築）
sonnet[1m]1M コンテキスト（プランにより利用クレジット要）

effort レベルを下げる

  • /effort（スライダー）、/effort medium、claude --effort low、CLAUDE_CODE_EFFORT_LEVEL、settings の effortLevel。
  • 既定は high。medium はコスト重視、low は短く範囲の狭い遅延重視タスク向け。
  • max は考えすぎになりやすい。広く採用する前にテスト。
  • スライダーで s を押すと今回のセッションだけに適用（v2.1.257〜）。

effort 変更は多くのモデルでキャッシュを無効化するので、セッション冒頭で決めるのが原則（Fable 5.1 は維持）。

extended thinking を調整

  • 既定で有効。思考トークンは出力トークンとして課金され、既定予算はモデルによって 1 リクエスト数万トークン。
  • 単純なタスクでは /effort や /model で effort を下げるか、/config で thinking を無効化。Fable モデルは無効化できない。
  • 固定予算モデル（Opus 4.6 / Sonnet 4.6）では MAX_THINKING_TOKENS=8000 のように上限を下げられる。適応推論モデル（Fable、Sonnet 5、Opus 4.7 以降）は非ゼロの予算を無視するので effort で制御。
  • 表示を畳んでいても全思考トークンが課金される。

Reduce ③ · always-on context

削減策③：常駐コンテキストを削る — MCP・CLAUDE.md・スキル

MCP サーバーのオーバーヘッド

  • MCP ツール定義は既定で deferred（tool search）。Claude が特定のツールを使うまで、ツール名とサーバー指示だけがコンテキストに入る。
  • /context で占有量を確認。/mcp で未使用サーバーを無効化。
  • CLI があるなら CLI を優先：gh、aws、gcloud、sentry-cli はツール一覧を一切追加しないので、MCP より context 効率が良い。

キャッシュ観点でも、deferred ツールなら MCP 接続・切断はプレフィックスを乱さない。

CLAUDE.md は 200 行以内、詳細はスキルへ

  • CLAUDE.md はセッション開始時に全文が読み込まれ、無関係な作業中も毎リクエスト居座る。
  • PR レビュー手順や DB マイグレーション手順のような特定ワークフロー向けの詳細はスキルへ。スキルは呼ばれたときだけ本文が載る。
  • 「必須のみ」に絞って 200 行以内を目安に。大きすぎる場合は /doctor がトリム案を出す。
  • .claude/rules/ の paths: 付きルールは、該当ファイルを扱うときだけ読み込まれる。

スキルの見え方を絞る

  • 既定ではスキルの説明文が毎リクエストに載る（本文は使用時）。
  • 自分で手動起動するスキルには disable-model-invocation: true を付けると、呼ぶまで説明文すら載らない。
  • 自分が書いていないスキルは settings の skillOverrides で同じことができる。
  • サブエージェントの skills: に列挙したスキルは起動時に全文プリロードされる点に注意。

Reduce ④ · offload

削減策④：前処理と冗長な出力をオフロードする

フックで「Claude が見る前」に前処理する

10,000 行のログを Claude に読ませる代わりに、フックが ERROR を grep して該当行だけ返す → 数万トークンが数百に。公式例は、テストコマンドを失敗行だけ表示するよう書き換える PreToolUse フック（下）。

# ~/.claude/hooks/filter-test-output.sh（公式例の要点） input=$(cat) cmd=$(echo "$input" | jq -r '.tool_input.command') if [[ "$cmd" =~ ^(npm test|pytest|go test) ]]; then filtered_cmd="$cmd 2>&1 | grep -A 5 -E '(FAIL|ERROR|error:)' | head -100" echo "$input" | jq --arg filtered "$filtered_cmd" \ '{hookSpecificOutput: {hookEventName: "PreToolUse", permissionDecision: "allow", updatedInput: (.tool_input + {command: $filtered})}}' else echo "{}" fi # settings.json の hooks.PreToolUse に matcher "Bash" で登録

スキルで「探索」を省く

"codebase-overview" スキルにアーキテクチャ・主要ディレクトリ・命名規約を書いておくと、複数ファイルを読んで構造を理解するトークンを使わずに文脈を得られる。

冗長な処理はサブエージェントへ

テスト実行、ドキュメント取得、ログ処理は大量のコンテキストを食う。サブエージェントに委譲すれば冗長な出力はサブ側に留まり、メインには要約だけ戻る。

ただしサブは別キャッシュを別に温める（TTL も既定 5 分）。小さな作業を大量に分散すると割高になりうる。

型付き言語はコードインテリジェンスプラグイン

「定義へ移動」1 回が「grep → 候補ファイルを複数読む」を置き換える。編集後に型エラーが自動で返り、正味の context 使用が下がることが多い。

Reduce ⑤ · how you work

削減策⑤：プロンプトと進め方 — 無駄な経路に入らない

1
具体的なプロンプトを書く

「このコードベースを改善して」は広範なスキャンを誘発する。「auth.ts の login 関数に入力バリデーションを追加して」なら最小限のファイル読取で済む。

2
複雑なタスクは計画モードから

Shift+Tab で計画モードへ。Claude が探索して方針を提案し、承認後に実装。最初の方向が間違っていたときの高価なやり直しを防ぐ。計画モードの指示は会話メッセージとして追加されるのでキャッシュも保たれる。

3
早めに軌道修正する

間違った方向に進み始めたら Esc で即停止。/rewind か Esc 2 回で会話とコードをチェックポイントへ戻す（rewind はキャッシュ済みプレフィックスに戻るので安い）。

4
検証ターゲットを渡す

テストケース、スクリーンショット、期待する出力をプロンプトに含める。Claude が自分の仕事を検証できれば、修正依頼の往復が減る。

5
段階的にテストする

1 ファイル書いてテストし、次へ。問題が安いうちに捕まえる。

6
モデル・effort は冒頭で決め、compact は区切りで

タスク途中の変更が少ないほどキャッシュヒット率が高い（prompt-caching の Tip）。

公式の姿勢

「委任せよ、指示するな」— どのファイルを読むか、どのコマンドを走らせるかは Claude が決められる。ただし範囲と場所（例：src/payments/ の中）を与えると効率が上がる。

Hidden usage

長いセッションで使用量が膨らむ理由と、バックグラウンド消費

「作業量の割に減っている」ときの原因（公式リスト）

長いコンテキスト毎リクエストに全会話。一日開いていたセッションの 1 行質問も会話全体分を引く
キャッシュミスTTL より長い休憩後の最初のメッセージは全コンテキストを再処理
スケジュールタスク/loop 等は idle 中も間隔ごとに全コンテキストを送る
クロスセッション通知他セッションからのメッセージが新ターンとして届く。crossSessionInbound: hold で保留可
ゴールのチェックインidle 中に確認ターンを起こす（最大 3 回、CLAUDE_CODE_GOAL_CHECKIN_MINUTES=0 で無効）
チームメイト終了するまで各自トークンを消費し続ける
compact要約対象の会話を読む＝それ自体が大きなリクエスト。継続性が不要なら /clear は無料

サブスクでは、直近使用量の 10% 以上を占める行動を /usage がフラグし、ヒントを添える。

バックグラウンドのトークン使用

  • 会話の要約：claude --resume 用に過去会話を要約するバックグラウンドジョブ
  • コマンド処理：/usage など状態確認のリクエスト
  • アイドル時でも発生するが、1 セッションあたり通常 $0.04 未満

エージェントチーム

  • チームメイトが計画モードで走ると通常セッションの約 7 倍のトークン。各自が独立した context window を持つ。
  • チームは小さく、spawn プロンプトは絞り、終わったら停止。既定では無効（CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1）。

1M コンテキスト

Claude 4.6 以降は 1M コンテキストが標準価格（900k のリクエストも 9k と同じ単価）。ただし context が大きいほど 1 リクエストの入力も大きくなるので、削減策の重要性は変わらない。

Checklist

まとめ：チェックリスト

1
まず計測：/usage・/context・ステータスライン

キャッシュヒット率と、何が常駐しているかを把握する。

2
タスクの切れ目で /clear、区切りで /compact（指示付き）

長いセッションは 1 行の質問でも全会話分を引く。

3
モデルと effort は冒頭で決める

Sonnet を既定に、Opus は必要なときだけ。途中変更はキャッシュを捨てる。

4
常駐コンテキストを削る

CLAUDE.md は 200 行以内、詳細はスキルへ。未使用 MCP は無効化、CLI があれば CLI。

5
冗長な出力は Claude に見せない

フックで前処理、サブエージェントに隔離、コードインテリジェンスで読取を減らす。

6
具体的に頼み、計画モードと早期修正で手戻りを防ぐ

検証ターゲットを渡し、段階的にテスト。/rewind は compact より安い。

7
TTL を意識する

サブスク・プラン内は 1 時間、それ以外は 5 分。API 利用なら promptCacheTtl: "1h" を検討。

8
見えない消費を止める

スケジュールタスク、チームメイト、ゴールのチェックイン、クロスセッションメッセージ。
