Yocto ビルドホストの構築手順

ビルドホストに使う Linux ディストリビューションの選び方と、インストールからビルド開始までの手順。サポート対象ディストロの選定、ベアメタル / VM / WSL2 の選択、ディスクとファイルシステムの設計、初期設定、ホスト依存パッケージ、最初のビルドでの動作確認まで。

Summary

結論を先に：迷ったらこの構成

① ディストロは「サポート対象」から選ぶ 選択

Yocto は動作確認済みのディストロをリリースごとに明示している（Ubuntu / Debian / Fedora / AlmaLinux / openSUSE Leap の特定バージョン）。迷ったら Ubuntu の LTS 版：情報量が多く、公式ドキュメントとメーリングリストの例もほぼ Ubuntu 基準。

デスクトップ用途と兼ねないなら Server 版の最小構成 で十分。GUI は runqemu を使うときだけ要る。

② 勝負はディスクと置き場所 設計

公式要件は空き 90 GB 以上だが、実務では 200〜400 GB を見ておく。ファイルシステムは ext4、置き場所はローカルディスク。ネットワーク共有・VM の共有フォルダ・NTFS/exFAT の上にビルドディレクトリを置くと必ず壊れる。

大文字小文字を区別し、拡張属性とハードリンクが効くこと。この 3 つが満たせない場所は失格。

③ インストール直後にやることは 5 つ 手順

(1) UTF-8 ロケール生成 (2) 一般ユーザーで作業（root でのビルドは拒否される）(3) ホスト依存パッケージの導入 (4) 時刻同期とネットワーク／プロキシ (5) core-image-minimal を 1 回通して環境を検証。

この 5 つを済ませてから本題のレイヤー作業に入る。順番を飛ばすと数時間後に落ちる。

流れ：要件（3）→ ディストロ選定（4–7）→ 設置形態とディスク設計（8–9）→ インストール手順（10–12）→ 依存パッケージと救済策（13–14）→ 検証と運用（15–17）。本資料は Yocto 入門 の 6–7 枚目を単独で詳しくしたもの。

Requirements

ビルドホストに求められる要件

項目公式の要件実務での目安
OSサポート対象の Linux ディストリビューションUbuntu LTS（Server）
ディスク空き90 GB 以上（core-image-sato のビルドを想定）200〜400 GB
メモリ8 GB 以上を推奨16〜32 GB（コア数 × 2 GB 目安）
CPU規定なし（並列数がそのまま時間に効く）物理 8 コア以上
ネットワークソース取得のため外部へ出られることプロキシ配下なら別途設定
ロケールUTF-8 ロケールが必要en_US.UTF-8 を生成
実行ユーザーroot では実行しない（BitBake が拒否）専用の一般ユーザー

ホストツールの最低バージョンも決まっている

Git・tar・Python 3・GNU make・gcc には最低バージョンが規定されている（リリースごとに更新される）。サポート対象ディストロを選べば自動的に満たされるが、古い企業内ディストロを使う場合はここが引っかかる。救済策は 14 枚目の buildtools-tarball。

ファイルシステムの必須条件

  • 大文字小文字を区別する：Makefile と makefile、linux/String.h のようなパスが共存する。
  • 拡張属性（xattr）が使える：pseudo が rootfs の所有者・パーミッションを記録するのに使う。
  • ハードリンクとシンボリックリンクが効く：sstate の展開と DL_DIR の共有に必須。
  • UNIX パーミッションを保持する：実行ビットが落ちる共有はビルド途中で不可解に失敗する。

NTFS・exFAT・FAT32・VM の共有フォルダ（HGFS 等）・CIFS/SMB はいずれかを満たさない。NFS は条件付きだが遅く、トラブルの元。

パス名の制約

ビルドディレクトリのパスに空白・日本語・記号を含めない。/home/yocto/build のような短い ASCII パスにする。パスが長すぎると、一部のレシピでシバン行や引数長の上限に当たる。

出典：Yocto Project Reference Manual — System Requirements。数値・対応バージョンはリリースごとに変わるため、使うリリースのドキュメントを正とする。

Choosing · ①

ディストリビューションの選択基準

1
サポート対象か
最優先
使う Yocto リリースの System Requirements に載っているか。載っていないと、ホスト依存の不具合を踏んだときに切り分けができない。
2
サポート期間
運用
Yocto の LTS は約 4 年。ホスト OS の寿命が先に切れると途中で移行が要る。LTS 同士を合わせる。
3
CI と同じか
再現性
手元と CI でディストロが違うと、ホストツール差で再現しない差分に悩む。CI のイメージに合わせるのが安全。
4
情報量
実利
エラーで検索したときの事例の多さ。Ubuntu > Debian / Fedora > その他、という現実がある。
5
組織の制約
政治
社内標準やサポート契約で RHEL 系しか使えない場合は AlmaLinux / Rocky で合わせる。

推奨：Ubuntu の LTS（Server）

上の 5 基準をまとめて満たす。デスクトップ環境は不要（runqemu のグラフィカル確認をするときだけ、あとから軽量 WM を入れれば足りる）。新しすぎる非 LTS 版は、サポート対象から外れていることが多いので避ける。

「サポート対象」はどこで確認するか

  • 公式マニュアルの Supported Linux Distributions の節（リリースごとにページがある）。
  • Poky の中の meta-poky/conf/distro/poky.conf にある SANITY_TESTED_DISTROS 変数。実際に sanity チェックが参照する一覧なので、これが実質の正本。
# 対象外だと最初のビルドでこう警告される WARNING: Host distribution "ubuntu-25.10" has not been validated with this version of the build system; you may possibly experience unexpected failures. It is recommended that you use a tested distribution.

警告であってエラーではないためビルドは進む。だからこそ、数時間後に見慣れないエラーで落ちたときに原因の切り分けが難しくなる。

サポート対象ディストロの例と、リリースとの対応

5.0 LTS（scarthgap）系での対象例

ディストロ対象バージョンの例備考
Ubuntu22.04 LTS / 24.04 LTS事例が最も多い。既定の選択
Debian11 / 12安定志向。Ubuntu とほぼ同じ手順
Fedora38 / 39 / 40新しいツールチェーン。寿命が約 13 か月と短い
AlmaLinux8.x / 9.xRHEL 互換。EPEL の追加が要る
openSUSE Leap15.4 / 15.5パッケージ名がやや異なる

この表はあくまで例。対象バージョンはリリースごとに増減する（新しい Yocto では古いディストロが外れ、新しいディストロが入る）。必ず使うリリースのドキュメントか SANITY_TESTED_DISTROS を見る。

Yocto のリリースとホスト OS の寿命を合わせる

Yocto は年 2 回（4 月・10 月）リリースし、2 年に一度が LTS（例：5.0 “scarthgap”、2024-04）。LTS のサポートは約 4 年。ホストに Fedora のような短命ディストロを選ぶと、製品の寿命の途中でホストだけ先に EOL になる。

  • 製品開発・長期保守 → Yocto LTS × ディストロ LTS（Ubuntu LTS / Debian / AlmaLinux）
  • 調査・検証・最新追随 → 最新リリース × Fedora でも可

アーキテクチャ（x86_64 / aarch64）

ホストの CPU アーキテクチャは x86_64 が主流だが、aarch64 ホストも公式に使える（Apple Silicon の Linux VM、Ampere などの ARM サーバー）。Yocto は元々クロスコンパイルなので、aarch64 ホストから x86_64 向けイメージも作れる。

ただし aarch64 ホストは事例が少なく、prebuilt のホストツールや一部レイヤーが x86_64 前提のことがある。また、作った x86_64 バイナリをホスト上でそのまま実行できないため、runqemu などでの動作確認方法が変わる。

Choosing · ③

候補の比較 — どれを選んでも動くが、性格が違う

ディストロ向いている場面利点注意点
Ubuntu LTS 既定 ほぼすべての用途。個人の学習から製品開発まで 事例・記事・公式例が最も多い。5 年サポート。VM イメージやクラウド AMI も豊富 Server 版を使う。非 LTS 版と最新すぎる LTS は対象外の期間がある
Debian 長期安定・サーバー運用に寄せたい場合 枯れている。パッケージ名は Ubuntu とほぼ同じで手順を流用できる ツールが古めで、新しい Yocto では最低バージョンに届かないことがある
Fedora 最新のツールチェーンで検証したい場合 gcc・Python が新しい。上流の変化を先に踏める サポート約 13 か月。頻繁な OS 更新でホスト差分が出やすい
AlmaLinux / Rocky
（RHEL 互換）		 社内標準が RHEL 系、サポート契約がある場合 10 年級の長期サポート。企業環境との親和性 EPEL の追加が必要。パッケージ名が Debian 系と大きく違う。事例が少ない
openSUSE Leap 既に SUSE を使っている組織 サポート対象に入っている。YaST での管理 依存パッケージ名が独特。日本語の事例が少ない

比較の結論

「どれが速いか」はほぼ差がつかない（実体はクロスコンパイラを自前で作るため、ホストのパッケージはほとんど成果物に影響しない）。差が出るのは トラブル時の情報量 と サポート期間。だから既定は Ubuntu LTS、制約があれば RHEL 系、という順で選ぶ。

デスクトップ環境は入れるべきか

基本は不要。SSH 経由で使う Server 構成が軽くて速い。runqemu でグラフィカルに動作確認したくなったら、後から軽量デスクトップを足すか、runqemu nographic でシリアルコンソールだけ使う。GUI はメモリとディスクを食う側であることを忘れない。

Choosing · ④

サポート対象外の環境をどう扱うか

環境判定扱い
Arch / Gentoo動くが対象外ローリングリリースのため上流より新しいツールが入り、想定外の失敗が出やすい。本番のビルドホストには選ばない
古い RHEL / CentOS 7要救済git・Python が古く最低バージョンに届かない。buildtools-extended-tarball で補う（14 枚目）
macOS不可大文字小文字を区別しない既定 FS、BSD ツール、pseudo 未対応。Linux VM を立てる
Windows 単体不可WSL 2 に Ubuntu を入れて、その中で作業する（16 枚目）
Docker / Podman条件付き可CROPS などのコンテナは公式にも案内されている。ただしビルドディレクトリを bind mount に置かない
NAS / 共有ストレージ不可拡張属性・ハードリンク・速度のいずれかで破綻する。DL_DIR の共有のみ、条件を確認したうえで検討

「動いた」と「サポートされる」は別

対象外の環境でも最初のビルドは通ることが多い。問題は数時間走ったあとに、レシピ側ではなくホスト側の理由で落ちたとき。原因の切り分けにサポート対象ホストでの再現が必要になり、結局そこで環境を作り直すことになる。最初から対象環境で始めるほうが速い。

どうしても手元の環境を変えられないとき

  • VM を立てる：もっとも確実。スナップショットで失敗から戻せる（8 枚目）。
  • コンテナを使う：ホストを汚さない。ただしビルド領域は名前付きボリュームかコンテナ内のパスに置く。
  • クラウドに 1 台立てる：ディスクとコアを金で買える。CI と同じイメージを使えば再現性も上がる。

いずれの場合も「サポート対象ディストロが動く Linux カーネル上の、ローカルの ext4」という条件に帰着させるのが目的。

学習・個人

VM が第一候補。ディスク 200 GB 以上の仮想ディスクを切り、Ubuntu Server LTS を入れる。うまくいった時点でスナップショットを取っておくと、実験で壊しても数十秒で戻せる。

チーム・製品開発

ベアメタルかクラウドの共有ビルドマシン。DL_DIR と SSTATE_DIR を共有し、CI と同じディストロ・同じ Yocto リリースで揃える。個人機はそこから sstate を引く構成にすると速い。

CI

コンテナ。ディストロとホストツールをイメージに固定し、sstate と downloads は永続ボリュームで外に出す。ビルド作業ディレクトリはコンテナ内（またはボリューム）に置く。

Sizing

ディスクとパーティションの設計 — ここが一番はまる

ビルド中にディスクが尽きると

数時間分のタスクがまとめて失敗し、中途半端な tmp が残る。BitBake には BB_DISKMON_DIRS で空き容量が減ったら一時停止・中断する仕組みがあるので、共有マシンでは設定しておく。

パーティション方針

  • ファイルシステムは ext4。既定でよい。/home を大きく取り、その下で作業する。
  • LVM にしておくと、あとからディスクを足して論理ボリュームを拡張できる（VM でもクラウドでも効く）。
  • スワップ 8〜16 GB。リンク時に数 GB 使うレシピがあり、OOM でビルドが飛ぶのを防ぐ。
  • SSD / NVMe を使う。Yocto のビルドは小さなファイルの大量 I/O で、HDD では桁で遅くなる。
  • /tmp が tmpfs でメモリを圧迫する構成なら、TMPDIR は作業ディスク側に置く。

btrfs / ZFS を使う場合

動作はするが、COW とスナップショットで実使用量が読みにくくなる。圧縮が効くぶん得に見えて、削除しても空きが戻らず苦しむことがある。素直に ext4 を勧める。

# 作業ツリーはローカルの ext4 の上に置く $ df -hT /home/yocto /dev/mapper/vg0-home ext4 400G 18G 362G 5% /home # 共有フォルダ・ネットワークドライブは失格 $ df -T /mnt/hgfs/work /mnt/hgfs/work fuse.vmhgfs ← ここでビルドしない

最小構成で入れる

Ubuntu Server のインストーラには「minimized install」に相当する選択肢がある。ビルドホストに要るのは ビルドツールとディスク だけなので、デスクトップ環境・オフィス系・不要なサービスは入れない。速く、壊れにくく、更新も軽い。

Install · ②

インストール手順 ② — 初回起動後の初期設定

# 1. まず更新して再起動 $ sudo apt update && sudo apt full-upgrade -y $ sudo reboot # 2. ロケール（UTF-8 は Yocto の前提条件） $ sudo locale-gen en_US.UTF-8 $ sudo update-locale LANG=en_US.UTF-8 $ locale | head -2 LANG=en_US.UTF-8 LANGUAGE= # 3. ホスト名・時刻（時刻ずれは sstate の事故のもと） $ sudo hostnamectl set-hostname yocto-build $ sudo timedatectl set-timezone Asia/Tokyo $ timedatectl | grep -E 'synchronized|Time zone' # 4. git の最低限の設定（devtool / patch で使う） $ git config --global user.name "Your Name" $ git config --global user.email "you@example.com" # 5. 作業ディレクトリ（短い ASCII パス・ローカル FS） $ mkdir -p ~/yocto && cd ~/yocto

忘れやすい設定

  • スリープ・サスペンドを止める：長時間ビルド中にホストが寝ると SSH が切れてビルドが死ぬ。systemctl mask sleep.target suspend.target など。ノート PC では蓋を閉じたときの挙動も変える。
  • 自動更新の扱いを決める：unattended-upgrades がビルド中に走ると I/O を持っていかれ、再起動要求も出る。共有ビルドマシンでは更新の時間帯を管理する。
  • SSH 公開鍵を置く：パスワード認証は切る。以後の作業は手元の端末からで済む。
  • スワップの確認：free -h。足りなければスワップファイルを追加する。

プロキシ配下の場合

社内プロキシがあるなら 3 か所に設定が要る。① シェル環境変数（http_proxy / https_proxy / no_proxy）② apt の設定 ③ git・npm など取得ツール個別の設定。Yocto はレシピごとに違うツールでソースを取りに行くため、環境変数だけでは通らないことがある。

どうしても通らない取得元は、先に DL_DIR へ手動で置いてしまう回避策もある。

Install · ③

ホスト依存パッケージを入れる

# Ubuntu / Debian（scarthgap 系での例） $ sudo apt install \ gawk wget git diffstat unzip texinfo gcc \ build-essential chrpath socat cpio python3 \ python3-pip python3-pexpect xz-utils \ debianutils iputils-ping python3-git \ python3-jinja2 python3-subunit zstd \ liblz4-tool file locales libacl1 # 動作確認（最低バージョンを満たしているか） $ git --version; python3 --version; gcc --version | head -1 git version 2.43.0 Python 3.12.3 gcc (Ubuntu 13.3.0-…) 13.3.0

この一覧は例であり、正本は公式マニュアルの “Required Packages for the Build Host”。Yocto のリリースごとに増減し、ディストロによって名前も変わる。使うリリースのページをそのままコピーして実行するのが確実。

ディストロ別の要点

ディストロコマンド注意点
Ubuntu / Debianapt install上の一覧。Debian では dpkg-reconfigure locales でロケール生成
Fedoradnf installパッケージ名が別系統（gcc-c++、perl-*、glibc-langpack-en など）。一覧はマニュアル参照
AlmaLinux / Rockydnf install先に EPEL を有効化する。バージョン 8 系と 9 系で必要なパッケージが違う
openSUSE Leapzypper install独自のパッケージ名（python3-Jinja2 など）

用途で追加が要るもの

  • グラフィカルな runqemu：SDL / Mesa 系の開発パッケージ。
  • ドキュメント生成や SDK のテスト：追加の Python パッケージ。
  • NFS ブート・TFTP で実機を動かすなら、それぞれのサーバー。

必要になってから足せばよい。まずは最小一覧で core-image-minimal を通す。

Rescue

ホストのツールが古いとき — buildtools-tarball

何を解決するものか

Yocto は git・tar・Python 3・make・gcc に最低バージョンを要求する。社内標準の古い RHEL 系ディストロなどでは、これらが要求を満たさず最初のビルドで止まる。OS を入れ替えられないとき、Yocto が用意した新しいホストツール一式を、ホストを汚さずに被せるのが buildtools。

  • buildtools-tarball — git・Python・tar などの基本ツール一式。
  • buildtools-extended-tarball — 上記に加えて新しい gcc を含む。ホストのコンパイラが古すぎる場合はこちら。

使い方の形

インストーラを実行して展開し、シェルごとに環境設定スクリプトを source する。PATH の先頭に新しいツールが入るので、以後の bitbake はそちらを使う。ターミナルを開き直すたびに source が要る点に注意（oe-init-build-env の前に実行する）。

あくまでホストツールの下駄であり、「サポート対象外ディストロをサポート対象にする」ものではない。可能なら素直に対象ディストロを使う。

# poky 同梱のスクリプトで取得・導入できる $ cd ~/yocto/poky $ scripts/install-buildtools --help $ scripts/install-buildtools \ --base-url https://downloads.yoctoproject.org/releases/yocto \ --release yocto-5.0 -d ~/yocto/buildtools # 使うときは毎回 source する $ source ~/yocto/buildtools/environment-setup-* $ git --version # 新しい git が先に見える git version 2.44.0 # そのうえで通常どおり $ source ~/yocto/poky/oe-init-build-env $ bitbake core-image-minimal

オプション名・URL・利用できるリリースはバージョンで変わる。--help と公式マニュアルの “Required Git, tar, Python, make and gcc Versions” の節を確認する。tarball は公式のダウンロードサイトから直接取得することもでき、自分で bitbake buildtools-tarball して作ることもできる。

判断の目安

最初のビルドで 「git/Python/gcc のバージョンが古い」と明示的に言われたときだけ使う。それ以外のエラーを buildtools で直そうとしないこと（原因が別のところにある）。

Per-environment · ①

VM に作る場合の追加手順

VM ならではの利点を活かす

  • スナップショットを段階ごとに取る：「OS 入れ終わり」「依存パッケージ導入済み」「最初のビルド成功」。実験で壊しても即戻せる。
  • テンプレート化：完成した VM を複製すれば、チームの他メンバーに同じ環境を配れる。
  • ホストを汚さない：macOS / Windows 側の環境はそのまま。

VM で必ず踏む落とし穴

  • 共有フォルダの上でビルドしない。大文字小文字を区別せず、拡張属性も怪しく、そして遅い。作業ツリーは必ず仮想ディスクの中に置く。
  • ディスクが足りなくなる。仮想ディスクを広げてもゲスト側のパーティションと LV と FS を順に広げる必要がある（growpart → lvextend → resize2fs）。最初から大きく取るほうが楽。
  • ホストがスリープする。長時間ビルド中に母艦が寝ると VM も止まる。macOS なら caffeinate -i、Windows なら電源プランを変更する。
  • サスペンド復帰後の時刻ずれ。ゲストの時刻が飛ぶとビルドの整合性チェックが荒れる。ゲスト用ツール（VMware Tools 等）を入れて時刻同期させる。
# 仮想ディスク拡張後、ゲスト側で広げる（LVM の例） $ lsblk $ sudo growpart /dev/sda 3 $ sudo pvresize /dev/sda3 $ sudo lvextend -l +100%FREE /dev/vg0/home $ sudo resize2fs /dev/vg0/home $ df -h /home /dev/mapper/vg0-home 400G 18G 362G 5% /home
製品備考
VMware FusionApple Silicon では arm64 ゲストのみ。Yocto はクロスコンパイルなので x86_64 向けイメージは作れる
UTMmacOS 向け。QEMU ベース。arm64 ゲストなら実用速度
VirtualBoxx86_64 ホスト向け。I/O が遅めなので仮想ディスクの設定に注意
KVM / libvirtLinux ホスト上なら最速。ビルドサーバーの分割に向く

要は「arm64 でも x86_64 でもよいので、サポート対象の Linux が動き、大きなローカル ext4 を持てる VM」であればよい。

Per-environment · ②

WSL 2 とコンテナに作る場合

WSL 2（Windows しか使えないとき）

  • wsl --install -d Ubuntu-24.04 のようにサポート対象のディストロを入れる。WSL 1 ではなく 2 であることを確認する（wsl -l -v）。
  • 作業ツリーは Linux 側のファイルシステム（~/）に置く。/mnt/c 以下は Windows の NTFS で、大文字小文字と速度の両方で破綻する。
  • %UserProfile%\.wslconfig で メモリ・CPU 数・スワップを割り当てる。既定のままだとメモリ不足でリンクが失敗しやすい。
  • 仮想ディスク（ext4.vhdx）は自動で伸びるが上限がある。大きなビルドをするなら上限と空き容量を事前に確認する（拡張手順は WSL のバージョンで異なる）。
  • ファイルを消しても Windows 側の空き容量はすぐには戻らない。定期的な整理が要る。
  • /etc/wsl.conf で systemd を有効にすると、サービス前提の手順がそのまま使える。

WSL 2 は実体が軽量 VM。ここまでの VM 向けの注意（ディスク・共有先・スリープ）はそのまま当てはまる。

コンテナ（CI・ホストを固定したいとき）

  • Yocto Project は CROPS（crops/poky）というコンテナイメージを公開しており、公式ドキュメントでも Windows / macOS からの利用手段として案内されている。
  • ビルドディレクトリを bind mount に置かない。ホスト側 FS の性質（xattr・大文字小文字）とオーバーヘッドがそのまま効く。名前付きボリュームかコンテナ内のパスを使う。
  • DL_DIR と SSTATE_DIR は永続ボリュームにして、コンテナを作り直しても失わないようにする。
  • root で走らせない。ホストと UID を合わせた一般ユーザーで実行する。
  • 自作イメージにするなら、ディストロのバージョンとホスト依存パッケージを Dockerfile に固定する。これが再現性の要になる。

特権の要否

通常のビルドに特権は不要（pseudo が root 権限なしで rootfs の所有者情報を扱う）。特権が要るのは、ビルド後に runqemu でネットワークを張るなど周辺の作業。「とりあえず --privileged」は避ける。

Verify

動作確認 — core-image-minimal を 1 回通す

# 一般ユーザーで実行する（root では拒否される） $ cd ~/yocto $ git clone -b scarthgap git://git.yoctoproject.org/poky $ source poky/oe-init-build-env # → build/ が作られ、そこへ移動した状態になる $ bitbake core-image-minimal Loading cache: 100% |####################| Parsing recipes: 100% |##################| Build Configuration: BB_VERSION = "2.8.0" BUILD_SYS = "x86_64-linux" MACHINE = "qemux86-64" DISTRO = "poky" Initialising tasks: 100% |###############| NOTE: Tasks Summary: Attempted 2841 tasks … # 動かしてみる（GUI 不要ならシリアルだけ） $ runqemu qemux86-64 nographic

初回は1〜4 時間かかる（ツールチェーンを一から作るため）。ここが通れば、ホストとしての要件はほぼ満たせている。2 回目以降は sstate が効いて劇的に速い。

BitBake は起動時に sanity チェックでホスト環境を検証する（必要なコマンドの有無、ディストロ、ロケール、パス、TMPDIR の移動など）。最初のエラーメッセージを最後まで読むのが最短路で、たいていそこに対処がそのまま書いてある。

Operations

ビルドホストの運用とチューニング

# build/conf/local.conf の要点 # 並列度（既定はコア数。メモリが足りなければ下げる） BB_NUMBER_THREADS ?= "8" PARALLEL_MAKE ?= "-j 8" # 取得物とキャッシュはビルドディレクトリの外へ出して共有 DL_DIR ?= "${HOME}/yocto/downloads" SSTATE_DIR ?= "${HOME}/yocto/sstate-cache" # ディスクが厳しいなら作業ディレクトリを都度削除 INHERIT += "rm_work" # 空きが減ったら停止させる（事故防止） BB_DISKMON_DIRS ??= "\ STOPTASKS,${TMPDIR},1G,100K \ HALT,${TMPDIR},100M,1K"

HALT は新しめのリリースでの指定。古いリリースでは ABORT という名前だった。変数名・既定値はリリースで変わるので Variables Glossary を確認する。

消してよいもの・だめなもの

build/tmp消せる 作り直せる。容量の大半はここ
sstate-cache消せる ただし次が遅くなる。古い物だけ整理する
downloads消さない 上流が消えたソースは二度と取れないことがある
レイヤーの git消さない 自作レイヤーはバックアップ対象

速くするための順番

  1. SSD にする（HDD なら他の何よりこれが効く）
  2. DL_DIR と SSTATE_DIR を共有する（複数ブランチ・複数機種で再利用）
  3. メモリを足す（並列度を上げてもスワップしない）
  4. コアを増やす（並列タスク数がそのまま効く）

チームで使うなら、共有 sstate をネットワーク越しに配る仕組み（HTTP 公開など）を用意すると、各自の初回ビルドが大幅に短くなる。

ホストの OS 更新はビルドしていない時間帯に計画的に。ツールチェーンの前提が変わると、再現ビルドの結果が変わり得る。

Wrap-up

まとめ — 構築チェックリストと参考資料

構築チェックリスト

  • 使う Yocto リリースを決め、そのサポート対象ディストロから選んだ（既定：Ubuntu LTS）
  • ディスクは 200 GB 以上、ローカルの ext4、LVM で後から拡張できる
  • メモリ 16 GB 以上＋スワップ、SSD、コア数に見合った並列度
  • 作業パスは短い ASCII（~/yocto）。共有フォルダ・ネットワーク FS 上ではない
  • UTF-8 ロケールを生成した／一般ユーザーで作業する
  • ホスト依存パッケージを公式一覧どおりに導入した
  • 時刻同期・スリープ抑止・プロキシ設定を済ませた
  • core-image-minimal が通り、runqemu で起動を確認した
  • DL_DIR / SSTATE_DIR をビルドディレクトリの外に出した
  • （VM なら）ここまでの状態でスナップショットを取った

この 10 項目が埋まっていれば、以後の失敗は「ホストのせい」ではなくレシピとレイヤーの問題として切り分けられる。それが、ビルドホストを丁寧に作る目的。
