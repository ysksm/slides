02 / 基本構造

ワークスペースの構造

Gitリポジトリを扱う場合は、worktreeが作業の分離単位になります。

用語役割例
RepositoryGitの履歴とコードを管理する単位web / api
Project group関連するプロジェクトのまとまりcommerce
Workspace端末・編集・ブラウザを束ねる作業拠点checkout-ui
Git worktree別ディレクトリに置く、ブランチの作業コピーwebのfeature/checkout
Agent sessionその作業拠点で実行するエージェントとの会話実装担当 / 調査担当

同じworkspaceに端末を増やしても、編集するファイルは共有されます。

補足説明

WorkspaceはGit worktreeだけを意味しない。Folder workspaceやFloating Workspaceもある。worktreeはファイルを分離するが、OSのポート、外部DB、Gitの共有情報まで分離するサンドボックスではない。

03 / ワークスペース設計

ワークスペースの切り方

おすすめの基準は「独立してレビュー・統合できる変更」ごとです。

仕事の性質構成例理由
小さなバグ修正1 workspace + 1 agent成果物と差分を追いやすい
同じ問題を別アプローチで試す候補ごとに別worktree互いの変更を混ぜずに比較できる
同じ機能の調査と実装同一workspace、編集者は1人調査結果を使い、同時編集を避ける
APIと画面を同時に変えるrepo別worktree + 共通の管理拠点コードの分離とタスク全体の管理を両立
別の納期・別の承認者別workspace / 別タスク完了判断が独立している

補足説明

このスライドの構成は運用上の提案であり、Orcaが強制するルールではない。同じブランチを複数の通常worktreeに同時チェックアウトすることはGitが制限するため、候補ごとに別ブランチを使う。

03 / ワークスペース設計

タスク用worktreeの作成

対象リポジトリ、分岐元、名前、エージェントを明示します。

  1. Project

    変更対象のリポジトリを選ぶ。

  2. Run on

    ローカルか、準備済みのホストを選ぶ。

  3. Start-from / Name

    分岐元を確認し、仕事が分かる名前にする。

  4. Agent / Issue

    担当エージェントと関連する課題を指定する。

orca worktree create \
  --repo name:web \
  --name checkout-ui \
  --base-branch origin/main \
  --agent codex \
  --prompt "決済画面の入力検証を実装" \
  --json

name:web は例。実際のselectorは
orca repo list --jsonで取得。

補足説明

新規worktreeを作るコマンド。既存workspaceで別のエージェントを起動したい場合はterminal createを使う。既存PRの上に積むときはStart-fromをそのブランチにする。Parent workspaceの表示上の親子関係とGitの分岐元は別。

04 / 複数リポジトリ

関連リポジトリをまとめる

公式機能のProject groupとFolder workspaceが、横断作業の入口になります。

~/dev/commerce/

  api/       # Git repository
  contracts/ # Git repository

04 / 複数リポジトリ

1つのタスクを、repo別の作業に分ける

運用例:「注文にクーポンを適用する」をwebとapiで実装。

拠点担当・役割変更と成果物
Folder workspace
checkout-42		Coordinator / 調整仕様、担当表、repoごとのPR・SHA一覧
apiのworktree
checkout-42-api		API worker / 編集割引計算、API契約テスト、APIのPR
webのworktree
checkout-42-web		UI worker / 編集クーポン入力、エラー表示、UIのPR
結合検証用の拠点検証担当 / 原則読み取り指定SHAの組み合わせでE2Eを実施

共有するのは仕様と完了条件。commit・PR・CIは各リポジトリで管理します。

補足説明

これは推奨構成例。CoordinatorがFolder workspaceにいることだけで、エージェントに配下全repoの編集権限が付くわけではない。各エージェントの許可されたパスを別途確認する。Folder workspaceから元checkoutを直接編集する方法もあるが、並行タスクを走らせる例ではrepo別worktreeを選ぶ。

04 / 複数リポジトリ

repo別worktreeの準備例

共通のタスク名を付け、返されたパスを担当表に記録します。

orca worktree create \
  --repo name:api \
  --name checkout-42-api \
  --base-branch origin/main \
  --no-parent --json
orca worktree create \
  --repo name:web \
  --name checkout-42-web \
  --base-branch origin/main \
  --no-parent --json
管理項目記録例
repoと作業パスapi: <返されたpath> / web: <返されたpath>
APIの約束POST /coupons/validate、成功・失敗レスポンス
実行先UI: 3101 / API: 4101
補足説明

準備例なのでこの段階では--agentや--promptを付けていない。作成後、オーケストレーションのworker-startで正確なworktree selectorを指定する。--no-parentはOrcaの表示上の親子関係の自動推定を外すだけで、分岐元は--base-branchが決める。repoの存在、origin/mainの存在、selectorの一意性を確認して使う。

04 / 複数リポジトリ

複数repoの完了判定

repoごとのテストに加え、組み合わせた状態の動作を確認します。

  1. 契約を先に合意

    APIのフィールド、エラーコード、互換性を固定する。

  2. 独立して実装

    UIは合意済みの契約をモックにして進める。

  3. 検証するSHAを固定

    apiとwebのcommit SHA、環境変数、起動方法を記録する。

  4. 結合テストと統合順

    成功・無効クーポン・期限切れを検証し、PRの統合順を決める。

依存タスクの完了だけでは、変更は別worktreeへ届きません。

補足説明

独自の運用提案。OrcaのTask依存関係はGitのmerge、cherry-pick、パッケージ公開、APIの起動を代行しない。検証用のcheckoutやサービスに対象SHAを取り込む工程を明示する。複数repoのPRが一括・原子的にmergeされると仮定しない。後方互換のAPIを先に出し、UIを後から切り替える方法が一例。

状態の例コメントに残すこと

06 / オーケストレーション

既存worktreeへの担当割り当て

Coordinatorの端末からRunを作り、準備済みの作業パスを渡します。

orca orchestration run-create --objective "checkout-42を実装" --json

orca orchestration worker-start \
  --worktree "path:<APIのworktree絶対パス>" \
  --agent codex --task-title "API実装" \
  --spec "対象: API。クーポン検証を実装。契約を維持しUIは編集しない。
APIの契約テストが通ること。変更ファイル・テスト結果・SHAを報告。" \
  --json

UI担当もUIのパスとspecで起動。返されたTask / Dispatch IDを記録する。

補足説明

山括弧を含む値は実際の絶対パスへ置換する。同じCoordinator端末でrun-createとworker-startを行う。新規agentの--modelはprovider固有ID、--effortには--modelが必要。既存worker端末の再利用と組み合わせられないオプションがあるため、正確な構文は版ごとのhelpで確認する。

06 / オーケストレーション

依存関係と判断待ち

並列にできる仕事と、結果を待つ仕事をTaskの依存関係で表します。

Task開始前に必要なこと進め方
契約の合意要件の確認最初に完了
APIの実装契約Taskの完了UIと並行
UIの実装契約Taskの完了APIと並行

06 / オーケストレーション

報告の受信と、完了後の扱い

無応答や待機タイムアウトを、完了・失敗と決めつけない運用にします。

orca orchestration check --wait \
  --types "worker_done,escalation,question" \
  --timeout-ms 60000 --json

orca orchestration task-list --json
orca orchestration worker-list --json
  1. 質問に回答

    ask / replyで担当の判断待ちを解消する。

  2. 結果を照合

    worker_doneのTask・Dispatchと、成果物・テスト結果を確認する。

  3. 片付けて受領

    settle済みworkerを再利用・retain・releaseし、deliveryをackする。

補足説明

worker_doneはworker自身が注入されたpreambleに従い、succeeded/failedを明示して送る。Coordinatorは成功したテストや変更SHAなどの証拠も確認する。releaseは完了後の後片付けでありcancelではない。受信メッセージを処理してからcheck --ack <delivery-id>で受領する。後続の待機でも同じRunを使う。

07 / オートメーション

平日9時の調査を登録する例

対象と指示を確認しやすいよう、最初は無効状態で作成します。

orca automations create \
  --name "平日朝の課題整理" \
  --trigger weekdays --time 09:00 \
  --timezone Asia/Tokyo \
  --provider codex --repo name:api \
  --prompt "新規Issueを読み、再現条件・影響・優先候補をまとめる。
結果はtriage.mdに記録。コードの変更やIssueへの投稿はしない。" \
  --disabled --json

例のproviderは選択するCLI、repoは作業対象。実行時に認証済みの環境が必要。

補足説明

登録するだけの説明例であり、この資料の作成時にはautomationを作成していない。UIで作る場合はAutomationsからCreate onで保存・実行ホストを選び、利用可能なprojectを指定する。--repoは各回の新規worktree、--workspaceは既存workspace。実行先を推定に任せず指定すると運用を追いやすい。
