tgrep 解説

Microsoft が公開したトライグラム索引付き grep「tgrep」。その仕組みと使い方を押さえたうえで、AI コーディングエージェントとの組み合わせと、プラグインとして配布して使わせる方法までを扱う。

Summary

結論を先に：索引を一度作り、エージェントに配る

① 何者か 索引付き grep

リポジトリ全体から 3 バイトのトライグラムの転置索引を事前に作り、検索時は候補ファイルだけを走査する。クライアント／サーバー構成で索引を常駐させ、ファイル監視で自動更新。巨大リポジトリで ripgrep 比 15〜52 倍の実測値が公開されている。

インターフェースは ripgrep 互換。-i -F -l -c -A/-B/-C -g -t --json がそのまま通る。

② なぜ AI エージェントに効くか 本題 1

エージェントは 1 タスクで何十回も grep する。1 回 30 秒の全走査が 0.5 秒になれば、探索の深さと往復回数がそのまま変わる。実際 GitHub Copilot CLI は tgrep を検索基盤に採用している。リポジトリには AGENTS.md（エージェント向けの作法）が同梱されている。

鍵は「速さ」だけではない。--json / 終了コード / -l による出力量の制御がコンテキスト節約に効く。

③ プラグイン化 本題 2

「入れて、常駐させて、使い方を教える」までを 1 パッケージにする。Claude Code プラグインなら SessionStart フックで tgrep serve を起動し、Skill で使い方を教え、marketplace 経由でチームに配るところまで一式にできる。

「各自インストールしてね」を配布物に変えるのがプラグイン化の目的。

この順に見ていく：仕組み（3〜6）→ 使い方（7〜11）→ エージェント連携（12〜16）→ プラグイン化（17〜21）。

What it is

tgrep とは何か

  • Microsoft が公開した トライグラム索引付きの grep（microsoft/tgrep、Rust 製、MIT ライセンス）。
  • grep / ripgrep は検索のたびに O(全バイト) の走査を行う。10 万ファイル超のモノレポではこれが支配的なコストになる。
  • tgrep は 索引を一度作り、検索時は索引が示した候補ファイルだけを開く。「毎回全部読む」を「最初に一度読む」に置き換える。
  • クライアント／サーバー構成。tgrep serve が索引を常駐させ、ファイル監視で差分を取り込む。問い合わせは JSON-RPC 2.0 over TCP。
  • CLI は ripgrep 互換。既存のフラグ・--json 出力・終了コードがほぼそのまま使え、GitHub Copilot CLI に統合されている。

似たツールとの位置づけ

ripgrep索引なしの全走査。常に最新・セットアップ不要。小〜中規模なら十分速い
Zoektトライグラム索引検索。サーバー前提の Web 検索基盤寄り
tgrepローカル CLI の使い勝手のまま索引を持つ。単一マシン向け
# 導入（Homebrew） $ brew install tgrep # 索引を作って常駐（初回は索引構築を含む） $ tgrep serve . & # 以後は ripgrep と同じ感覚で検索 $ tgrep "TODO|FIXME" . -t rust -C 2 # 状態確認 $ tgrep status . pid 48213 port 51037 files 388,214 watcher native trigrams 16,742,901 indexing complete

How it works · 原理

なぜ速いのか ①：トライグラム転置索引

索引側：3 バイトの連なりを全部覚える

各ファイルの本文を 3 バイトずつスライドさせた部分文字列（トライグラム）に分解し、「どのトライグラムがどのファイルに出現するか」の転置索引を作る。parseConfig なら par, ars, rse, seC … が記録される。

検索側：正規表現をトライグラムの論理式に落とす

パターンを解析し、「マッチするなら必ず含まれるトライグラム」の AND / OR 式を導く。TODO|FIXME なら (TOD AND ODO) OR (FIX AND IXM AND XME) のような式になる。索引でこの式を評価し、候補ファイル集合を得る。

最後は通常の正規表現エンジンで確認する

索引が返すのは「含む可能性があるファイル」（偽陽性あり・偽陰性なし）。その候補だけを実際に読んで正規表現でマッチさせるので、結果は ripgrep と同じになる。速さは「読むファイルを減らした」ことから来ており、精度を落としていない。

短すぎるパターンや .* のように有効なトライグラムを取り出せないパターンでは候補が絞れず、全走査に近づく。3 文字以上の具体的な文字列ほど索引が効く。

# パターン → トライグラム論理式 → 候補ファイル pattern: "parseConfig" ↓ 分解 trigrams: par ars rse seC eCo Con onf nfi fig ↓ 索引を AND で引く posting: par → [12, 88, 204, 991, …] seC → [204, 991] ↓ 積集合 → 正規表現で検証 candidates: [204] ← 実際に開くのはここだけ match: src/config/parser.ts:41

オンディスク索引の中身

lookup.binトライグラム → オフセット・長さ（ソート済み・二分探索）
index.binポスティングリスト本体（ファイル ID の列）
files.binファイルパス表
meta.jsonバージョン・件数・タイムスタンプ・カバレッジ
serve.jsonサーバーの PID と TCP ポート（クライアントの発見用）

既定では対象ディレクトリ直下の .tgrep/ に置かれる。.gitignore に .tgrep/ を追加すること。

IndexReader（ディスク層）

オンディスク索引を mmap して、コピーなしの二分探索で引く。プロセス起動時に全体を読み込まないため、常駐していなくても索引があれば十分速い。

LiveIndex（メモリ層）

起動後に変更・追加されたファイルのトライグラムをメモリ上のオーバーレイとして保持。5 万ファイルごと／5 分ごとなどの契機でディスクへフラッシュされる。

HybridIndex（合成層）

両者を重ね、メモリ層を優先して結果を返す。「索引は古いがファイルは新しい」状態を、再構築なしで吸収するための仕組み。

索引構築自体も並列化されている（1,024 ファイル単位のバッチを rayon で処理し、外部マージソートでピークメモリを抑える）。.gitignore を尊重し、約 50 種類のバイナリ拡張子と先頭 8KB の内容判定でバイナリを除外する。

この数字の読み方

  • 索引構築の時間は含まない。初回はリポジトリ規模に応じた構築コストを一度払う。
  • マッチ件数が多いほど差は縮む。chromium で倍率が落ちているのは、候補を絞る利得よりマッチを出力する時間が支配的になるため。「絞り込める検索」ほど効く。
  • 小さなリポジトリでは差が出ない。数千ファイル規模なら ripgrep でも数十 ms で、索引の維持コストのほうが高くつく。

効く場面 / 効かない場面

  • 10 万ファイル超のモノレポ。1 タスク中に何度も検索する
  • 具体的な識別子・文字列を探す（トライグラムが取れる）
  • 同じリポジトリで作業し続ける（索引が再利用される）
  • 使い捨てのチェックアウト・CI の 1 回きりの検索
  • . や 1〜2 文字など、索引が絞り込めないパターン
  • 結果が数万行になる検索（出力が支配的）

コストの実態

索引はディスクを消費し、常駐サーバーはメモリと監視ハンドルを消費する。監視ハンドルの上限（Linux の inotify など）に達すると ポーリングへ自動降格するため、--watch-mode poll / --poll-interval / --watch-budget で明示的に制御できる。

Getting started

導入とセットアップ

# Homebrew（macOS / Linux） $ brew install tgrep # ソースから（Rust ツールチェーンが必要） $ git clone https://github.com/microsoft/tgrep.git $ cd tgrep $ cargo install --path tgrep-cli --locked # ビルド済みバイナリ（Linux x86_64 の例） $ gh release download --repo microsoft/tgrep \ -p '*x86_64-unknown-linux-musl*' -D "$tmpdir" $ tar xzf "$tmpdir"/tgrep-*.tar.gz -C "$tmpdir" $ install -Dm755 "$tmpdir/tgrep" "$HOME/.local/bin/tgrep"

Linux (x86_64) / macOS (Intel・Apple Silicon) / Windows のビルド済みバイナリが GitHub Releases で配布されている。エージェントやチームへ配る場合は、この「バイナリ取得」の手順こそが自動化の対象になる（スライド 19）。

リポジトリごとの初期化（1 回だけ）

索引の置き場所と対象の調整

$ tgrep index . --exclude vendor $ tgrep index . --max-filesize 8M $ tgrep index . --index-path /tmp/idx $ tgrep serve . --index-path /tmp/idx

ここが最大の落とし穴：--exclude / --no-ignore / --index-path / --max-filesize / --no-require-git は index・serve・検索のすべてで揃えないと、黙って別のファイル集合を検索することになる（スライド 11）。

ripgrep との JSON の差分

不正な UTF-8 バイトを含む行で、ripgrep は lines.bytes に base64 を入れるが、tgrep は lines.text に U+FFFD（置換文字）を入れて返す。バイト列を厳密に扱うパイプラインではこの違いが効く。

終了コードの意味

01 件以上マッチした
1マッチしなかった — エラーではない
2本当のエラー（不正な正規表現、読めないパス）

set -e のシェルや、非ゼロを一律に失敗とみなすツールラッパーでは 1 を失敗として扱ってしまう。エージェントに「検索は失敗しました」と誤って伝える典型的な事故なので、1 と 2 を分けて扱うこと。

出力形式の使い分け

人間・LLM既定のテキスト。-C で文脈を足す。LLM にとっても読みやすい
プログラム--json。1 行 1 オブジェクトなのでストリーム処理できる
エディタ連携--vimgrep。file:line:col:text で該当箇所へ飛べる
存在判定-q + 終了コード。出力ゼロでコンテキストを使わない

Caveats

ripgrep との違いと、踏みやすい落とし穴

① 索引の鮮度 最重要

サーバーの結果は「インデクサが処理し終えた最後の監視イベント時点」を反映する。イベントは非同期にキューイングされるため、直前の編集が即座には見えないことがある。「今さっき書いた内容が必ず見えてほしい」場面では --no-index を付けて全走査させる。

サーバーを使わずディスク索引だけの場合は、最後に tgrep index を走らせた時点が反映される。エージェントに「編集直後の再検索」をさせる設計なら、ここは必ず考慮する。

② フラグの不整合

--exclude / --no-ignore / --index-path / --max-filesize / --no-require-git は index・serve・検索で一致していなければならない。ずれるとエラーにならず、黙って違うファイル集合を検索する。ラッパーやプラグインでは、これらを 1 か所に固定するのが安全。

③ 既定値の違い

ファイルサイズ上限既定 64 MiB（ripgrep は無制限）。合わせるなら --no-max-filesize
不正な UTF-8索引化のため U+FFFD に修復する
大文字小文字Git リポジトリでは core.ignorecase の設定を尊重する

④ サブコマンドとパターンの取り違え

ユーザー入力や LLM 生成のパターンが serve や index と一致すると、サブコマンドとして解釈されうる。公式 AGENTS.md は明確に指示している — 「パターンの前に -- を置き、検索ルートを明示的に渡すこと」。

# 危ない $ tgrep "index" # 安全 $ tgrep -- "index" .

AI agents · なぜ効くのか

本題 1：AI エージェントとの組み合わせ

エージェントの作業は「検索が律速」になりやすい

コーディングエージェントは、1 つのタスクの中で 探索 → 読む → 仮説 → また探索 を何十回も繰り返す。人間は 1 回の grep を待てるが、エージェントは待ち時間の合計がそのままタスク時間になる。1 回 30 秒の全走査を 20 回行えば 10 分が検索に消える。

速さは「深さ」に変換される

  • 検索が安いと、当たりをつけずに広く探ることが許される。推測でファイルを読む回数が減る。
  • 「この識別子は他にどこで使われているか」を毎回確認できる。思い込みによる破壊的変更が減る。
  • タイムアウトでツール呼び出しが失敗し、エージェントが別の（劣った）手段に逃げることがなくなる。

実例：GitHub Copilot CLI

tgrep は GitHub Copilot CLI に統合され、大規模リポジトリの高速 grep を担っている。エージェント向けの AGENTS.md が同梱されていることからも、「エージェントの検索基盤」が想定された主用途のひとつだと読める。

速さと同じくらい重要な「出力量」

エージェントにとって検索結果はコンテキストウィンドウの消費でもある。10,000 行の grep 結果は、遅いだけでなく会話を破壊する。tgrep が持つ -l / -c / -m / -q / --json は、この観点では速度と同格の機能になる。

# 悪い例：全部返させる $ tgrep -- "config" . … 18,402 matches across 2,913 files # → コンテキストが飽和し、要約に迷い込む # 良い例：段階的に絞る $ tgrep -l -t ts -- "parseConfig" . 3 files $ tgrep -C 3 -m 2 -- "parseConfig" src/config/ 6 matches # → 読むべき場所が特定できた

AI agents · 作法

公式 AGENTS.md が定めるエージェントの作法

セットアップは 1 リポジトリ 1 回

$ tgrep serve . & # 索引が無ければ構築し、 # .tgrep/serve.json にポートを書く

バックグラウンドプロセスを維持できない環境（1 コマンド 1 プロセスのサンドボックス等）では tgrep index . で代替する。.tgrep/ は .gitignore へ。

クエリの組み立て方

-- の前置パターンをサブコマンドと誤解させない。検索ルートも明示する
-F を優先記号やユーザー入力の文字列は正規表現エスケープ事故を避けるためリテラルで
-t で先に絞る出力を削る -m より先に、対象を型で絞るほうが効く
-l から始める広いクエリはまずファイル名だけ。そのあと深掘りする
-C 2 / -C 3周辺コードの意味が要るときだけ文脈を足す
-q + 終了コードYes/No の判定は出力を捨てて終了コードで見る

鮮度について合意しておく

サーバーの結果は監視イベントの処理状況に依存するため、「たった今の編集が必ず見えなければならない検索」には --no-index を使う、と公式ドキュメントは明示している。エージェントの「編集 → 検証」ループを設計するときの前提条件になる。

stderr を必ず返す

「索引がありません」といった警告は、成功の終了コードと同時に stderr へ出る。ツールラッパーが stderr を捨てると、エージェントは「今は遅い経路で動いている」ことに気づけない。stdout・stderr・終了コードを 3 点セットで返すのが公式の指示。

ツールスキーマの推奨形

最小構成は pattern（必須）・path（既定 .）・flags（文字列配列）。実行形は次の形に固定する。

tgrep <flags...> -- <pattern> <path>

AI agents · 実装

エージェントへの組み込み：ツール定義と安全設計

// LLM に見せるツール定義（MCP / Function calling 共通） { "name": "tgrep_search", "description": "Search the repo with tgrep. Prefer -l first, then" "narrow with -t and -C. Use -F for literals.", "input_schema": { "type": "object", "properties": { "pattern": { "type": "string" }, "path": { "type": "string", "default": "." }, "flags": { "type": "array", "items": { "type": "string" } } }, "required": ["pattern"] } } // 実装側（擬似コード）: フラグは allowlist const ALLOWED = new Set(["-i","-S","-F","-w","-l","-c","-o","-q","-U", "-A","-B","-C","-m","-g","-t","--json","--vimgrep","--no-index"]); const root = realpath(repoRoot); const dir = realpath(join(root, input.path ?? ".")); if (!dir.startsWith(root)) throw new Error("path escapes repo root"); for (const f of input.flags ?? []) assertAllowed(f, ALLOWED); // シェルを介さず引数配列で起動する const r = spawnSync("tgrep", [...flags, "--", input.pattern, dir]); return { stdout: r.stdout, stderr: r.stderr, exitCode: r.status };

安全設計の 4 点

  • シェルを経由しない。spawn に引数配列で渡す。文字列連結して sh -c に渡すと、パターン内の ; や $( ) がコマンド実行になる。
  • フラグは allowlist。任意のトークンを通すと、-r（置換）や設定系フラグで想定外の挙動を作れてしまう。検索専用フラグだけを通す。
  • パスを正規化してルート内に閉じる。realpath 後にリポジトリルート配下かを検証する。../ やシンボリックリンクでの脱出を防ぐ。
  • 出力に上限を設ける。ツール側で -m の既定値と総バイト数の打ち切りを入れる。エージェントのコンテキストは有限のリソース。

返し方

stdout・stderr・終了コードを常に 3 つとも返す。終了コード 1（マッチなし）は正常系としてモデルに伝え、2 だけをエラーとして扱う。stderr の警告文はモデルが読んで自分で対処できる情報になる。

AI agents · 運用

実際のワークフロー：常駐させ、段階的に絞らせる

1
セッション開始時に常駐
自動化する
tgrep serve . & をセッション開始フック等で起動する。初回だけ索引構築のコストが乗るが、以降のセッションでは再利用される。エージェント自身に「まず serve しろ」と指示するより、環境側で済ませておくほうが確実。
2
輪郭を掴む
-l / -c
tgrep -l -- "SymbolName" . でまずどのファイルにあるかだけを得る。ファイル数が多ければ -t や -g で絞り直す。この段階の出力は数十行に収める。
3
文脈を読む
-C / -m
絞れたディレクトリに対して -C 3 -m 3 付きで再検索し、定義と主要な使用箇所を掴む。ここで初めてファイル全体を読む判断ができる。
4
編集する
tgrep の外
エージェントがファイルを編集する。サーバーはファイル監視で差分を取り込むが、取り込みは非同期である点を忘れない。
5
編集直後の検証
--no-index
「置換漏れがないか」のようにたった今の編集が反映されていなければ意味がない検索は --no-index で全走査させる。対象を編集したディレクトリに限定すれば、全走査でも十分速い。
6
存在判定で締める
-q + exit code
「旧 API はもう残っていないか」を -q と終了コードで確認する。出力ゼロなのでコンテキストを消費せず、判定が曖昧にならない。

要点：索引は「速いが少し古いかもしれない」層として扱い、確証が要る場面だけ全走査に落とす。この使い分けをエージェントに教えるのが、次のプラグイン化の中身になる。

Plugin · なぜ

本題 2：なぜ「プラグイン化」するのか

ドキュメントに書くだけでは配れない

ここまでの内容（導入・常駐・フラグの作法・鮮度の扱い）を README に書いても、実際には ①各自がインストールし ②毎回 serve を起動し ③作法を覚えている ことが前提になる。エージェントに至っては、セッションごとに記憶がリセットされる。

プラグインなら 4 つを同梱できる

実行環境bin/ に置いた実行ファイルは、プラグイン有効時に Bash ツールの PATH に入る
起動hooks/hooks.json の SessionStart で tgrep serve を自動起動できる
作法skills/ の SKILL.md が、必要なときだけモデルに読み込まれる
配布marketplace 経由で /plugin install 一発。バージョン管理も効く

標準設定（.claude/）との使い分け

標準設定プラグイン
範囲そのプロジェクトだけ複数プロジェクト・チームで再利用
呼び名/tgrep-search/tgrep:search（名前空間付き）
配布手でコピー/plugin install ・バージョン指定
向き試作・個人の工夫共有・版管理された配布物

まず .claude/ で作り、形が決まったらプラグインへ移す、が公式の推奨順序。

「Skill か MCP か」の判断

tgrep は CLI として完成しているので、わざわざ MCP サーバーを書かなくても、Bash ツール + 使い方を教える Skill で機能する。MCP サーバーが要るのは、フラグを allowlist で強制したい／出力量を機械的に打ち切りたい／Bash ツールを許可していない環境で使いたい場合（スライド 19）。

Plugin · 構成

プラグインの構成とマニフェスト

tgrep-plugin/ ├── .claude-plugin/ │ └── plugin.json # マニフェスト ├── skills/ │ └── search/ │ └── SKILL.md # 使い方をモデルに教える ├── hooks/ │ └── hooks.json # SessionStart で serve ├── scripts/ │ ├── ensure-tgrep.sh # 導入・起動 │ └── tgrep-search.mjs # MCP を出す場合 ├── .mcp.json # 任意 └── README.md

よくある間違い

.claude-plugin/ の中に入れてよいのは plugin.json だけ。skills/・hooks/・.mcp.json はすべてプラグインルート直下に置く。

// .claude-plugin/plugin.json { "name": "tgrep", "displayName": "tgrep search", "description": "Trigram-indexed repo search", "version": "0.1.0", "license": "MIT", "author": { "name": "ysksm" }, "userConfig": { "exclude": { "type": "string", "default": "node_modules" } } }

使える置換変数

${CLAUDE_PLUGIN_ROOT}プラグインの絶対パス。スクリプト・バイナリの参照に使う
${CLAUDE_PLUGIN_DATA}更新をまたいで残る保存領域。索引置き場に向く
${CLAUDE_PROJECT_DIR}プロジェクトのルート。検索対象の起点

userConfig の値は Skill 内では ${user_config.exclude}、フック・MCP では CLAUDE_PLUGIN_OPTION_EXCLUDE 環境変数として渡る。「フラグ不整合」（スライド 11）を 1 か所に固定できる。

Plugin · 起動と教育

SessionStart で常駐させ、Skill で作法を教える

// hooks/hooks.json { "hooks": { "SessionStart": [ { "hooks": [ { "type": "command", "command": "\"${CLAUDE_PLUGIN_ROOT}\"/scripts/ensure-tgrep.sh" } ] } ] } }
# scripts/ensure-tgrep.sh #!/usr/bin/env bash set -u command -v tgrep >/dev/null || exit 0 # 未導入なら黙って諦める cd "${CLAUDE_PROJECT_DIR:-$PWD}" || exit 0 tgrep status . >/dev/null 2>&1 && exit 0 # 常駐済み EX="${CLAUDE_PLUGIN_OPTION_EXCLUDE:-node_modules}" nohup tgrep serve . --exclude "$EX" >/dev/null 2>&1 & exit 0

未導入でも exit 0 で黙って諦めるのが行儀のよいフック。tgrep が無ければ Claude Code は通常の検索にフォールバックするだけで、セッションは壊れない。

# skills/search/SKILL.md --- description: Search this repository with tgrep (trigram-indexed grep). Use for any code search in this repo - finding symbols, callers, TODOs, or checking whether a string still exists. --- # tgrep search 必ず `tgrep <flags> -- <pattern> <path>` の形で呼ぶ。 1. まず `-l` でファイル一覧を取り、`-t` で型を絞る 2. 絞れたら `-C 3 -m 3` で文脈つきに再検索する 3. 記号やユーザー入力の文字列は `-F`（リテラル） 4. 存在確認は `-q`。終了コード 1 は正常（マッチなし） 5. 直前の編集を確実に見たい検索は `--no-index` 6. `--exclude ${user_config.exclude}` を常に付ける

Skill にする理由

Skill は description に合致したときだけ本文が読み込まれる。「毎回すべてのセッションのシステムプロンプトに tgrep の使い方を載せる」のと違い、検索しようとした瞬間にだけ作法が届く。常時のコンテキスト消費がほぼゼロで済む。

Plugin · 設計の選択

Skill + Bash か、MCP ツールか

A. Skill + Bash ツール まずこれ

  • 実装ゼロ。SKILL.md を書くだけ
  • 全フラグが使える。モデルが状況に応じて選べる
  • 出力がそのまま見えるので挙動を追いやすい
  • フラグを強制できない。作法は「お願い」止まり
  • 出力量を機械的に打ち切れない
  • Bash ツールを許可していない環境では使えない

B. MCP サーバーとして出す

  • フラグ allowlist・パス正規化・出力上限をコードで強制できる（スライド 14）
  • Bash 権限なしで検索だけを許可できる
  • Claude Code 以外の MCP 対応エージェントでも同じ実装を使い回せる
  • サーバー実装と保守が要る
  • スキーマで塞いだフラグは使えなくなる
// .mcp.json（B を選ぶ場合。プラグインルート直下） { "mcpServers": { "tgrep": { "command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/scripts/tgrep-search.mjs"], "env": { "TGREP_INDEX_PATH": "${CLAUDE_PLUGIN_DATA}/idx" } } } }

実務的には「両方入り」が扱いやすい

1 つのプラグインに Skill（人間とモデルへの説明） と MCP ツール（強制したい制約） の両方を入れ、Skill 側から「検索は tgrep_search ツールを使う」と指示する。プラグインは skills/・hooks/・.mcp.json・bin/ をまとめて 1 パッケージにできるのが強みなので、どれか 1 つを選ぶ必要はない。

bin/ でバイナリごと配る

プラグインルートの bin/ に置いた実行ファイルは、プラグインが有効な間 Bash ツールの PATH に追加される。「tgrep を各自インストール」の手順自体を消せる。ただし claude.ai の組織設定から配布するプラグインでは、トップレベル bin/ を含められない点に注意。

Wrap-up

まとめと参考資料

要点

  • tgrep = 索引付き grep。トライグラム転置索引で候補ファイルを絞り、最後は通常の正規表現で検証する。結果は ripgrep と同じで、速度だけが違う。
  • 効くのは大規模 × 高頻度。10 万ファイル超で 15〜52 倍。逆に小規模・一回きり・マッチ数が膨大な検索では利得が薄い。
  • AI エージェントとの相性が本題。速度はタスク時間に直結し、-l/-m/-q による出力制御はコンテキスト消費に直結する。Copilot CLI が実例。
  • 作法は 3 つ。-- を前置する／リテラルは -F／index・serve・検索でフラグを揃える。加えて索引の鮮度が要る場面は --no-index。
  • プラグイン化で「配布物」にする。フックで常駐、Skill で作法、MCP で制約の強制、marketplace で配布。ドキュメントを実行可能な形にする作業。
