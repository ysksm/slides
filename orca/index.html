AIエージェント時代のオーケストレーターIDEOrca 解説

Claude Code・Codex・Cursor CLI などのエージェントを、タスクごとに独立した git worktree で並列に走らせ、一か所で追跡・レビュー・出荷するためのデスクトップIDE。機能一覧、機能ごとの設定、そして機能の組み合わせ方をまとめました。

はじめに

Orca とは何か「100x ビルダーのための AI オーケストレーター」。モデルでも git の代替でもなく、既存の CLI エージェントを並列に運用する土台。

1 タスク = 1 worktree = 1 エージェント端末 = 1 ブラウザタブ。stash やブランチの切り替えなしに、複数のエージェントに仕事を配って結果を比べ、勝ったものをマージする。

Orca がやること

  • worktree の作成・一覧・削除と、その中のエージェント状態の追跡
  • AI 差分のレビュー、コミット、PR 作成、CI チェック確認
  • GitHub / GitLab / Linear / Jira のタスクと worktree の紐づけ
  • スケジュール実行（オートメーション）と多エージェント協調（オーケストレーション）

Orca がやらないこと

  • モデルではない：Claude / Codex / OpenCode などの契約は自分で用意
  • git の代替ではない：全 worktree は本物の git worktree。cd して素の git が使える
  • ホスティング VPS ではない：リモート実行は自分の SSH ホスト・クラウド口座で

対応エージェント

Claude Code, Codex, Cursor CLI, Gemini, GitHub Copilot, OpenCode, Pi, Amp, Grok, Devin, Goose, Droid, Kimi, Kiro, Qwen Code, Cline, Continue, Rovo Dev … ターミナルで動く CLI なら何でも。

誰向けか

差分を読み、コミットに責任を持ち、worktree を整理して使う「コードを書く人」向け。ノーコードツールではない。

技術スタック

Electron + React（renderer）、VS Code 由来の Monaco エディタ、xterm ベースの WebGL 端末、Node 製 CLI（orca）、モバイル用リレー（cloud/）。

はじめに

基本フロー：add → worktree → agent → split → diff → ship公式ドキュメント曰く「この流れが Orca の全て。他のページは各ステップの深掘り」。

リポジトリを追加ローカル checkout を指定。デフォルトブランチが base ref（全 worktree の分岐元）になる
worktree を作るタスク名を入力し start-from ref を選ぶ。git worktree add はバックグラウンドで走る
エージェントを選ぶ端末の agent コンボボックスから Claude Code 等を起動。作業ディレクトリと認証は Orca が渡す
ペインを分割worktree タブを端にドラッグして分割。3 エージェントを同時に眺める
差分をレビューstart-from ref との diff。行コメントを束ねてエージェントに返す（Annotate AI Diff）
出荷Orca 内でコミット・push・PR 作成・チェック待ち。負けた worktree はワンクリック削除

worktree の実体

Orca 管理ディレクトリに本物の worktree が作られる。例（このマシン）：~/orca/workspaces/<repo>/<task名>。ブランチ名はタスク名や紐づけた Issue から自動導出。

名前を空にすると

海の生き物の名前が自動で付く（Settings → General → Default new-worktree name で接頭辞に変更可）。:rocket: 形式の絵文字ショートコードも使える。

3 エージェント競争

同じタスクで worktree を 3 つ作り、Claude Code / Codex / Cursor CLI に同じプロンプトを貼る。3 ブランチ・3 差分から勝者を選び、他は削除。これが「最初の 5 分」の公式チュートリアル。

第 1 章

ワークスペース設計リポジトリの切り方、ワークスペースの切り方、そしてマルチリポで 1 タスクを回す方法

Orca では「プロジェクト（= リポジトリ）」と「ワークスペース（= worktree または フォルダワークスペース）」を分けて考える。前者は登録、後者はタスクの単位。

ワークスペース設計

Worktree モデルひとつの checkout で branch と stash を繰り返す代わりに、タスクごとに「ディスク上の別コピー」を持つ。

base ref
リポごとに 1 つ。通常 origin/main。全 worktree の既定分岐元
start-from ref
worktree ごとに 1 つ。base ref／別ローカルブランチ（PR に積む時）／SHA／リモートブランチ
worktree が持つもの
専用ブランチ、専用ファイル、専用のエージェント端末・エディタタブ・ブラウザタブ・ペイン構成
削除
ディレクトリとブランチを同時に消す（確認あり）。未マージの可能性がある branch は保護され「Review N Branches」で個別判断
作成の裏側
ダイアログは即閉じ、git fetch と git worktree add はバックグラウンド。進捗行が出て失敗時は Retry
~/orca/workspaces/ └─ slides/ ← プロジェクト（1 リポ） ├─ ai-ide/ branch: ysksm/ai-ide agent: Claude Code ├─ claude-code/ branch: ysksm/claude-code agent: Codex └─ tsc-lsp/ branch: ysksm/tsc-lsp agent: Claude Code └─ .orca-preparing/ ← 作成中の一時領域

ライフサイクル

  1. Create：名前、start-from、GitHub / Linear / Jira / GitLab リンク
  2. Work：端末・エディタ・ブラウザが全部この worktree スコープ
  3. Review：diff、Annotate AI Diff、Attribution
  4. Ship：commit → push → PR → チェック待ち
  5. Archive / Delete：ワンクリック

素の git も OK

全部本物の worktree なので git rebase や cherry-pick を端末で叩いてよい。自分で git worktree add したものは「Non-Orca worktrees」から表示に切り替え可能（Claude Code の worktree も認識）。

ワークスペース設計

リポジトリの切り方「プロジェクト」= 1 つの git リポ、または関連リポの集まり。サイドバーの最上位行になる。

A. 1 リポ = 1 プロジェクト（基本）

Add Repo でローカル checkout を登録。デフォルトブランチが base ref。リポ設定でアイコン・バッジ色・base ref・Hooks・Shared Paths・AI 上書きを持つ。

B. 親フォルダをまとめて登録

複数リポを含むフォルダを追加すると「個別にインポート」か「1 つのプロジェクトグループに束ねる」かを選べる。マイクロサービス群、フロント + バック、モノレポ外の関連リポに向く。

C. リモートホスト上のリポ

SSH ホストや Remote Orca Server の checkout を「Run on」でそのホストを選んで登録。同じプロジェクトを複数ホストで「Set project location」できる。

リポ設定（Settings → Repository）でやること

  • base ref：全 worktree の分岐元。trunk が develop のリポなら変更
  • Hooks：worktree 作成後に自動実行するコマンド（依存インストール、.env 復元）
  • Worktree Shared Paths：gitignore 済みパスを主 checkout から各 worktree へ（macOS は APFS clone、他は symlink）
  • Source Control AI overrides：コミットメッセージ・PR 本文・ブランチ名の生成ルールをリポ単位で
  • アイコン／色：絵文字・画像・favicon・GitHub アバター。複数リポを並べた時の識別に

切り方の指針

  • PR を出す単位でプロジェクトを切る（PR は必ずリポ単位）
  • 一緒に変更することが多いリポは プロジェクトグループに
  • サイドバーが伸びたら「Hide sleeping / default branch / automation-created / CLI-created」フィルタで隠す。⌘J からは検索で届く
ワークスペース設計

ワークスペースの切り方：5 種類「リポではない切り方」も含めて。どれもサイドバーの 1 行で、端末・ブラウザ・タブ構成を独立して持つ。

共通の操作

pin（上部固定）、rename（タイトルをダブルクリック）、archive / sleep / delete、⌘ / Shift クリックで複数選択、⌘⇧⌫ で削除開始。

子孫ごと操作

親 worktree の右クリックに「Sleep with Descendants (N)」「Delete with Descendants…」。同じプロジェクト・リポ・ホスト内の子だけが対象。

Resource Manager

「Clean up workspaces」でローカル worktree・main worktree・フォルダワークスペース・切断中 SSH ホストの workspace をサイズ・git 状態・レビュー付きで一括整理。

CLI からの制御

orca worktree create --name review-api \
  --agent claude --setup run --json
orca worktree create --name quick-check \
  --agent codex --prompt "…" --setup skip --json

--setup run|skip|inherit（inherit はリポの方針）。--agent で最初の端末にエージェント起動、--prompt で初手を送る。

優先順位と注意

  • orca.yaml の共有ディレクトリはユーザー設定に追加（置換しない）
  • 共有済みパスは .worktreeinclude で再コピーされない。追跡中・不在・非 gitignore は警告してスキップ
  • .claude/ .codex/ CLAUDE.md AGENTS.md は Orca が読むだけで触らない
ワークスペース設計

マルチリポで 1 タスクを回す：3 パターンPR はリポ単位なので、git 上は「リポごとのブランチ」になる。Orca でそれをどう 1 つのタスクとして束ねるかの選択。

推奨 ① プロジェクトグループ + フォルダワークスペース

  • 親フォルダを Add Repo → 「グループに束ねる」
  • グループ行の「+」で Create Folder Workspace。ソースプロジェクト（Issue / PR を紐づける主リポ）を選ぶ
  • ワークスペース内の端末は親フォルダ起点。エージェントは配下リポを跨いで編集できる
  • リポごとの diff・コミット・PR は各プロジェクトの worktree／Source Control で

向く：フロント + バック + 共有スキーマのような「常に一緒に触る」構成。注意：フォルダワークスペースは worktree ではなく、配下リポの checkout をそのまま使うので、同時に 2 つのマルチリポタスクを走らせるなら②③と組む。

② 親 worktree + リポごとの子 worktree

  • 主リポで worktree を作り、そこをコーディネーター席にする
  • 子は CLI で：orca worktree create --repo id:<他リポ> --name task-api --parent-worktree active
  • サイドバーで親の下にネスト。「Sleep / Delete with Descendants」で一括操作
  • 各子 worktree は独立ブランチなので同一タスクを複数並行できる

向く：リポ間の依存が薄く、それぞれ独立に PR を出したい。注意：親子リンクはサイドバー表示専用で、git 履歴には影響しない。

③ オーケストレーション Run でリポ横断

  • run-create で Run を作り、リポごとに Task を切る
  • worker-start --worktree new-top-level --repo <selector> で各リポに新 worktree + ワーカーを配置（別ホストなら --on）
  • ワーカーは worker_done / ask で報告。決定は Gate で止める
  • 「共有 API の変更を先に完了 → フロント着手」は Task の依存関係で表現

向く：順序依存があり、ワーカーの完了を追跡したい。注意：実験的機能。Settings → Experimental で有効化が必要。

組み合わせの現実解

第 3 章 実験的

オーケストレーションRun・Task・Dispatch・Message・Gate で、監督型の多エージェント協調を組む

単発のプロンプト送信（orca terminal send）では足りない、「所有者」「完了追跡」「依存 DAG」が必要になった時のための構造化レイヤー。Settings → Experimental で有効化し、orca status --json が通ることを確認してから。

オーケストレーション

コアモデル：5 つの概念「Run は場所を決めない」「完了権限は Dispatch にある」の 2 点を押さえると設計が崩れない。

概念役割備考
Run永続的な名前空間 + コーディネーターの受信箱ワーカーのスケジュールや配置はしない
Taskspec・依存・状態を持つ作業項目pending → ready → dispatched → completed | failed | blocked
DispatchTask を 1 つの端末で試行する 1 回分。worker_done と heartbeat の権限を持つ再試行は新しい Dispatch。--retry-of は配置を継承しない
Message受信箱の郵便：status / dispatch / worker_done / escalation / question / heartbeat …check は最古の未 ack から FIFO。--ack するまで再送
Decision gateコーディネーターが持つ「決めるまで Task を止める」質問gate-create → gate-resolve
Run "checkout v2 across repos" ├─ Task schema [completed] ── Dispatch #1 → worker(claude, worktree schema/checkout-v2) ├─ Task api [dispatched] ── Dispatch #2 → worker(codex, worktree api/checkout-v2) │ └─ ask → coordinator: "shared component か page-only か？" └─ Task web [blocked by gate] gate: "v2 client を先にマージする？" → yes/no

グループアドレス

@all @idle @claude @codex @opencode @gemini @droid @grok @cursor @worktree:<id>。自分の Run の生きている Dispatch に配送（@worktree: のみコーディネーターも含む）。worker_done と heartbeat には使えない。PowerShell では引用符で囲む。

退役コマンド

orchestration run / run-stop / coordinator-start / coordinator-stop は何もしない。run-create + worker-start の流れを使う。

UI との接点

端末に出る task_… はクリック可能リンクで、担当端末にフォーカス（リモートでも）。ワーカーが作った worktree は親の下にネスト。Hibernation は未決着の Dispatch がある端末を寝かせない。

オーケストレーション

推奨の監督ループコーディネーター（人 or エージェント）が叩くコマンド列。フラグは進化するので、実運用前に orca skills get orchestration --full。

# 1. Run と Task
orca orchestration run-create --objective "Split checkout QA and summarize blockers" --json
orca orchestration task-create --spec "Audit billing settings for mobile layout" \
  --task-title "Billing audit" --json

# 2. ワーカー配置：現在の worktree で／新しい子 worktree で／モデルと effort 指定
orca orchestration worker-start --task <taskId> --worktree current --agent codex --json
orca orchestration worker-start --task <taskId> --worktree new-child --name billing-audit \
  --agent codex --setup run --json
orca orchestration worker-start --task <taskId> --worktree current --agent claude \
  --model <model-id> --effort high --json      # Claude / Codex / Cursor のみ、--terminal とは併用不可

# 3. 完了待ち：Delivery 内の全メッセージを処理してから ack
orca orchestration check --wait --types worker_done,escalation,question --timeout-ms 900000 --json
orca orchestration check --ack <deliveryId> --wait --types worker_done,escalation,question \
  --timeout-ms 900000 --json

# 4. 後片付け：出力を読むなら release 後に worker-read
orca orchestration worker-release --dispatch <dispatchId> --json
orca orchestration worker-read    --dispatch <dispatchId> --limit 50 --json
orca orchestration worker-retain  --dispatch <dispatchId> --json   # デバッグで残す時だけ

配置先の選び方

--worktree current
自分の worktree に同居。軽い調査向き
new-child
子 worktree を新設。並行実装の基本形
new-top-level --repo …
別リポに最上位 worktree。マルチリポ用
--on <host>
別ホストに federated 配置。以後は Dispatch ID で経路が決まるので --on は繰り返さない

Floating terminal との組み合わせ

⌘⌥A のフローティング端末はオーケストレーションのセットアップに対応。worktree ペインを占有せずにコーディネーター席を置ける。

低レベル API

独自トポロジーなら orca worktree create --agent codex → orca terminal wait --for tui-idle → orca orchestration dispatch --task … --to <handle> --inject。

オーケストレーション

ワーカー契約・質問・ゲート・復旧ワーカーには起動時にプリアンブルが注入され、コーディネーターへの報告義務を知る。

ワーカーの義務

  • worker_done を必ず 1 回、失敗時も送る（--outcome succeeded|failed 必須）
  • --body に「何をした・何が分かった・何が残る」の要約
  • --task-id と --dispatch-id の両方を付け、古い再試行が別 Dispatch を完了させないようにする
  • 長い作業中は heartbeat
  • ブロックする質問はローカル TUI ではなく orca orchestration ask
orca orchestration send --type worker_done \
  --subject "Completed mobile audit" \
  --body "Fixed footer overlap; no follow-ups." \
  --task-id <taskId> --dispatch-id <dispatchId> \
  --outcome succeeded --files-modified "src/app/settings/Billing.tsx" --json

orca orchestration ask --to <coordinatorHandle> \
  --question "Should I update the shared component or only this page?" \
  --options "shared,page-only" --timeout-ms 600000 --json
# → jq -r .result.answer で回答を読む

Decision gate（コーディネーター側）

orca orchestration gate-create --task <taskId> \
  --question "Merge the shared button change into the task branch?" \
  --options '["yes","no"]' --json
orca orchestration gate-resolve --id <gateId> --resolution "yes" --json

ask は「ワーカー → コーディネーター」の質問。Gate は「DAG 上の Task を決定まで止める」。

復旧

orca orchestration dispatch-show --task <taskId> --preamble --json
orca orchestration task-list --json
orca orchestration task-update --id <taskId> --status blocked \
  --result '{"reason":"waiting on credentials"}' --json

reset は最後の手段

reset --tasks|--messages|--all はランタイム全体の状態を消す。別のコーディネーターが動いている間は叩かない。release_pending / release_unknown が返ったら広い terminal close で代用せず、レシートの recovery action に従う。

オーケストレーション

「エージェントに仕事を渡す」3 段階の使い分け全部をオーケストレーションにすると重い。軽い順に。

1. orca terminal send

見ているエージェントに一言足す。--text "continue" --enter。追跡なし、所有権なし。

向く：自分が画面を見ていて、フォローアップを 1 つ投げたい時。モバイルからの「続けて」もこれ。

orca terminal send --text "continue" --enter --json
orca terminal wait --for tui-idle --timeout-ms 30000 --json

2. worker-start / dispatch --inject

ワーカーが worker_done を返し、質問はコーディネーター経由、Task ID で追跡される。

向く：1 つの独立した作業を丸ごと任せ、終わったことを確実に知りたい時。Run を作らずに単発でも使える。

orca orchestration worker-start --task <id> \
  --worktree new-child --name audit --agent codex --json

3. run-create + Tasks + Workers

永続的な Run 名前空間、複数 Task の依存 DAG、監督ループ、Gate。

向く：順序依存がある複数タスク、複数リポ、複数ホスト。あるいは「エージェントがエージェントを管理する」構成。

orca orchestration run-create --objective "…" --json
orca orchestration task-create … && worker-start …
orca orchestration check --wait …

「完全に手渡して監督しない」なら

オーケストレーションを使わず、orca-cli スキルの worktree / terminal コマンドで orca worktree create --agent codex --prompt "…" と投げ、Notifications と Agents feed で完了を拾う。コーディネーターの受信箱が要らない場面ではこれが最も軽い。

オートメーションプロンプトをスケジュールで走らせる。トリアージ・レビュー・保守を人が worktree を開かずに始める

「毎朝 9 時に新着 Issue を分類」「毎時レビュー依頼された PR を見る」「18 時に今日の変更を要約」。Automations ページと orca automations の両方から同じものを扱う。

オートメーション

オートメーションの作成と設定項目公式の手順は「--disabled で作る → show で確認 → run で手動実行 → 納得したら --enabled」。

# まず無効状態で作る
orca automations create \
  --name "Weekday triage" \
  --trigger weekdays --time 09:00 --timezone Asia/Tokyo \
  --prompt "Triage new issues and summarize blockers" \
  --provider codex \
  --repo my-repo \
  --disabled --json

# 手動で 1 回走らせて確認 → 有効化
orca automations run  <automationId> --json
orca automations runs --id <automationId> --json
orca automations show <automationId> --json
orca automations edit <automationId> --enabled --json

# 既存 worktree の中で cron 式実行
orca automations create --name "Nightly status" --trigger "0 18 * * 1-5" \
  --prompt "Summarize today's changes" --provider claude \
  --workspace active --disabled

--triggerhourly / daily / weekdays / weekly、cron 式、RRULE
--time / --timezone実行時刻と IANA タイムゾーン
--provider使うエージェント（codex / claude …）
--repo <sel>実行ごとにそのリポで作業（worktree を作成／選択）
--workspace <sel>既存 worktree の中で実行。両方省略時は現在ディレクトリの worktree
--project / --host特定ホスト上のプロジェクトセットアップを対象に（--project-host-setup <id> でも）
--precheck "cmd"シェルコマンドが非 0 なら「skipped」として記録し実行しない

オートメーション

運用のコツと他機能との組み合わせ

precheck で「空振り」をゼロにする

orca automations create --name "PR review" --trigger hourly \
  --precheck "gh pr list --search 'review-requested:@me' --json number -q .[0].number" \
  --prompt "Review requested PRs" --provider codex --repo my-repo --disabled --json

レビュー依頼が無ければエージェントは起動しない。gh のレート制限にも優しい（Settings → Git の GitHub API Budget を見ながら間隔を決める）。

対象の選び方：--repo か --workspace か

  • --repo：実行ごとに worktree を作る／選ぶ。成果物が「変更 + PR」になる仕事（依存更新、lint 修正、Issue 対応）
  • --workspace + --reuse-session：同じ端末で継続。「要約」「監視」「日報」のような状態を積む仕事
  • 自動作成された worktree はサイドバーの「Hide automation-created」で普段は隠せる

ホスト横断で管理する

  • Automations ページは、このマシンと接続済み Orca ホスト（Remote Orca Server、SSH）のスケジュールを 1 表に。Host 列と Filters → Host

  • 常時稼働させたいなら Remote Orca Server 側に作る（ノート PC が閉じていても走る）
  • SSH ホスト切断中でも一覧に残り、削除できる

失敗時と一覧の使い方

  • workspace を開く前に失敗した run は Orca 内で「Rerun」
  • Filters：Host / Enabled・Paused / 直近結果（Failed・Succeeded・Never ran）/ Agents。検索は name・project・prompt
  • Notifications と Agents feed は自動実行の完了も拾う。夜間実行の結果は朝 Dashboard の Done 列に並ぶ
  • Workspace status の recipe と組み合わせ、自動実行が終わったら in-review にさせる

レビュー：Diff viewer・Annotate AI Diff・AttributionAI の差分を「真面目にレビューしてから出荷する」ための 3 点セット。

Diff viewer

  • スコープ切替（作業ツリー／staged／コミット）
  • エディタ側にも「Changes」表示モード

Annotate AI Diff

  1. 行にホバー → ガターの「+」（または c）
  2. Markdown でコメント、⌘↵ で保存
  3. 「Send to agent」→「Send notes to」で worktree 内のエージェントを選ぶ（新規起動も可）
  4. コメントは行に追従。修正後に Resolve、未解決は次回のバッチに含まれる

なぜバッチか：1 件ずつ送るとエージェントが右往左往する。1 回の思考・1 回の修正で当たりが上がる。ショートカット「Send Review Notes to Agent」は既定で未割当。

  • エージェントがツール経由で書いた範囲を記録し、ガターに AI 由来マークを表示。人が上書きすると人間に戻る
  • 「どこを重点的に読むか」「監査で AI 由来を分離」「自分で書いた所は読み直さない」
  • ローカルのみで git にコミットされない。残したければ Diff ツールバーからメタデータをエクスポート

レシピ：3 エージェント競争のレビュー

SSH と Remote Orca Server の違い

リモート実行は常に自分の管理下のマシンとクラウド口座。Cloud VM はプロバイダの create / suspend / resume / destroy スクリプトを Orca が呼び、返ってきたペアリング URL または SSH 情報に繋ぐだけ。

まとめ

まとめ

  • 単位を揃える：プロジェクト = リポ（PR の単位）、ワークスペース = タスク（worktree／フォルダワークスペース）。マルチリポはプロジェクトグループ + リポごとの worktree で束ねる
  • 新規 worktree を即戦力にする：orca.yaml（setup、sharedDirectories）と .worktreeinclude をリポにコミットしておく
  • 状態を機械に書かせる：Agent status hooks + orca worktree set。人は Dashboard の Needs You と in-review だけ見る
  • 仕事の渡し方は 3 段階：terminal send → worker-start → run-create + Tasks + Gates。重い方から始めない
  • 定期作業は Automations：--disabled → run → --enabled。--precheck で空振りを消し、常時稼働ホストに置く
  • レビューは束ねて返す：Annotate AI Diff で 1 バッチ、Attribution で自分の手直しを守る
  • 実行環境は混ぜてよい：手元・SSH・Remote Orca Server・Cloud VM を worktree ごとに選ぶ
