01 / 方針

既存 Redmine を残し、よく使う画面から置き換える

チケット一覧・詳細・更新を SPA にする。
データと権限判定は Redmine を利用する。

  • Web 版の出発点は、同一オリジンで配信する SPA + BFF。
  • 管理・プラグイン固有画面は、既存 UI へのリンクを用意する。
  • デスクトップ版は、同じ UI に Electron / Tauri の通信層を組み合わせる。

前提：既存 Redmine を運用中。バージョン・認証基盤・導入プラグインは未指定。

設計提案。参考: Redmine REST APIElectron process modelTauri overview

02 / UI 置き換え

置き換える範囲で実装方式が変わる

方式できること保守上の論点
テーマ配色・余白・既存画面の外観調整SPA 化のための API や画面遷移は別実装
Redmine プラグイン独自ページ・メニュー・API を追加本体・Rails・他プラグインとの互換性
独立 SPA + REST API画面と配信を Redmine から分離API にない操作の扱いを決める
本体ビュー改変 / fork既存画面を広範囲に変更アップグレード時に差分の追従が必要

本資料の提案：独立 SPA を基本にし、不足機能だけプラグインで補う。

設計提案。参考: ThemesPlugin TutorialRedmine REST API

05 / 認証

どの利用者の権限で API を呼ぶか

方式認証情報の場所適用条件
利用者 API キーを直接送るブラウザの実行メモリ小規模 PoC。再読込時の再入力を許容
BFF が利用者キーを保持サーバーの秘密情報ストアブラウザには BFF のセッション Cookie
プラグイン + 既存セッションRedmine のセッション専用 API の認証・CSRF 対策を実装
管理者キー + 代理ユーザーサーバーのみ強い信頼境界。必要な場合に限定

SSO で BFF にログインしても、Redmine の権限は自動では引き継がれない。本人と Redmine アカウントの対応を検証する。

設計提案。参考: Redmine REST APIPlugin Tutorial

06 / 別 Web サーバー

リバースプロキシと BFF は役割が違う

Browser   →   NGINX   →   BFF   →   Redmine

構成要素役割その要素だけでは解決しないこと
NGINXTLS 終端、静的 SPA 配信、パス振り分け利用者ごとのキー管理・業務 API の合成
BFF（UI 専用のバックエンド）セッション、利用者キー付与、応答整形Redmine にない業務機能の自動生成
Redmineデータ保存、権限判定、業務ルール新しい SPA のルーティングと表示

単純中継だけならプロキシでも構成可能。キー管理や SSO 連携が必要なら BFF を追加する。

設計提案。参考: NGINX proxy moduleRedmine REST API

07 / 配信設定

同じ公開オリジンで SPA と BFF を配信する

# TLS server ブロック内の抜粋。BFF は /api/* を受け付ける。
root /srv/redmine-spa/dist;
location /api/ {
    proxy_pass http://127.0.0.1:3001;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}
location / {
    try_files $uri $uri/ /index.html;
}

/issues/42 の直リンクは SPA に戻し、/api/... は BFF に送る。

proxy_pass に URI 部分がないので /api/ を保持。既存 Redmine UI は別ホストで併用する設計例。TLS 設定などは research.md を参照。

設計提案。参考: NGINX proxy moduleVite static deploy

08 / CORS

サーバーの設置場所より、ブラウザから見た URL が重要

ブラウザからの呼び出しCORS必要な設計
https://tasks.example → 同じ /api/クロスオリジンではないCookie・CSRF・BFF の認証は別途必要
https://tasks.example → https://redmine.exampleクロスオリジン許可 Origin・メソッド・ヘッダーを設定
BFF → Redmineブラウザの CORS 対象外TLS・接続先制限・タイムアウトを設定

API キーヘッダーや JSON 更新では preflight が発生し得る。Cookie を使う場合、許可 Origin に * は使えない。

別ホスト・別ポートは別オリジン。CORS は API の認証・認可を代替しない。

出典: MDN CORS

09 / API の不足

プラグインで不足部分を小さく補う

Redmine 内で追加するもの

  • SPA の入口とメニュー
  • 標準 API にない操作の専用エンドポイント
  • 画面で必要な入力候補の取得

実装時に維持するもの

  • プロジェクトと利用者の認可
  • 既存の検証・履歴・通知処理
  • セッション認証時の CSRF 防御

DB への直接書き込みは避ける。Redmine 内のモデル操作でも、権限・履歴・通知が成立する経路を明示してテストする。

既存 HTML の DOM 置換は、マークアップ変更への追従が必要。長期運用では専用ページを優先する。

設計提案。参考: Plugin Tutorial

10 / 書き込み

更新・添付は成功以外の経路も設計する

チケット更新

PUT /issues/42.json
Content-Type: application/json

{"issue":{"notes":"確認しました"}}

添付は 2 段階

  1. POST /uploads.json にファイル本体を送信
  2. 返却された token をチケットの uploads に指定
  • 入力不備の 422 をフォームに表示し、権限不足・再認証と分ける。
  • 送信結果が不明なときは再取得して確認する。作成・コメントの自動再送は重複に注意。

同時編集の扱いは実機で確認し、変更通知・再読込・競合表示を設計する。

設計提案。参考: Redmine REST APIIssues API

11 / デスクトップ

PWA・Electron・Tauri の比較

方式適した条件実装・運用の負担
PWAWeb 配信中心、アプリ風の起動で足りるmanifest・HTTPS。OS / ブラウザ差を確認
ElectronNode.js 資産や統一した描画環境を使いたいChromium を同梱。更新と IPC の管理
Tauri 2OS の WebView と Rust 側処理を使いたいRust のビルド環境、OS ごとの表示検証

アプリ化だけではオフライン更新や同期は増えない。必要ならキャッシュ・更新キュー・競合解決を別途実装する。

12 / Electron

Renderer に API キーを渡さない構成

SPA Renderer   →   preload / IPC   →   main   →   Redmine

  • 同梱した UI を表示し、preload で listIssues() などの操作だけ公開する。
  • main 側でキーを取り出し、接続先・引数・IPC の送信元を検証する。
  • nodeIntegration: false、contextIsolation: true、sandbox を維持する。
  • キー保存には safeStorage 等を検討。Linux の basic_text では永続保存を避ける。

任意 URL を受け取る汎用 fetch の公開は避け、許可した Redmine への業務操作に限定する。

設計提案。参考: Electron process modelElectron securityElectron safeStorage

13 / Tauri

Rust 側に通信と秘密情報をまとめる

SPA WebView   →   invoke   →   Rust command   →   Redmine

  • WebView は画面を担当し、Rust command が利用者キーを付けて API を呼ぶ。
  • capabilities / permissions で呼び出せる機能を制限する。独自 command の引数も検証する。
  • HTTP plugin を使う場合は接続先スコープを限定する。キーを JS に返さない。
  • Stronghold などの保管先と、解除用パスワード・鍵の管理を設計する。

ネイティブ側の HTTP はブラウザ CORS の制約外。通信をネイティブへ移しても、認証や接続先検証は必要。

設計提案。参考: Tauri overviewTauri capabilitiesTauri HTTP clientTauri Stronghold

14 / 配布

Web と Desktop で共通化する範囲

共通化するもの環境ごとに実装するもの
一覧・詳細・編集 UI、入力検証Web：BFF セッション / Desktop：ネイティブ通信
業務操作と DTO、表示エラーWeb：URL ルート / Desktop：deep link の受け口
画面・API 契約のテストDesktop：OS ごとのビルド・署名・更新配布

Web UI をウィンドウで開く方式は着手しやすい。同梱 SPA は版を固定できるが、配布と更新の仕組みが必要になる。

PWA では manifest と HTTPS を用意し、対象環境のインストール条件を確認する。

設計提案。参考: Electron process modelElectron securityTauri overviewMDN PWA installability

15 / 導入手順

PoC で確認してから、書き込み範囲を広げる

段階実施すること完了条件
1. 環境確認バージョン、認証、プラグイン、API 有効化必要操作と未対応操作の一覧がある
2. 読み取り一覧・検索・詳細を SPA で表示異なる権限の利用者で可視性が一致
3. 書き込みコメント・状態変更・添付履歴・通知・入力エラー・重複を確認
4. 展開BFF 配信、必要なら Desktop を追加直リンク・再認証・更新・復旧を確認

既存 UI への導線を残し、問題時は SPA の利用を止められる構成にする。
