Oxlint で独自の
Lint ルールを作る

Rust 製リンタ Oxlint に、ESLint 互換の JS プラグイン API で自社ルールを載せる。最小構成から context API・自動修正・createOnce・RuleTester・設定・制限、そして Rust ネイティブルールまでを一通り。

2026-09-15oxlint 1.83.0oxc-project (Rust)

Summary

結論を先に：独自ルールは「JS プラグイン」で書く

① JS プラグインが本命 推奨

Oxlint のプラグイン API は ESLint v9+ と互換。create(context) に AST ビジタを書き、.oxlintrc.json の jsPlugins に登録するだけで動く。JavaScript でも TypeScript でも書ける。

既存の ESLint カスタムルールは、多くの場合そのまま移植できる（コピーして登録するだけ）。

② Rust ネイティブは原則不要 OSS 貢献の話

公式は「JS プラグインが使えるようになったので 新しい Rust 製プラグインは追加しない」方針。Rust の出番は 既存プラグインへのルール追加＝ oxc への貢献で、自社ルールの手段ではない。

全ユーザーに効く汎用ルールなら PR を歓迎、という位置づけ。

③ ただし現状は alpha 2026-09 時点

ESLint の API 面はほぼ実装済み（自動修正・スコープ解析・LSP まで）。一方で 型情報を使う独自ルールと Vue / Svelte / Angular の独自ファイル形式は未対応。

挙動が ESLint と違えば「バグとして報告してほしい」というのが公式の立場。

最短ルート：npm add -D oxlint → plugin.js に create を書く → jsPlugins に登録 → npx oxlint（次スライド以降で詳細）

What it is

前提：Oxlint とは何か

  • oxc（The JavaScript Oxidation Compiler）プロジェクトの Rust 製 JS/TS リンタ。公式ブログによれば 650 以上の人気ルールを Rust で内蔵し、ネイティブ速度で走る。
  • ESLint 比の速度向上は ベンチマークで概ね 4x〜100x。設定は .oxlintrc.json または oxlint.config.ts。
  • JS プラグイン（本スライドの主題）が「Rust で実装されていないルール」の穴を埋める。既存 ESLint プラグインの実行と、独自ルールの作成の両方を担う。
  • 型情報が要るルールは別系統：oxlint --type-aware が Go 製 tsgolint（typescript-go）を呼び、typescript-eslint の型認識ルール 61 個中 59 個に対応。TypeScript 7.0+ が前提。
  • 本番採用例として Preact・PostHog・Outline・Actual・Midjourney などが挙げられている。

数値はいずれも oxc 公式ドキュメント／公式ブログ（2026-03-11「Oxlint JS Plugins Alpha」）の記載。バージョンは npm の oxlint@1.83.0（2026-09-14 公開）時点。

# 導入（dev 依存） $ npm add -D oxlint # 実行 / 自動修正 $ npx oxlint $ npx oxlint --fix # 型認識ルール（tsgolint 経由） $ npx oxlint --type-aware # 動作要件（package.json の engines） node: "^20.19.0 || >=22.12.0" # ESLint 設定からの移行ツール $ npx @oxlint/migrate eslint.config.js

Options

Hello world

最小構成：3 ファイルで独自ルールが動く

// plugin.js — クラス宣言が 6 個以上のファイルを警告 const rule = { create(context) { let classCount = 0; return { ClassDeclaration(node) { classCount++; if (classCount === 6) { context.report({ message: 'Too many classes', node }); } }, }; }, }; const plugin = { meta: { name: 'best-plugin-ever' }, rules: { 'max-classes': rule }, }; export default plugin;

出典：oxc 公式ドキュメント「Writing JS Plugins」のサンプルに注釈を加えたもの。

// .oxlintrc.json { "jsPlugins": ["./plugin.js"], "rules": { "best-plugin-ever/max-classes": "error" } }
// oxlint.config.ts でも同じことが書ける import { defineConfig } from 'oxlint'; export default defineConfig({ jsPlugins: ['./plugin.js'], rules: { 'best-plugin-ever/max-classes': 'error' }, });

ここだけ押さえる

  • ルール名は <meta.name>/<rules のキー>。プラグイン名が名前空間になる。
  • jsPlugins のパスは 設定ファイルからの相対で解決される。
  • プラグインは default export。npm パッケージ名でも指定できる。

呼び出し規約

  • create は ファイルごとに 1 回、毎回新しい context で呼ばれる。ファイル単位の状態はここのローカル変数で持つ。
  • ビジタは AST を 深さ優先で下る時に発火。"ノード名:exit" は登る時。ファイル全体を見てから判定するなら Program:exit。
  • 診断の重大度はルール側では決めない。rules の設定値（"error" / "warn" / "off"）が決める。

ESLint 経験者向けの差分

書き方は ESLint と同一。違うのは「登録先が plugins ではなく jsPlugins」という設定側だけ。加えて Oxlint 独自の高速版 API createOnce がある（スライド 11）。

Recipe ①

実践：禁止 import を検出するルール（TypeScript）

// tools/oxlint-plugin/no-direct-dayjs.ts import { defineRule } from '@oxlint/plugins'; export const noDirectDayjs = defineRule({ meta: { type: 'problem', messages: { useWrapper: 'dayjs ではなく @/lib/date を使ってください', }, }, create(context) { return { ImportDeclaration(node) { if (node.source.value !== 'dayjs') return; // 許可されたラッパ自身は対象外にする if (context.filename.includes('/lib/date')) return; context.report({ node, messageId: 'useWrapper' }); }, }; }, });
// tools/oxlint-plugin/index.ts import { definePlugin } from '@oxlint/plugins'; import { noDirectDayjs } from './no-direct-dayjs.js'; export default definePlugin({ meta: { name: 'house-rules' }, rules: { 'no-direct-dayjs': noDirectDayjs }, });
// .oxlintrc.json { "jsPlugins": ["./tools/oxlint-plugin/index.ts"], "rules": { "house-rules/no-direct-dayjs": "error" } }

ポイント

  • definePlugin / defineRule は 型付けのための薄いヘルパで、付けなくても動く。型 Context / Rule / ESTree も同パッケージから取れる。
  • TypeScript でルールを書ける（alpha で TypeScript プラグイン対応が入った）。
  • messages + messageId にしておくと、テストで文言に依存せず検証できる。

Recipe ②

実践：オプションと自動修正を付ける

オプション

meta.schema に JSON Schema を書き、context.options[0] で受け取る。設定側は ["error", { … }] の配列形式。

自動修正

meta.fixable: 'code' を宣言し、report に fix(fixer) を渡す。fixer は replaceText / insertTextBefore / remove などの ESLint と同じ API。

適用するコマンド

oxlint --fix安全な修正（挙動を変えない）
--fix-suggestions挙動が変わりうる提案
--fix-dangerously壊す可能性のある強い修正

エディタ拡張では「コードアクション」として提示される。既定では何も適用されない（明示フラグが必要）。

// 非推奨 API を新しい API に置換するルール（抜粋） const rule = { meta: { fixable: 'code', // ← これが無いと fix は無視される messages: { deprecated: '{{from}} は非推奨。{{to}} を使う' }, schema: [{ // ← オプションの JSON Schema type: 'object', properties: { mapping: { type: 'object' } }, }], }, create(context) { const { mapping = {} } = context.options[0] ?? {}; return { 'CallExpression > Identifier.callee'(node) { const to = mapping[node.name]; if (!to) return; context.report({ node, messageId: 'deprecated', data: { from: node.name, to }, // ← {{…}} に埋まる fix: (fixer) => fixer.replaceText(node, to), }); }, }; }, }; // .oxlintrc.json — 設定側 "house-rules/no-deprecated-api": ["error", { "mapping": { "formatDateOld": "formatDate" } }]

Performance API

代替 API：createOnce と before / after フック

import { eslintCompatPlugin } from '@oxlint/plugins'; const rule = { createOnce(context) { // ← 全体で 1 回だけ let classCount; return { before() { // ← ファイルごとの初期化 classCount = 0; }, ClassDeclaration(node) { classCount++; if (classCount === 6) { context.report({ message: 'Too many classes', node }); } }, after() { /* 後始末（任意）*/ }, }; }, }; export default eslintCompatPlugin({ meta: { name: 'best-plugin-ever' }, rules: { 'max-classes': rule }, });

before() が false を返すとそのファイルはスキップされる（ESLint の「空ビジタを返す」に相当）。

なぜこの API があるのか

ESLint の create はファイルごとに任意のビジタを返せるため、Rust 側は「このルールがどのノードに関心があるか」を事前に知れず、毎ファイル JS を呼ぶしかない。createOnce なら一度呼べば分かるので、① 関心ノードへのポインタ列だけを Rust から渡す、② 該当ノードが無いファイルは JS を呼ばない、という最適化ができる。

公式の但し書き

  • 「今は速くない。でもすぐ速くなる」— 最適化は順次投入予定で、createOnce で書いておけば バージョンを上げるだけで恩恵を受けられる。
  • before / after は 全ファイルで走る保証がない（将来スキップされうる）。必ず毎ファイル実行したい処理は Program(node) ビジタに置く。
  • before が false を返した場合、after も実行されない。

Interop

ESLint と Oxlint の両方で動かす

eslintCompatPlugin の役割

プラグイン内の各ルールに createOnce へ委譲する create を生やすだけの薄いラッパ。結果として同じプラグインが：

  • Oxlint では createOnce の高速パスで動く
  • ESLint では通常の create ルールとして動く

npm 公開時の注意

  • @oxlint/plugins は runtime dependency に入れる（devDependencies ではない）。
  • 同パッケージは ESM / CommonJS 両方のエントリを持ち、Node.js 12.22+ で動く（ESLint 8 の最低要件に合わせてある）。
  • つまり公開プラグインは Oxlint の任意バージョン + ESLint 8 以降の両対応にできる。

移行期の現実解

  • ESLint と Oxlint は併走できる。まず Oxlint を CI に足し、ESLint 側を段階的に削る。
  • 社内ルールを両対応にしておけば、切り替えの可逆性が確保できる。
  • ESLint 設定の変換は npx @oxlint/migrate eslint.config.js。

Testing

ルールをテストする：RuleTester

import { RuleTester } from 'oxlint/plugins-dev'; import { describe, it } from 'vitest'; import { maxClasses } from './max-classes.js'; RuleTester.describe = describe; RuleTester.it = it; const ruleTester = new RuleTester({ languageOptions: { parserOptions: { lang: 'ts' } }, }); ruleTester.run('max-classes', maxClasses, { valid: [ 'class A {}', // ちょうど上限 'class A {} class B {} class C {} class D {} class E {}', // 式は宣言ではないので数えない 'const a = class {}; const b = class {};', ], invalid: [ { name: 'the sixth declaration', code: 'class A {} … class F {}', errors: [{ messageId: 'maxClasses', line: 1, column: 55, endColumn: 65 }], }, ], });

使い方

  • ESLint の RuleTester と同じ思想の API を oxlint/plugins-dev が提供する。
  • テストランナーは任意（例は Vitest）。RuleTester.describe / .it に注入する。
  • valid は誤検知しないこと、invalid は期待する診断が出ることを確認する。

テストで押さえるケース

  • 境界値（上限ちょうど / 1 つ超え）
  • 似ているが対象外のコード（クラス式、動的 import、型だけの import など）
  • オプションの各パターン（options: [{ … }]）
  • 自動修正を持つなら output で修正後のコードを固定する

ルールは「検出漏れ」より 誤検知で信頼を失う。valid ケースを厚く書くほうが実務では効く。

Config

設定リファレンス：jsPlugins の指定方法

// 3 通りの指定（いずれも import 指定子として解決） { "jsPlugins": [ "./path/to/my-plugin.js", // 設定ファイルからの相対パス "eslint-plugin-whatever", // npm パッケージ "@foobar/eslint-plugin" // スコープ付きパッケージ ], "rules": { "my-plugin/rule1": "error", "whatever/rule2": "warn", "@foobar/rule1": "error" } }

エイリアスが要る場面

  • ネイティブプラグイン名（jsdoc / react など）と衝突する
  • 名前が長すぎる
  • ネイティブ実装済みだが、欲しいルールだけ未実装のとき、JS 版を別名で併用する

設定ファイルの形式

  • .oxlintrc.json（JSONC）と oxlint.config.ts（defineConfig）
  • ディレクトリごとのネスト設定に対応
  • 重大度は "error" / "warn" / "off"、オプションは配列形式

よくある詰まり

  • パスの基準は 設定ファイルであって cwd ではない
  • ルール名の接頭辞は プラグインの meta.name（パッケージ名ではない）
  • jsPlugins に入れただけでは何も有効にならない。rules での明示が必要

oxlint-plugin-eslint

ESLint の組み込みルール全部を JS プラグインとして詰めたパッケージ。Oxlint にネイティブ実装がまだ無い no-restricted-syntax などを、自作せずに使えるようにする。

判断基準：セレクタ 1 本で書ける禁止なら設定で済ませる。状態を持つ・相関を見る・自動修正したい、のいずれかが要るなら独自ルールを書く。

Design

設計指針：何をルールにし、どう運用するか

ルール化に向くもの

  • 機械的に判定できて、例外が少ない規約（禁止 import、禁止 API、レイヤ間依存、命名パターン）
  • レビューで毎回同じ指摘をしているもの
  • 壊れると事故になるが、目視では見落とすもの

逆に「設計が良いか」「命名が適切か」といった判断は、ルールにすると誤検知だらけになる。

誤検知を抑える作法

  • まず 狭く作る。対象パスやノード種別を絞り、必要になってから広げる。
  • 正当な例外は オプション（allowList）で逃がす。コメントでの無効化（// oxlint-disable-next-line）も想定しておく。
  • メッセージは命令形で「どう直すか」まで書く（oxc 自身のルール作法でもある）。

運用

  • 導入時は "warn" で入れて件数を見る → 既存違反を潰す → "error" に上げる。
  • ルールは リポジトリ内の tools/oxlint-plugin/ に置き、テストを CI で回す。複数リポジトリで使うなら npm パッケージ化。
  • 自動修正を付けられるルールは付ける。--fix 一発で移行できると定着が速い。

ルールは「増やすこと」ではなく「レビューの手間を減らすこと」が目的。使われない・無効化だらけのルールは消す判断も運用のうち。

Limitations

制限と注意点（2026-09 時点）

仕様上できないこと

  • 型情報を使う独自ルールは書けない。「この式の型が Promise なら」といった判定は不可。typescript-eslint の型認識ルール自体は --type-aware で内蔵提供される（61 個中 59 個）。
  • Vue / Svelte / Angular などの独自ファイル形式は限定的な対応にとどまる（公式は「今年後半に対応予定」）。独自パーサも未対応。
  • ESLint v9 より前の API しか使っていない未メンテのプラグインは、原則動かない。

既知の不具合

Windows でメモリ不足エラーが報告されている（既知の issue）。回避策として WSL での実行が案内されている。

書き方で踏みやすい落とし穴

  • before / after は 毎ファイル実行が保証されない。必ず走らせたい初期化は Program ビジタへ。
  • create（ESLint 形式）はファイルごとに呼ばれる。重い初期化をここに書くとファイル数ぶん効いてくる。createOnce + before に寄せる。
  • プラグインのコード自体の速度は Oxlint の管轄外。ファイル I/O や重いアルゴリズムは ESLint と同じだけ遅い。
  • JS プラグインは alpha。ESLint と挙動が違えばバグとして報告する（それが公式の想定）。

出典：oxc 公式ドキュメント「JS Plugins」および公式ブログ「Oxlint JS Plugins Alpha」（2026-03-11）。進捗はトラッキング issue で追える。

速さの仕組み：raw transfer

AST を JSON にせず Rust のメモリ配置のまま JS へ渡す。さらに 遅延デシリアライズで、ルールが実際に触ったノードだけを JS オブジェクト化する。Rust ↔ JS の往復コストが native ツールの宿命的ボトルネックだったが、これをほぼゼロに近づけた。

初代の技術プレビュー（2025-10）では Vue core で ESLint 4,116ms に対し Oxlint 単体 48ms、JS プラグイン込み 236ms という比較が示されていた。

公式の性能 tips

  • 整形はフォーマッタに寄せる。Oxfmt（Prettier 比 30x）に移すと、Stylistic 系プラグインぶんの linting 時間が丸ごと消える。
  • プラグインを選ぶ。遅いプラグインは Oxlint 上でも遅い。

Checklist

導入手順：既存プロジェクトに独自ルールを載せるまで

1
現状を移す 半自動
npm add -D oxlint の後、npx @oxlint/migrate eslint.config.js で .oxlintrc.json を生成。まずは 既存 ESLint 設定の再現から始める。
2
穴を埋める 設定だけ
ネイティブ実装が無いルールは jsPlugins に既存 ESLint プラグインを追加して補う。名前が衝突するものはエイリアス（{ name, specifier }）で回避する。
3
独自ルールを書く 本題
tools/oxlint-plugin/ に createOnce + eslintCompatPlugin で実装（ESLint 併走が不要なら素の create でよい）。messageId を使い、可能なら fix も付ける。
4
テストする 必須
oxlint/plugins-dev の RuleTester + Vitest。valid ケースを厚く書いて誤検知を潰す。ルールの追加・変更時は必ずテストも更新する。
5
段階的に有効化 運用
"warn" で入れて件数を確認 → --fix と手作業で既存違反を解消 → "error" に昇格。CI では oxlint を必須チェックにし、エディタ拡張も配る。
6
ESLint を畳む 任意
型認識ルールが必要なら --type-aware に寄せる。Vue / Svelte の独自ファイル形式など未対応領域が残る場合のみ、その範囲だけ ESLint を併走させる。

Wrap-up

まとめと参考資料

要点

  • Oxlint の独自ルールは ESLint 互換の JS プラグインで書く。create(context) にビジタ、jsPlugins に登録、それだけ。
  • 書く前に探す：既存 ESLint プラグイン → eslint-js/no-restricted-syntax + セレクタ → それでも無ければ自作。
  • 新規は createOnce + before で書く。ESLint 互換は eslintCompatPlugin が保証し、将来の最適化も無改修で乗る。
  • 型情報は使えない。型が要る判定は --type-aware の内蔵ルールか、ESLint 併走で。
  • JS プラグインは alpha だが、ESLint 本体のテスト 33,006 件が 100% 通る水準。実プロジェクトでの採用を想定した段階にある。
