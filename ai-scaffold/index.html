はじめに

前提アーキテクチャ：4 レイヤーと、生成すべきものRails の model / controller / view / migration は、このレイヤー構成では次のように対応する。

PresentationReact / Hooks / Redux　≒ Rails の view + controller の入口
Redux slice（状態と thunk）、ユースケースを呼ぶ Hook、一覧・詳細・フォームのページ／コンポーネント、ルート登録
Applicationプレゼンとドメインの橋渡し　≒ controller の中身
ユースケース（Command / Query）、入出力 DTO、Repository ポートの利用、DI トークン
DomainEntity 中心、VO と ID を厳重に　≒ model
ID 型（branded）、Value Object、Entity / Aggregate、Repository インターフェース（ポート）、不変条件のテスト雛形
InfrastructureDIP でドメインに従属　≒ ActiveRecord の実装側
API Repository 実装（生成クライアント経由）、テスト用バックエンド／インメモリ Repository、DTO ⇄ Entity Mapper、DI 登録

依存の向き

Presentation → Application → Domain ← Infrastructure。Infrastructure は Domain のポートを実装する（DIP）。生成器はこの向きを破るコードを出せないようテンプレートを固定し、arch lint でも守る。

Rails と決定的に違う点

  • DTO（API の型）と Entity は別物。必ず Mapper を挟む
  • 「1 テーブル = 1 モデル」ではなく「1 集約 = 複数 Entity + VO」
  • 配線先が 3 つある（DI コンテナ・Redux store・ルーター）

用語：本資料では Rails の「モデル情報」に相当する入力を生成仕様（spec / マニフェスト）と呼ぶ。

Part 1

検討メモ

Rails generate が成立する理由から逆算し、「何を決定論で書き、何を AI に判断させ、何を生成後に書くか」を切り分ける。ここでの結論が、提案 4 案の評価軸になる。

検討 1

Rails generate はなぜ成立するか生成器が賢いのではなく、規約が強い。フロントエンド DDD に足りないのは規約の方。

Rails が持っているもの

命名規約Order → orders テーブル、OrdersController、app/views/orders/。名前 1 つから全パスが決まる
配置規約レイヤーごとの固定ディレクトリ。生成器は「どこに置くか」を考えない
モデル定義の唯一の入力name:string price:integer という 1 行の DSL。曖昧さがない
generate once生成されたファイルはその後ユーザーのもの。再生成で上書きしない（--skip / --force は明示）
差分は migrationスキーマ変更はファイルの再生成ではなく、追加の migration で表現
配線の規約routes.rb に 1 行足すだけ。DI もコンテナも無い

このプロジェクトに足りないもの（＝先に作るもの）

① 命名・配置規約の明文化

「集約 Order のユースケースはどこに、何という名前で置くか」が文書化・機械可読になっていないと生成器は書けない。手書きのリファレンス実装 1 集約をまず用意し、それを規約にする。

② モデル定義の唯一の入力形式

TypeSpec は API の形は表せるが、「どれが VO か」「集約境界はどこか」「不変条件は何か」は表せない。ドメイン意味を載せた生成仕様が別に要る。

③ 配線の規約

DI コンテナ登録・Redux reducer 登録・ルート登録の 3 か所。「どこに何を足すか」が規約化されていないと、生成器は既存ファイルを壊す。

結論：ジェネレーターの前に規約。Phase 0 はコードを生成せず、リファレンス実装と規約文書を作る工程に充てる。

検討 2

3 つのゾーン：決定論で書ける／AI が判断する／生成後に書く「どこまで自動化するか」の議論は、この境界線を先に引くと収束する。

Zone 1　決定論 — スクリプトが書く

  • ファイルパス・ファイル名・命名（PascalCase / camelCase / kebab）
  • import 文、barrel export、ヘッダコメント
  • ID 型（branded type）と ID を持つ VO の骨格
  • Repository インターフェース、インメモリ／テストバックエンド実装
  • DTO ⇄ Entity Mapper の骨格（フィールド対応表）
  • Redux slice / Hook / CRUD ページの骨格
  • DI・store・ルートの配線、テストファイルの雛形

原則：ここは決して AI に書かせない。同じ仕様から毎回同じバイト列が出る。

Zone 2　判断 — AI が「引数」を決める

  • 集約の境界（何を 1 集約にするか）
  • どのフィールドを VO にし、どれをプリミティブのままにするか
  • 他集約への参照（CustomerId のような ID 参照）の同定
  • ユースケースの列挙と Command / Query の分類
  • 画面の種類（一覧・詳細・フォーム・カスタム）
  • 今回の生成範囲（レイヤー・成果物）
  • 入力が曖昧なときの命名

原則：判断の結果は必ず生成仕様（ファイル）に落とし、人がレビューできる形にする。

Zone 3　創作 — 生成後に AI／人が書く

  • Entity の不変条件・業務ルール（place() の中身）
  • VO のバリデーション（金額は 0 以上、など）
  • CRUD で表せない画面・複雑な UI 状態
  • エラーハンドリング方針、認可
  • 非 CRUD ユースケースの本体

原則：生成器は // TODO(gen): マーカーだけ置き、中身を書かない。ここを生成器で頑張るとテンプレートが肥大し、決定論が崩れる。

「自動生成をどこまで行うかはその都度異なる」は、Zone 1 の中でどの成果物を出すかを選ぶ問題（部分生成）と、Zone 3 をAI に任せるか人が書くかの 2 つに分解できる。前者は生成器の機能、後者はワークフロー（スキル）の問題。

検討 4

生成仕様（spec）= AI が考える「引数」CLI 引数ではなく、スキーマ付きのファイルにする。これが「決定論的に進めつつ AI に引数を考えさせる」の実装形。

性質CLI 引数（gen model Order name:string）仕様ファイル（spec/order.yaml）
表現力フラット。集約・VO・ユースケースの入れ子を書けない入れ子・配列・参照を素直に書ける
レビューシェル履歴に残るだけPR の diff で「AI が何を判断したか」が見える
再実行同じコマンドを打ち直すgen apply で何度でも同じ結果。CI でも実行できる
検証引数パーサ頼みJSON Schema で検証。AI の出力を構造化出力として制約できる
部分生成フラグを増やし続けるgenerate: セクションで範囲を宣言。フラグは上書き用
履歴無いgit 管理。仕様の変更 = 生成物の変更、が追える

CLI 引数は完全に捨てない。gen apply spec/order.yaml --layers domain のように「今回だけの範囲指定」は引数の方が自然。仕様は what、引数は今回の how。

AI にとっての意味

  • 出力先がスキーマ付き JSON/YAMLなので、幻覚の余地が狭い。不正なら検証エラーがそのまま再試行の材料になる
  • MCP ツールやスキルの引数としてスキーマをそのまま渡せる
  • 「仕様を書く」と「コードを書く」が分離され、AI の役割が明確になる

仕様に載せるもの／載せないもの

  • 載せる：名前、フィールド、型、VO/Entity/ID の区別、参照、ユースケース一覧、API 操作との対応、画面の種類、生成範囲
  • 載せない：業務ルールの実装、UI のレイアウト、コード片。仕様がコードになった瞬間に決定論が崩れる
検討 5

部分生成と再生成：手で直したものを壊さない「どこまで生成するか」を仕様と引数で選べること、「もう一度流しても安全」なことの両方が必要。

ファイルを 3 種類に分類する

種類命名再生成時の挙動例
常時再生成*.gen.ts毎回上書き。手編集禁止（ヘッダで明示、lint で警告）Mapper、DTO 型、DI／store／ルートのレジストリ
create-only通常のファイル名存在すればスキップ。--force で明示上書きEntity、VO、ユースケース、ページ、テスト
レジストリregistry.gen.ts全 spec を読んで丸ごと再生成。既存ファイルへの追記はしないDI 登録、reducer 一覧、ルート一覧

Rails と同じ「generate once」を create-only で再現し、Rails に無い「常に最新に保ちたいもの」を .gen.ts に逃がす。OpenAPI 生成クライアントや Prisma と同じ流儀なので、チームの学習コストが低い。

生成範囲の指定

# 仕様側：この集約で普段生成するもの
generate:
  layers: [domain, application, infrastructure, presentation]
  presentation: { screens: [list, detail, form] }
  tests: true

# 引数側：今回だけの範囲・モード
gen apply spec/order.yaml --layers domain,application
gen apply spec/order.yaml --only repository
gen apply spec/order.yaml --dry-run      # 差分だけ表示
gen apply spec/order.yaml --force Order.ts # 名指しで上書き
gen check                                # CI：.gen.ts が仕様と一致するか

やらないと決めること

  • マーカー区間の部分マージ（// BEGIN generated）はしない。区間のずれで壊れやすく、決定論を検証しづらい
  • 既存ファイルへの AST 追記はレジストリ方式で不要にする。ts-morph は最後の手段
検討 6

決定論性の担保と、AI・スクリプト・人の役割分担「決定論的」を検証可能な条件に落とす。役割は工程ごとに 1 つに固定する。

決定論チェックリスト（生成器の受け入れ条件）

  • 純関数：出力は spec と テンプレートのバージョンだけで決まる。日時・乱数・環境変数・ファイルシステムの列挙順に依存しない
  • 安定した順序：フィールド・import・レジストリ項目は spec の順、または名前順に固定
  • 整形の固定：生成後に Prettier を固定バージョン・固定設定で通す
  • 来歴ヘッダ：// @generated by gen v1.2.0 from spec/order.yaml (sha256:…)
  • ゴールデンテスト：手書きリファレンス集約 == 同じ spec からの生成物。ここが通らなければ規約かテンプレートが間違い
  • スナップショット：代表 spec 数本の生成物を固定。テンプレート変更の diff が見える
  • CI で gen check：.gen.ts の drift をブロック

工程ごとの担当

工程担当成果物検証
入力の読解AIspec 草案JSON Schema
仕様の確定人レビュー済み specPR レビュー
差分プレビュースクリプトdry-run の一覧人が承認
生成スクリプトファイル群tsc / lint / arch

AI は「読む」「判断する」「埋める」だけをやり、「配置する」「配線する」「整形する」には一切関与しない。この線引きが守られていれば、AI のモデルが変わっても生成物は変わらない。

Part 2

提案：4 つの案

A. 生成仕様駆動の自作ジェネレーター／B. TypeSpec を単一ソースにするカスタムエミッタ／C. ジェネレーター無し、規約とガードレールで AI 生成／D. 既存テンプレート CLI（Hygen・Plop・Nx）を AI から呼ぶ。検討メモの論点で比較する。

案 A

案 A：生成仕様駆動の自作ジェネレーターYAML/JSON の spec（JSON Schema 付き）→ TypeScript 製の生成器 → 4 レイヤー。入力側は「インポータ」で吸収する。

入力 ハブ 生成器 出力 TypeSpec ─┐ domain/ 設計メモ ─┼→ spec/order.yaml → gen apply ──┬─ templates/ ──→ application/ 画面モック─┘ (JSON Schema) │ ├─ writers/ infrastructure/ ↑ AI が草案 ↑ 人がレビュー │ └─ registry/ ──→ presentation/ └─ gen check (CI) *.gen.ts / registry.gen.ts

構成要素

  • spec スキーマ：集約・VO・ID・ユースケース・API 対応・画面・生成範囲
  • インポータ：TypeSpec → spec 草案（Phase 3）。逆向きの spec → TypeSpec 草案も
  • テンプレート：レイヤー × 成果物ごとの文字列テンプレート（EJS/Eta 程度）
  • レジストリ生成：全 spec を集めて DI／store／ルートを丸ごと出す
  • CLI：apply / check / import / export、--dry-run --layers --only --force

AI との接点

  • Claude Code スキル /gen：入力を読み spec を書く → dry-run を見せる → 承認後に apply → TODO を埋める
  • スキーマを構造化出力として渡す
  • Hook で tsc・lint・gen check を自動実行
  • 入力形式に依存しない。IDL-first でも Domain-first でも UI-first でも同じ生成器
  • 決定論を最も検証しやすい（純関数 + ゴールデン + スナップショット）
  • 部分生成・再生成をファイル分類で素直に扱える
  • 「AI が引数を考える」を spec ファイルとしてそのまま実現
  • テンプレートはプロジェクト固有の規約を 100% 反映できる
  • 自作。テンプレート・スキーマ・CLI の保守が発生する
  • TypeSpec と spec の二重管理になる（インポータで緩和するが、真実の源は 2 つ）
  • 初期コスト：規約の固定を含め 4〜6 週間程度

向いている状況

規約を自分たちで決められ、集約が今後も増え続け、IDL 以外から始まる案件が現実にある。今回の前提はほぼこれ。

案 B

案 B：TypeSpec を単一ソースにするドメイン意味をカスタムデコレータで TypeSpec に載せ、カスタムエミッタが 4 レイヤーを直接吐く。IDL が常に先なら最も筋がいい。

// ddd.tsp — カスタムデコレータで意味を付ける
import "@myorg/typespec-ddd";
using DDD;

@aggregate
model Order {
  @id id: OrderId;
  @ref(Customer) customerId: CustomerId;
  @entity lines: OrderLine[];
  @valueObject total: Money;
  status: "draft" | "placed" | "cancelled";
}

@useCase("command") op placeOrder(id: OrderId): Order;
@useCase("query")   op listOrders(): Order[];

// tspconfig.yaml
emit:
  - "@typespec/openapi3"
  - "@myorg/typespec-ddd-emitter"   # → 4 レイヤーを生成

TypeSpec はライブラリ（デコレータ）とエミッタ（$onEmit で Program を走査）を自作できる。API 契約とドメイン意味が 1 ファイルに同居し、バックエンド側の OpenAPI と必ず同期する。

  • 真実の源が 1 つ。API と生成物がずれない
  • TypeSpec のコンパイラが型解決・検証をやってくれる
  • IDL-first の案件では AI の仕事が「デコレータを付ける」だけになり、最小
  • IDL が先でない案件に弱い。Domain-first / UI-first では「先に TypeSpec を書く」を強いる
  • API 契約にドメイン意味（VO・不変条件）が混ざる。DTO と Entity の分離思想と衝突しやすい
  • エミッタ開発の学習コストが高い。TypeSpec のバージョン追従も要る
  • 画面の種類・生成範囲など「API と無関係な指示」を IDL に書く違和感
  • バックエンド側が TypeSpec を編集する場合、フロント固有のデコレータが混入する

採るべき部分

「TypeSpec から情報を取る」機構は案 A のインポータとして採用する。デコレータは Phase 3 の任意拡張（付いていればインポータが読む、無ければ AI が補う）に格下げする。

案 C

案 C：ジェネレーターを作らず、規約とガードレールで AI に書かせるリファレンス実装と規約文書を渡して AI が毎回 4 レイヤーを書く。決定論は lint・arch テスト・レビューで「事後に」担保する。

用意するもの

  • ゴールデン集約：手書きのリファレンス実装（Order）
  • CONVENTIONS.md：命名・配置・依存の向き・ID/VO の作法
  • スキル／プロンプト：「この集約を Order と同じ構造で作れ」
  • arch lint：eslint-plugin-boundaries / dependency-cruiser でレイヤー違反を検出
  • 構造テスト：「集約ごとに Repository interface と Test 実装がある」等をテストで強制

ワークフロー

  1. AI が入力を読み、ゴールデン集約を参照して全ファイルを書く
  2. lint・arch テスト・tsc で違反を検出し、AI に修正させる
  3. 人がレビュー

ツールを 1 行も書かずに今日から始められる。

決定論の実態

「同じ入力なら同じ出力」は保証されない。モデルやプロンプトの変化で骨格が揺れる。ガードレールが止められるのは「規約違反」までで、「微妙に違う書き方」は止められない。集約が 10 を超えると、集約ごとに癖のある骨格が積み上がる。

  • 初期コストがほぼゼロ。規約文書とリファレンスはどの案でも必要なので無駄にならない
  • 非 CRUD の複雑な集約にも柔軟
  • 生成器の保守が無い
  • Issue の「決定論的に進めたい」を満たさない
  • 配線（DI／store／ルート）を AI が既存ファイルを編集して行う。壊れやすい
  • 再生成という概念が無い。仕様変更時は差分を AI に説明し直す
  • トークン消費が毎回大きい（骨格を毎回書き直す）

採るべき部分

ゴールデン集約・規約文書・arch lint は案 A の Phase 0 そのもの。案 C は「案 A の Phase 0 だけを実施して止まった状態」と見なせるので、段階的移行の出発点として採用する。

案 D

案 D：既存のテンプレート CLI（Hygen / Plop / Nx generators）を AI から呼ぶ自作は最小限にし、枯れたスキャフォールディングツールに乗る。AI はプロンプトへの回答や CLI 引数を考える。

ツール特徴このケースでの評価
Hygen_templates/ に EJS + frontmatter。inject で既存ファイルへの行挿入も可。軽いフラットな引数向き。集約の入れ子構造を渡すには -- 引数が苦しい。inject は行マーカー依存
PlopNode の対話式ジェネレーター。Handlebars。plopfile.js で actions を組む対話式が AI と相性悪い（非対話モードはあるが引数はフラット）。actions は自作コードになる
Nx generatorsgenerateFiles・AST ユーティリティ・--dry-run・冪等性の思想が揃う強力だが Nx ワークスペース前提。Nx を使っていないなら導入コストが本体より大きい

共通する構造的な問題

  • どれも「テンプレート → ファイル」の部分は担うが、spec のスキーマ検証・レジストリの丸ごと再生成・TypeSpec インポート・gen check は結局自作になる
  • つまり案 D は「案 A のテンプレートエンジン部分を外部化した案」に過ぎない。外部化で減るのは全体の 2 割程度
  • 一方で引数の表現力が落ち、AI が渡す情報がフラットに制約される
  • テンプレート処理・dry-run・prompt などの周辺機能が最初から揃う
  • ドキュメントと事例が多く、AI も使い方を知っている
  • 数日で最初の 1 レイヤーが動く
  • 入れ子の生成仕様を渡しにくい（案 A の核心を失う）
  • 配線は行マーカー inject 頼み。決定論の検証がしづらい
  • 再生成ポリシー（.gen.ts / create-only）は自前で足す
  • ツール側の破壊的変更に追従する必要

採るべき部分

案 A のテンプレートエンジンとして Hygen のテンプレート形式（EJS + frontmatter の to:）を借りるのは合理的。ただし CLI 入口・スキーマ・レジストリは自作にし、Hygen はライブラリとして呼ぶか、同等の薄い実装（Eta + 自前ライタ）にする。

推奨

推奨：案 A を軸に、B のインポータと C のガードレールを吸収する単独の案ではなく、「A の Phase 0 = C」「A の Phase 3 = B の読み取り部分」として段階的に積む。

Phase 0 ＝ 案 Cゴールデン集約・規約文書・arch lint。ここまでで AI 生成は「規約付きで」始められる
Phase 1–2 ＝ 案 A の核spec スキーマ・生成器・レジストリ・gen check。ゴールデンと一致するまで作る
Phase 3 ＝ 案 B の読み取りTypeSpec インポータ／エクスポータ。デコレータは任意
Phase 4 ＝ AI 統合スキル /gen、構造化出力、Hook、3 起点のプロンプト

なぜ A が軸か

  • Issue の 4 要件を全て「◎」で満たす唯一の案
  • 決定論をテストで証明できる（ゴールデン・スナップショット・check）
  • 入力起点が変わっても生成器を作り直さなくてよい

何を捨てるか

  • TypeSpec を唯一の真実にすること（spec と二重管理を受け入れ、インポータと gen check で同期を保つ）
  • 非 CRUD の複雑な生成（Zone 3 は生成しない、と割り切る）
  • 既存ファイルへの AST 追記（レジストリ方式で回避）

途中で止まっても価値が残る順序

  • Phase 0 で止まる → 規約付き AI 生成（案 C）が手に入る
  • Phase 1 で止まる → Domain / Infra の骨格だけ決定論生成。ID と Repository が揃う
  • Phase 2 で止まる → 4 レイヤー生成。AI は手動でスキル無しに spec を書く
  • Phase 3 で止まる → IDL-first が高速化

判断の前提（変わったら再検討）

  • 集約が今後 10 以上増える見込み
  • IDL 以外から始まる案件が年に数回以上ある
  • チームが規約を自分たちで決められる

集約が数個で終わる小規模案件なら案 C で十分。この推奨は「生成器を作る価値がある規模」を前提にしている。

スキーマが強制すること

  • 全ての集約・Entity に ID 型がある（id 必須）。「ID を厳重に」を仕様レベルで保証
  • 他集約への参照は ref 付き ID 型のみ。オブジェクト埋め込みは書けない
  • invariants は文字列の宣言。生成器は TODO コメントと failing test の雛形にするだけで、実装しない
  • api.operations の値は TypeSpec の操作名。インポータが埋め、gen check が存在を検証

AI が判断した箇所（この例）

  • total と unitPrice を Money VO に寄せた
  • customerId を埋め込みではなく ID 参照にした
  • PlaceOrder / CancelOrder を Command に分けた
  • 画面は 3 種の標準画面で足りると判断した

→ これらが PR の diff として見える、というのが仕様ファイル方式の利点。

create-only の運用ルール

  • 生成後は普通のソースコード。ヘッダの「生成元」は残すが編集自由

  • フィールド追加のような変更は .gen.ts（Mapper / DTO）側が追随し、Entity は tsc エラーで気付ける設計にする

設計 4

レイヤー別テンプレートの中身どこまで書き、どこから TODO にするかの線を、実物で示す。

// domain/ordering/order/OrderId.ts（create-only）
declare const brand: unique symbol;
export type OrderId = string & { readonly [brand]: "OrderId" };
export const OrderId = {
  of(raw: string): OrderId { /* uuid 形式を検証 */ return raw as OrderId; },
  equals(a: OrderId, b: OrderId) { return a === b; },
};

// domain/ordering/order/Order.ts（create-only）
export class Order {
  private constructor(readonly id: OrderId, readonly customerId: CustomerId,
    readonly lines: readonly OrderLine[], readonly total: Money,
    readonly status: OrderStatus, readonly placedAt?: Date) {}
  static reconstruct(p: OrderProps): Order { return new Order(…); }
  place(): Order {
    // TODO(gen): invariant — draft からのみ遷移できる。lines は 1 件以上。
    throw new Error("not implemented");
  }
}

// domain/ordering/order/OrderRepository.ts（create-only）
export interface OrderRepository {
  findById(id: OrderId): Promise<Order | undefined>;
  findAll(): Promise<OrderSummary[]>;
  save(order: Order): Promise<void>;
}
// application/ordering/PlaceOrder.ts（create-only）
export class PlaceOrder {
  constructor(private readonly orders: OrderRepository) {}
  async execute(input: { orderId: OrderId }): Promise<void> {
    const order = await this.orders.findById(input.orderId);
    if (!order) throw new NotFoundError("Order", input.orderId);
    await this.orders.save(order.place());   // 骨格はここまで決定論で書ける
  }
}

// infrastructure/ordering/OrderMapper.gen.ts（常時再生成）
export const OrderMapper = {
  toDomain(dto: OrderDto): Order {
    return Order.reconstruct({
      id: OrderId.of(dto.id), customerId: CustomerId.of(dto.customerId),
      lines: dto.lines.map(OrderLineMapper.toDomain),
      total: Money.of(dto.total.amount, dto.total.currency), status: dto.status,
      placedAt: dto.placedAt ? new Date(dto.placedAt) : undefined,
    });
  },
  toDto(order: Order): OrderDto { /* 逆方向。同じ対応表から生成 */ },
};

// presentation/ordering/useOrders.ts（create-only）
export function useOrders() {
  const dispatch = useAppDispatch();
  const { items, status } = useAppSelector(s => s.ordering.order);
  return { items, status, load: () => dispatch(listOrders()),
           place: (id: OrderId) => dispatch(placeOrder({ orderId: id })) };
}

Mapper は「DTO のどのフィールドが Entity のどのフィールドに、どの VO のコンストラクタを通って入るか」が spec から一意に決まるため、常時再生成できる。Entity のメソッド本体は spec に載せない（載せた瞬間にコードになる）ので、TODO と失敗するテストだけを置く。

設計 5

配線：既存ファイルに追記せず、レジストリを丸ごと再生成するDI・Redux store・ルーターの 3 か所。生成器は全 spec を知っているので、追記ではなく全量生成ができる。

// src/registry/di.gen.ts — 全 spec から生成。手編集禁止
import { PORTS } from "@/application/ports.gen";
export function registerRepositories(c: Container, mode: "api" | "test") {
  c.bind(PORTS.OrderRepository).to(mode === "api" ? OrderApiRepository : OrderTestRepository);
  c.bind(PORTS.CustomerRepository).to(mode === "api" ? CustomerApiRepository : CustomerTestRepository);
  // … spec/ の集約ぶん。順序は context/aggregate 名の辞書順で固定
}

// src/registry/store.gen.ts
export const generatedReducers = {
  "ordering/order": orderReducer,
  "customer/customer": customerReducer,
};

// src/registry/routes.gen.ts
export const generatedRoutes: RouteObject[] = [
  { path: "/orders",     element: <OrderListPage /> },
  { path: "/orders/:id", element: <OrderDetailPage /> },
];

// 手書き側（一度だけ書く）：レジストリを取り込むだけ
const store = configureStore({ reducer: { ...generatedReducers, ...handWrittenReducers } });
const router = createBrowserRouter([...generatedRoutes, ...handWrittenRoutes]);

この方式の利点

  • 既存ファイルを一切編集しない。マーカーや AST 操作が不要
  • 集約を削除したら spec を消して gen apply。配線も消える
  • gen check でレジストリの drift を検出できる（追記方式では不可能）
  • 手書きの配線と生成の配線がファイル単位で分離する

制約

  • 手書き側に「レジストリを spread する 1 行」を最初に入れる必要がある（Phase 0 の作業）
  • 集約ごとに配線を細かくカスタムしたい場合は、手書き側で上書き（後勝ち）する
  • DI コンテナの選定に依存する部分は bind() の 1 行のみ。テンプレート側で吸収

Api / Test の切替

「テスト用バックエンドを使っている」前提に合わせ、mode は 3 値にできる：api（本番 API）/ testBackend（テスト用バックエンドへ本物の ApiRepository で接続）/ memory（インメモリ）。生成器は 3 つとも同じ spec から出す。

設計 6

TypeSpec との接続：インポータとエクスポータTypeSpec は「API の形」の真実の源、spec は「ドメイン意味と生成指示」の真実の源。両者の対応を機械で検証する。

インポータ：tsp → spec 草案（IDL-first）

  1. tsp compile で @typespec/openapi3 を出す（自作エミッタを書かない最短経路）
  2. OpenAPI の components.schemas → aggregate.fields の型・optional・enum
  3. paths の operationId → api.operations と useCases の候補
  4. 出力は草案。VO 化・集約境界・ref は # TODO(ai) 付きで空欄

Phase 3b（任意）：@typespec/compiler の Program を直接歩き、カスタムデコレータ（@ddd.valueObject 等）があれば草案に反映する。無くても動く。

エクスポータ：spec → tsp 草案（Domain-first / UI-first）

  1. spec の集約・Entity・VO を model に平坦化（VO は構造体または scalar に）
  2. useCases を op の候補に。Command は POST、Query は GET
  3. 出力は api/ordering.draft.tsp。バックエンドと合意して正式版にしたら spec の api.file を差し替える

逆方向があることで「IDL が先でない」案件でも、最終的に IDL-first と同じ状態に収束する。

API クライアント

OpenAPI から openapi-typescript + openapi-fetch（または TypeSpec の JS クライアントエミッタ）で型付きクライアントを生成し、OrderApiRepository はそれを呼ぶ。生成器はクライアントを作らず、呼び方だけをテンプレートで固定する。

DTO ≠ Entity を守る

  • DTO 型は OrderDto.gen.ts（TypeSpec 由来）、Entity は Order.ts（spec 由来）。同じ名前を付けない
  • 変換は必ず OrderMapper.gen.ts を通す。Presentation が DTO を触ったら arch lint で落とす
  • API に無いフィールド（導出値・UI 状態）は Entity や slice に、spec で api: false と宣言

gen check が見るもの

  • api.operations で参照した操作が tsp に存在する
  • DTO のフィールド集合と Mapper の対応表が一致する
  • tsp 側で追加されたフィールドが spec に無ければ警告（エラーではない。UI に不要な項目もある）

TypeSpec のエミッタ自作は Phase 3b に隔離し、openapi3 経由で先に動かす。エミッタ API の変更に追従するコストを本体から切り離すため。

設計 9

CLI 仕様：genサブコマンドは 5 つ。全て非対話。終了コードで CI と AI が結果を判定できる。

gen apply <spec.yaml> [options]      # 生成。spec を検証してから書く
  --layers domain,application,…        # 今回出すレイヤー（spec の generate.layers を上書き）
  --only repository|usecase|slice|…    # 成果物の種類で絞る
  --skip tests                         # 除外
  --dry-run                            # 作成 / スキップ / 上書き の一覧と差分を表示。書かない
  --force <file>…                      # create-only を名指しで上書き
  --json                               # 機械可読な結果（AI・CI 向け）

gen check [--fix]                      # 全 spec を再生成し .gen.ts / registry と比較。差があれば exit 1
gen import tsp <file.tsp> --out spec/… # TypeSpec → spec 草案（TODO(ai) 付き）
gen export tsp <spec.yaml> --out api/… # spec → TypeSpec 草案
gen list                               # spec 一覧と生成状態（未生成 / 最新 / drift）

# 終了コード
0 成功 / 1 drift または検証エラー / 2 spec スキーマ違反（メッセージに JSON Pointer） / 3 テンプレートエラー

# dry-run の出力例
$ gen apply spec/ordering/order.yaml --dry-run --layers domain
  create  src/domain/ordering/order/OrderId.ts
  create  src/domain/ordering/order/Order.ts
  skip    src/domain/ordering/order/Money.ts        (exists; use --force)
  update  src/registry/di.gen.ts                    (+2 lines)
  3 create, 1 skip, 1 update

設計上の決め事

  • 非対話：質問を返さない。足りない情報はスキーマ違反として exit 2。AI が spec を直して再実行する
  • 冪等：2 回続けて apply しても 2 回目は全部 skip / 変更なし
  • 順序の固定：出力ファイル一覧はパスの辞書順
  • spec の正規化：派生名（OrderRepository、useOrders、orderSlice）は CLI が決め、spec には書かせない
  • Prettier は生成器の中：外部の整形に依存しない

AI から見た CLI

--json の結果に「作成されたファイル」「TODO(gen) の位置」「次にやること」を含める。スキルはこれを読んで TODO 埋めに進む。エラーは JSON Pointer 付きなので、spec のどこを直すかが機械的に分かる。

まとめ

まとめ「決定論的に進めたい。スクリプトを作り、渡す引数を AI が考える」を、そのまま構造にした。

  • ジェネレーターの前に規約：Rails が生成できるのは規約が強いから。手書きゴールデン集約と CONVENTIONS.md を Phase 0 で作る
  • 3 ゾーンで線を引く：配置・配線・骨格はスクリプト（Zone 1）、集約境界・VO・ユースケースの判断は AI が spec に書く（Zone 2）、業務ルールと UI は生成後に AI か人が書く（Zone 3）
  • AI の引数 = スキーマ付き生成仕様ファイル：レビューでき、再実行でき、構造化出力で制約できる
  • 入力の起点は 3 通り、ハブは 1 つ：IDL-first はインポータ、Domain-first / UI-first はエクスポータで TypeSpec に合流
  • 再生成は 3 種のファイル分類で：create-only / .gen.ts / レジストリの丸ごと再生成。既存ファイルへの追記はしない
  • 決定論はテストで証明：ゴールデン一致、スナップショット、CI の gen check
  • 推奨は案 A を軸に B・C を吸収：Phase 0 = 案 C、Phase 3 = 案 B の読み取り部分。途中で止まっても価値が残る順序
