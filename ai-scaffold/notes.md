# 検討メモ — 自動実装 × AI（Issue #16）

スライド `index.html` の「検討」章の元になったメモ。スライドに載せなかった途中経過・却下した選択肢・未解決の論点も残す。

## 0. 問いの分解

Issue #16 の要望は 4 つ。それぞれ別の設計判断を要求している。

| 要望 | 翻訳した設計要件 | 決めるべきこと |
|---|---|---|
| Rails generate のようにモデル情報から UI・モデル・コントローラー・リポジトリを生成 | 1 入力 → 4 レイヤーの一括生成 | 命名・配置規約、レイヤーごとのテンプレート |
| 最初に決まるのは IDL（TypeSpec）が多いが、そうでない場合もある | 入力形式に依存しない中間表現 | 中間表現の形、インポータ／エクスポータ |
| 自動生成をどこまで行うかはその都度異なる | レイヤー・成果物単位の部分生成、手編集を壊さない再生成 | ファイルの分類（create-only / 常時再生成） |
| 決定論的に進めたい。スクリプトを作り、渡す引数を AI が考える | 生成器は純関数、AI は入力を作る | 引数の形（CLI 引数かファイルか）、検証の方法 |

「Rails の generate」は比喩として強いが、成立している理由を分解しないと再現できない。

## 1. Rails generate が成立している理由

Rails の生成器が賢いわけではない。以下の規約が先にあり、生成器はそれを機械的に適用しているだけ。

- **命名規約**：`Order` から `orders`（テーブル）、`OrdersController`、`app/views/orders/` が一意に決まる。生成器は「名前を決める」仕事をしない。
- **配置規約**：レイヤーごとの固定ディレクトリ。「どこに置くか」を考えない。
- **モデル定義の唯一の入力**：`name:string price:integer` の DSL。曖昧さがない。
- **generate once**：生成後のファイルはユーザーのもの。再生成で上書きしない（`--skip` / `--force` は明示的な指示）。
- **スキーマ差分は migration**：ファイルの再生成ではなく、追加の migration で表現する。
- **配線の規約**：`routes.rb` に 1 行足すだけ。DI コンテナは無い。

このプロジェクト（DDD + レイヤード + DIP + React/Redux）に足りないもの：

1. **命名・配置規約の明文化**。集約 `Order` のユースケースの置き場と名前が機械可読になっていない。
2. **モデル定義の唯一の入力形式**。TypeSpec は API の形は表せるが、「どれが VO か」「集約境界はどこか」「不変条件は何か」は表せない。
3. **配線の規約**。DI コンテナ登録・Redux reducer 登録・ルート登録の 3 か所に「何をどう足すか」の規約がない。

結論：**ジェネレーターの前に規約**。Phase 0 はコードを生成せず、手書きのリファレンス実装（ゴールデン集約）と規約文書を作る。

## 2. 3 つのゾーン

「どこまで自動化するか」の議論は、次の 3 つに切ると収束する。

### Zone 1 — 決定論（スクリプトが書く）

- ファイルパス・ファイル名・命名の変換（PascalCase / camelCase / kebab-case）
- import 文、barrel export、来歴ヘッダ
- ID 型（branded type）と ID を持つ VO の骨格
- Repository インターフェース、インメモリ／テストバックエンド実装
- DTO ⇄ Entity Mapper の骨格（フィールド対応表は spec から一意）
- Redux slice / Hook / CRUD ページの骨格
- DI・store・ルートの配線
- テストファイルの雛形（`it.todo()`）

原則：**ここは AI に書かせない**。同じ仕様から毎回同じバイト列が出ることをテストで保証する。

### Zone 2 — 判断（AI が「引数」を決める）

- 集約の境界
- どのフィールドを VO にし、どれをプリミティブのままにするか
- 他集約への参照（ID 参照）の同定
- ユースケースの列挙と Command / Query の分類
- 画面の種類（一覧・詳細・フォーム・カスタム）
- 今回の生成範囲
- 入力が曖昧なときの命名

原則：**判断の結果は必ず仕様ファイルに落とし、人がレビューできる形にする**。

### Zone 3 — 創作（生成後に AI／人が書く）

- Entity の不変条件・業務ルール（`place()` の中身）
- VO のバリデーション
- CRUD で表せない画面・複雑な UI 状態
- エラーハンドリング方針、認可
- 非 CRUD ユースケースの本体

原則：**生成器は `// TODO(gen):` マーカーだけ置き、中身を書かない**。ここを生成器で頑張るとテンプレートが肥大し、決定論が崩れる。

### 「その都度異なる」の分解

「自動生成をどこまで行うかはその都度異なる」は 2 つに分かれる。

- Zone 1 の中で**どの成果物を出すか**を選ぶ問題 → 生成器の機能（部分生成）
- Zone 3 を **AI に任せるか人が書くか** → ワークフロー（スキル）の問題

前者は `generate:` セクションと CLI 引数、後者はスキルの手順で扱う。生成器に「Zone 3 をどこまで書くか」のつまみを付けない。

## 3. 入力の起点

| 起点 | 決まっているもの | AI が補うもの | 流れ |
|---|---|---|---|
| A. IDL-first | モデルの形（フィールド・型）、操作 | VO 化する項目、集約境界、ID 参照、ユースケース名 | tsp → インポータで spec 草案 → AI が意味を付加 → 生成 |
| B. Domain-first | 集約・Entity・VO・不変条件 | 仕様ファイルへの構造化、API 操作の提案 | AI が spec → Domain + Application 生成 → spec から tsp 草案をエクスポート → API 確定後に Infra |
| C. UI-first | 画面・ユーザーストーリー・表示項目 | ビューモデル → ユースケース → 集約の逆算 | AI が spec → Presentation + Application 生成、Domain / Infra はスタブ |

3 起点とも**生成仕様（spec）に合流**させる。生成器は 1 つで済み、起点ごとに違うのはインポータ／エクスポータとスキルの手順だけ。

## 4. 「引数」の形：CLI 引数か、ファイルか

Issue は「スクリプトに渡す引数を AI が考える」と言っている。引数の形の選択肢：

| | CLI 引数 | 仕様ファイル（YAML/JSON + JSON Schema） |
|---|---|---|
| 表現力 | フラット。集約・VO・ユースケースの入れ子を書けない | 入れ子・配列・参照を書ける |
| レビュー | シェル履歴に残るだけ | PR の diff で AI の判断が見える |
| 再実行 | コマンドを打ち直す | `gen apply` で同じ結果。CI でも実行 |
| 検証 | 引数パーサ頼み | JSON Schema。AI の構造化出力の制約にそのまま使える |
| 部分生成 | フラグを増やし続ける | `generate:` で宣言、フラグは上書き |
| 履歴 | 無い | git 管理 |

結論：**仕様は what（ファイル）、引数は今回の how（`--layers` など）**。

仕様に載せるもの：名前、フィールド、型、VO/Entity/ID の区別、参照、ユースケース一覧、API 操作との対応、画面の種類、生成範囲、不変条件の**宣言**（文字列）。
仕様に載せないもの：業務ルールの実装、UI のレイアウト、コード片。仕様がコードになった瞬間に決定論が崩れる。

## 5. 部分生成と再生成

### ファイルの 3 分類

| 種類 | 命名 | 再生成時 | 例 |
|---|---|---|---|
| 常時再生成 | `*.gen.ts` | 毎回上書き。手編集禁止 | Mapper、DTO 型、DI / store / ルートのレジストリ |
| create-only | 通常 | 存在すればスキップ。`--force` で名指し上書き | Entity、VO、ユースケース、ページ、テスト |
| レジストリ | `registry/*.gen.ts` | 全 spec から丸ごと再生成 | DI 登録、reducer 一覧、ルート一覧 |

OpenAPI 生成クライアントや Prisma と同じ流儀。学習コストが低い。

### 却下した選択肢

- **マーカー区間の部分マージ**（`// BEGIN generated` … `// END generated`）：区間のずれで壊れやすく、決定論の検証がしづらい。手編集と生成が同じファイルに同居するのも避けたい。
- **既存ファイルへの AST 追記**（ts-morph で `container.bind(...)` を挿入）：冪等にするのが難しく、既存ファイルの書き方に依存する。レジストリ方式で不要になる。
- **フィールド変更の Entity 追随**：spec でフィールドを足したとき Entity（create-only）を書き換える案。却下。Mapper（`.gen.ts`）が追随して tsc エラーになるので、そこで人か AI が Entity を直せばよい。Rails の「migration は追加、モデルは手で直す」と同じ。

## 6. 決定論の担保

「決定論的」を検証可能な条件に落とす。

- **純関数**：出力は spec とテンプレートのバージョンだけで決まる。日時・乱数・環境変数・ファイル列挙順に依存しない
- **安定した順序**：フィールド・import・レジストリ項目は spec の順または名前順
- **整形の固定**：Prettier を固定バージョン・固定設定で生成器の中から呼ぶ
- **来歴ヘッダ**：`// @generated by gen <version> from <spec path> (sha256:…)`
- **ゴールデンテスト**：手書きリファレンス集約 == 同じ spec からの生成物
- **スナップショットテスト**：代表 spec 数本の生成物を固定
- **CI で `gen check`**：`.gen.ts` の drift をブロック

## 7. 役割分担

| 工程 | 担当 | 成果物 | 検証 |
|---|---|---|---|
| 入力の読解 | AI | spec 草案 | JSON Schema |
| 仕様の確定 | 人 | レビュー済み spec | PR レビュー |
| 差分プレビュー | スクリプト | dry-run の一覧 | 人が承認 |
| 生成 | スクリプト | ファイル群 | tsc / lint / arch |
| TODO の実装 | AI or 人 | 業務ルール・UI | テスト・レビュー |
| 回帰確認 | スクリプト | CI 結果 | `gen check`・test |

AI は「読む」「判断する」「埋める」だけ。「配置する」「配線する」「整形する」には関与しない。この線引きが守られていれば、モデルが変わっても生成物は変わらない。

## 8. 案の検討過程

### 案 A：生成仕様駆動の自作ジェネレーター

spec（JSON Schema 付き YAML）→ TypeScript 製生成器 → 4 レイヤー。入力側はインポータで吸収。

- 長所：入力に依存しない、決定論を検証しやすい、部分生成・再生成が素直、「AI が引数を考える」をそのまま実現
- 短所：自作の保守、TypeSpec と spec の二重管理、初期コスト 4〜6 週

### 案 B：TypeSpec を単一ソースに

カスタムデコレータ（`@aggregate` `@valueObject` `@id` `@ref` `@useCase`）で意味を載せ、カスタムエミッタで 4 レイヤーを直接生成。

- 長所：真実の源が 1 つ、コンパイラの型解決・検証が使える、IDL-first では AI の仕事が最小
- 短所：**IDL が先でない案件に弱い**、API 契約にドメイン意味が混ざる（DTO ≠ Entity と衝突）、エミッタ開発と TypeSpec の追従コスト、画面や生成範囲を IDL に書く違和感、バックエンド側がフロント固有デコレータを扱う負担
- 採る部分：「TypeSpec から情報を取る」機構をインポータとして。デコレータは Phase 3b の任意拡張。

### 案 C：規約 + ガードレールで AI 生成

ゴールデン集約と CONVENTIONS.md を渡し、AI が毎回 4 レイヤーを書く。arch lint・構造テスト・レビューで事後に守る。

- 長所：初期コストほぼゼロ、非 CRUD に柔軟、生成器の保守なし
- 短所：**決定論を満たさない**、配線を AI が既存ファイルを編集して行う、再生成の概念がない、トークン消費が大きい
- 採る部分：ゴールデン集約・規約文書・arch lint は案 A の Phase 0 そのもの。

### 案 D：既存テンプレート CLI（Hygen / Plop / Nx）

- Hygen：EJS + frontmatter、`inject` で行挿入。引数がフラット。
- Plop：対話式。非対話モードはあるが引数フラット。actions は自作コードになる。
- Nx generators：`generateFiles`・AST ユーティリティ・dry-run が揃うが Nx ワークスペース前提。
- 共通の問題：spec のスキーマ検証・レジストリ再生成・TypeSpec インポート・`gen check` は結局自作。外部化で減るのは全体の 2 割程度で、引数の表現力を失う。
- 採る部分：テンプレート形式（EJS + frontmatter の `to:`）。CLI 入口・スキーマ・レジストリは自作。

|---|:-:|:-:|:-:|:-:|
| 決定論性 | ◎ | ◎ | × | ○ |
| 入力の柔軟性 | ◎ | × | ◎ | ○ |
| 部分生成・再生成 | ◎ | ○ | × | △ |
| 「AI が引数を考える」との適合 | ◎ | ○ | △ | △ |
| 配線 | ◎ | ◎ | × | △ |

### 推奨

**案 A を軸に、B のインポータと C のガードレールを吸収する**。Phase 0 = 案 C、Phase 1–2 = 案 A の核、Phase 3 = 案 B の読み取り部分、Phase 4 = AI 統合。

途中で止まっても価値が残る順序：

- Phase 0 で止まる → 規約付き AI 生成（案 C）
- Phase 1 で止まる → Domain / Infra の骨格だけ決定論生成
- Phase 2 で止まる → 4 レイヤー生成。AI はスキル無しに spec を手で書く
- Phase 3 で止まる → IDL-first が高速化

判断の前提（変わったら再検討）：集約が今後 10 以上増える、IDL 以外から始まる案件が年に数回以上ある、チームが規約を自分たちで決められる。集約が数個で終わる小規模案件なら案 C で十分。

## 9. 設計上の個別論点

### 配線はレジストリの丸ごと再生成

生成器は全 spec を知っているので、DI・store・ルートを追記ではなく全量生成できる。既存ファイルを一切編集せず、`gen check` で drift を検出でき、集約の削除も spec を消すだけで済む。手書き側には「レジストリを spread する 1 行」を Phase 0 で入れる。

### DTO ≠ Entity

DTO 型は `OrderDto.gen.ts`（TypeSpec 由来）、Entity は `Order.ts`（spec 由来）。同じ名前を付けない。変換は必ず `OrderMapper.gen.ts` を通す。Presentation が DTO を触ったら arch lint で落とす。API に無いフィールドは spec で `api: false` と宣言する。

### TypeSpec インポータは openapi3 経由で先に作る

エミッタ自作は Phase 3b に隔離する。`tsp compile` で `@typespec/openapi3` を出し、OpenAPI を読む方が短く、TypeSpec のエミッタ API の変更に本体が引きずられない。カスタムデコレータを読むには `@typespec/compiler` の `Program` を歩く必要があるが、それは任意拡張にする。

### API クライアントは生成器の外

OpenAPI から `openapi-typescript` + `openapi-fetch`（または TypeSpec の JS クライアントエミッタ）で型付きクライアントを作る。生成器はクライアントを作らず、`OrderApiRepository` からの**呼び方**だけをテンプレートで固定する。

### テスト用バックエンド

Repository の実装は 3 モード：`api`（本番 API）/ `testBackend`（テスト用バックエンドへ本物の ApiRepository で接続）/ `memory`（インメモリ）。テスト用バックエンドのハンドラとフィクスチャ（決定論的な固定 ID）は `handlers.gen.ts` として spec から生成する。出力形式（MSW / json-server / 独自）はテンプレートの切替で吸収し、フィクスチャの内容は共通。

ApiRepository ⇄ テスト用バックエンドの結合テストは契約テストの役割を持つ。TypeSpec が変わって DTO が再生成されたとき、最初に落ちるのがここ。

### AI ワークフローの禁止事項は Hook で止める

「spec 以外を直接書かない」「`.gen.ts` を編集しない」「dry-run の承認を待つ」をプロンプトで頼むのではなく、PreToolUse Hook で `.gen.ts` への書き込みを拒否し、Stop Hook で `gen check` を走らせる。

## 10. 未解決の論点（Phase 0 で決める）

- DI コンテナの選定（既存のものに合わせる。テンプレート側で `bind()` の 1 行を吸収）
- Redux の書き方（RTK の `createSlice` + `createAsyncThunk` を前提にしているが、RTK Query を使っているなら slice テンプレートの形が変わる）
- テスト用バックエンドの実体（MSW か、別プロセスのサーバーか）
- 集約をまたぐ Query（一覧画面で複数集約を結合する場合）を Application 層でどう表すか。spec の `useCases[].output` に読み取りモデルを別途宣言する案が有力
- VO の表現（class か branded primitive + 関数か）。ゴールデン集約で決める
- 生成仕様のファイル配置（`spec/<context>/<aggregate>.yaml` を仮置き）
- 工数の目安は 1 名専任の場合。並行作業なら Phase 1 と Phase 0 の T-04〜T-07 は重ねられる
