Background 背景と変遷

TSServer から Go ネイティブへの大転換

TypeScript エディタ統合の 12 年史

  • 2014〜 (TS 1.x〜5.x): tsserver.js が登場。独自プロトコルで VS Code と通信。Node.js 実行環境が必須で、メモリ消費が課題。
  • 2018〜 (TS 3.x〜6.x): コミュニティ主導で typescript-language-server や vtsls が誕生。TSServer を LSP 形式に変換するラッパーとして普及。
  • 2025〜2026 (Native Preview): Microsoft が Go 言語への移植プロジェクト（typescript-go / tsgo）を公表。
  • 2026-07 (TS 7.0 GA): Go 版が正式版となり、tsc 自体にネイティブ LSP サーバー機能が統合！
💡 名称の整理: 2025 年の開発プレビュー時は @typescript/native-preview や tsgo と呼ばれていましたが、TS 7.0 正式版では公式 typescript パッケージの tsc コマンド自身 になっています。

なぜ Go 移植だったのか？

  • 超高速なコールドスタート: JIT コンパイル待ちや V8 起動のオーバーヘッドを完全排除。CLI ツールとしての応答性を追求。
  • 劇的なメモリ効率化: V8 オブジェクトヘッダーの肥大化から解放され、構造体のコンパクト配置と効率的な Go ランタイム GC を獲得。
  • マルチスレッド対応: 型チェック・パースの並列処理を言語コアでネイティブ実装。

TSServer プロトコルの終焉

長年使われてきた TSServer 独自プロトコルは内部実装となり、外部インターフェースとしては 業界標準の LSP (Language Server Protocol) が第一級市民になりました。

発表者ノート

過去の記事にある「tsgo をビルドする」という情報は古く、現在は `npm install typescript@7` だけで OS 固有のネイティブバイナリが配布されます。

Architecture アーキテクチャ比較

従来の二重ラッパー構成 vs 単一 Go バイナリ

従来 (TS 6 以前): 2 段プロセスとプロトコル変換

┌───────────────────────────────────────────────┐ │ Editor / AI Agent (Claude Code, Zed, etc.) │ └───────────────────────┬───────────────────────┘ │ JSON-RPC (LSP 3.17) ┌───────────────────────▼───────────────────────┐ │ typescript-language-server (Node.js) │ │ * プロトコル相互変換 (LSP ↔ TSServer) │ └───────────────────────┬───────────────────────┘ │ TSServer Custom JSON ┌───────────────────────▼───────────────────────┐ │ tsserver.js (Node.js / V8 Engine) │ │ * メモリ 200〜450MB+ / 起動 400ms+ │ └───────────────────────────────────────────────┘

Node プロセスが 2 重起動。中間シリアライズとプロセス間通信のオーバーヘッドが存在。

現在 (TS 7.0+): 単一バイナリ直接通信

┌───────────────────────────────────────────────┐ │ Editor / AI Agent (Claude Code, Orca, etc.) │ └───────────────────────┬───────────────────────┘ │ JSON-RPC (LSP 3.17) via stdio │ Direct Native Stream ┌───────────────────────▼───────────────────────┐ │ tsc --lsp --stdio (Go Native Binary) │ │ * ネイティブ LSP サーバー実装 (internal/lsp) │ │ * コアコンパイラ・型チェッカーを直接駆動 │ │ * メモリ 18〜35MB / 起動 28ms │ └───────────────────────────────────────────────┘

Node.js の介在ゼロ。中間変換層がなく、メモリ・レイテンシともに桁違いの効率。

発表者ノート

エディタや AI エージェントから見ると、余計な中間ラッパーを挟むことなく、直接 Go の超高速バイナリと標準 LSP で対話できるのが最大の変革です。

Protocol 起動と通信仕様

起動コマンドと JSON-RPC 2.0 ライフサイクル

起動フラグと要件

# プロジェクト直下の tsc を起動 $ ./node_modules/.bin/tsc --lsp --stdio # --stdio を省略するとエラー終了 (code: 1) only stdio is supported
  • 必須引数: --lsp と --stdio の双方が必要。
  • 標準入出力: stdin からリクエストを受信し、stdout にレスポンス/通知を返却。stderr は内部ログ用。
  • メッセージ形式: Content-Length ヘッダー付き JSON-RPC 2.0。
⚠️ 位置情報の仕様: 照会位置の line / character は 0 始まり（0-based）。ヘッダーの Content-Length は UTF-8 バイト長ですが、位置エンコーディングは utf-16 です。
JSON-RPC Lifecycle Trace 
Client ➔ Server (Request: initialize)
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}

Server ➔ Client (Response: capabilities)
{"jsonrpc":"2.0","id":1,"result":{"serverInfo":{"name":"typescript-go",...}}}

Client ➔ Server (Notification: initialized) ← 必須！
{"jsonrpc":"2.0","method":"initialized","params":{}}

Client ➔ Server (Notification: didOpen)
{"jsonrpc":"2.0","method":"textDocument/didOpen",...}

Client ➔ Server (Request: textDocument/diagnostic)
{"jsonrpc":"2.0","id":2,"method":"textDocument/diagnostic",...}

Client ➔ Server (Request: shutdown) ← params は省略！
{"jsonrpc":"2.0","id":3,"method":"shutdown"}

Client ➔ Server (Notification: exit)
{"jsonrpc":"2.0","method":"exit"}

発表者ノート

initialize の後に必ず initialized 通知を送る必要があります。これを怠ると、後続のリクエストすべてが ServerNotInitialized エラーとなります。

Gotchas 実装上の落とし穴

クライアント実装者がハマる 3 つの厳格性

1. shutdown の引数厳格性

現象: shutdown に params: null を渡すとサーバーが拒絶。

{"code":-32602, "message":"InvalidParams"} # 正解は params 自体を省略: {"id":2,"method":"shutdown"}

Node や Python の汎用 JSON-RPC クライアントで params: null をデフォルト送出する設定になっていると即座に失敗します。

2. サーバー要求のハンドリング

現象: 初期化直後に通信がハングアップする。

初期化完了後、サーバー主導で workspace/configuration リクエスト（設定問い合わせ）がクライアントに飛んできます。

クライアント側で 「サーバーからのリクエスト」と「クライアントリクエストへの返信」を峻別 し、即座に空配列（null）を返信しないとデッドロックします。

3. URI パスデコード漏れ

現象: 空白を含むパスで push 診断が迷子になる。

LSP の file:///path/my%20file.ts はパーセントエンコードされています。単純な文字列操作ではなく、Node の fileURLToPath() や Python の url2pathname() で正規ファイルパスに変換する必要があります。

✅ 同梱の検証スクリプト: examples/lsp-probe.mjs および examples/probe_lsp.py は、上記 3 つの落とし穴をすべてクリアした堅牢なリファレンス実装になっています。

発表者ノート

先行調査で報告されていた「LSP クライアントがハングする」「InvalidParams が返る」という問題は、すべてこの仕様に起因していました。同梱の probe では完全に解消しています。

TS 6 (Node.js + TSServer) 239 MB

なぜここまで省メモリなのか？

V8 は動的型付け言語実行エンジンのため各オブジェクトに隠れクラスやポインタ等の大きなオーバーヘッドがあります。Go ネイティブ版はコンパイル時にメモリレイアウトが静的決定され、不要なガベージを最小限に抑えます。

発表者ノート

CI やコンテナ環境、複数エージェントを並列実行する環境において、メモリ消費が 1/10 以下になるメリットは絶大です。

Deep Dive 機能深掘り (1)

Pull 診断と workspaceDiagnostics: false の真意

検証対象コード (`diagnostics-demo.ts`)

1: import { processCheckout } from "./checkout";
2: 
3: const totalAmount: number = processCheckout();
4: const invalidAssignment: string = totalAmount; // TS2322
5: const unusedVariable: number = 42;             // TS6133

実測 Pull 診断レスポンス (`diagnostic`)

0 始まりの行番号（L4 ➔ line: 3）と正確に合致：

[TS2322] L4:7-L4:24
  "Type 'number' is not assignable to type 'string'."
[TS6133] L4:7-L4:24
  "'invalidAssignment' is declared but its value is never read."
[TS6133] L5:7-L5:21
  "'unusedVariable' is declared but its value is never read."

workspaceDiagnostics: false とは？

  • 仕様: textDocument/diagnostic は 開いているファイル（didOpen されたファイル） のみ診断を返します。
  • 理由: 数万ファイル規模の巨大リポジトリでクライアントが一括 Pull 診断を要求した際のメモリ・CPU 枯渇を防ぐため。
  • 他ファイルへの波及: interFileDependencies: true のため、開いているファイルが依存する別ファイルの型が壊れた場合は正確にエラーを検知します。
💡 役割分担:
・`tsc --lsp`: エージェントが現在編集しているファイルの超高速診断（1〜20ms）
・`tsc --noEmit`: タスク完了前のリポジトリ全体の最終合格判定（全体検査）

発表者ノート

コード行数（5行）と診断結果（4行目と5行目のエラー）が1行たりともズレることなく完全に再現されることを確認しました。

Deep Dive 機能深掘り (3)

呼び出し階層 (Call Hierarchy) とセマンティックリネーム

呼び出し階層 (`callHierarchy`)

関数の「呼び出し元」や「呼び出し先」のコールツリーを再帰的に追跡：

prepareCallHierarchy (シンボル登録: 0.09 ms)
  └─ calculateTotal (src/pricing.ts:L8)

callHierarchy/incomingCalls (呼び出し元一覧: 0.26 ms)
  └─ processCheckout (src/checkout.ts:L8)
       └─ (module scope) (src/diagnostics-demo.ts:L3)

「この関数を変更したらどこに影響が出るか？」を AI がミリ秒で全自動トレース可能。

安全なリネーム (`rename` + `prepareRename`)

  • 事前検証 (`prepareRename`): 対象シンボルが安全にリネーム可能か（予約語や外部ライブラリではないか）を事前判定。
  • 一括 WorkspaceEdit:
    • 関数宣言の名前変更
    • 全参照ファイルの import { old as new } または直接書き換え
    • 型注釈の更新
  • ファイル移動連動 (`willRenameFiles`): ファイルを移動・改名した際に、プロジェクト全体の相対 import パスを自動更新。
🛡️ 破壊的変更の防止: AI に直接正規表現置換をさせず、LSP の rename が生成する WorkspaceEdit を適用することでリファクタリング事故を防ぎます。

発表者ノート

Call Hierarchy はリファクタリング Bot や影響範囲分析 Bot にとって最強の武器です。静的なコード関係を正確に把握できます。

AI Agents プログラム構造の理解

なぜ AI に LSP が不可欠か？ プログラム構造理解と品質向上

grep / 全文検索の限界

  • 同名シンボルの混同: user.id や format() を区別できず、無関係なファイルを大量に LLM に渡してトークン浪費。
  • 型情報がゼロ: 関数の引数の型や戻り値の型を推測（ハルシネーション）に頼るしかない。
  • リネーム漏れ: import エイリアスや再エクスポートを追跡できない。

tsc --noEmit の限界

  • 全体スキャンによる遅延: 1 ファイルを微修正しただけでも全プロジェクトを再検査するため 数秒〜十数秒 かかる。
  • 非対話的: 型や参照関係を能動的に質問（クエリ）する機能がない。
  • 出力のパース負荷: 膨大なエラーログから対象箇所の切り分けが必要。

tsc --lsp の解決策

  • セマンティック構造の把握: 型チェッカーが解決した AST・シンボルツリー・参照グラフをそのまま活用。
  • ピンポイント Pull 診断: 編集したファイルだけを 1〜20ms で即座検査し品質向上。
  • トークン消費の極小化: 必要な定義・シグネチャだけをピンポイント抽出しコンテキスト節約。

発表者ノート

AI エージェントにとって「間違った推論をさせないための構造把握（Grounding）」と「高速な試行錯誤ループ」の2点が開発体験を左右します。

Workflow 高速エージェントループ

「編集 ➔ 1ms 即座診断 ➔ 自己修正」の極小ループ

エージェントの対話ループ革命

  1. 指示受付: ユーザー「totalAmount の代入エラーを直して」
  2. 型確認 (0.7 ms): hover で右辺の型が number であることを確認。
  3. コード編集: エージェントがメモリ上でファイルを書き換え。
  4. 即座診断 (19 ms): textDocument/diagnostic を叩く。
  5. 判定 (0 ms): エラー 0 件を確認 ➔ 即座に完了報告！
⏱️ 所要時間の劇的短縮: 従来の「`tsc --noEmit` を走らせて 5 秒待つ」ループが 20 ミリ秒 に圧縮。エージェントが迷走した際の試行錯誤回数を 10 倍以上増やせます。
Fast Feedback Sequence 
[Agent] Reading definition & types...
  ➔ hover: function processCheckout(): number
  ➔ diagnostic before: 1 error (TS2322)

[Agent] Applying edit to line 4:
- const invalidAssignment: string = totalAmount;
+ const validAssignment: number = totalAmount;

[LSP] textDocument/didChange (version: 2)
[LSP] textDocument/diagnostic
  ➔ 0 errors, 1 warning (TS6133: unusedVariable)

この 20ms のループは人間がエディタで波線を見る感覚と同じ速度です。AI エージェントがリアルタイムにコードの整合性を担保しながら作業を進められます。

Claude Code 連携構成 (1)

Claude Code への接続：.lsp.json 雛形

公式プラグインの課題と解決策

公式の claude-plugins-official/typescript-lsp は typescript-language-server（TS 6 以前）を前提としており、そのままでは TS 7 の高速性を享受できません。

リポジトリルートに以下の .lsp.json を置くだけで、Claude Code の組み込み LSP ツールが直接 tsc --lsp --stdio を利用するようになります。

📁 雛形ファイルを同梱: antigravity-tsc-lsp-research/examples/claude-code-plugin/ 内のファイルをそのままコピーして利用可能です。
.lsp.json (Claude Code Configuration) 
{
  "typescript": {
    "command": "tsc",
    "args": ["--lsp", "--stdio"],
    "filePatterns": [
      "**/*.ts", "**/*.tsx",
      "**/*.mts", "**/*.cts",
      "**/*.js", "**/*.jsx"
    ],
    "initializationOptions": {
      "disablePushDiagnostics": false,
      "userPreferences": {
        "includeInlayParameterNameHints": "all"
      }
    }
  }
}

発表者ノート

Claude Code には 9 種類の LSP ツールが内蔵されており、この設定を入れるだけでモデルが自律的に tsc --lsp のツールを呼び分けます。

MCP 連携構成 (2)

Model Context Protocol (MCP) サーバー設計とトークン圧縮

生の LSP レスポンスの課題

LSP の生レスポンス（例: completion や documentSymbol）は数万行の JSON になり得ます。これをそのまま LLM に渡すと一瞬でコンテキストウィンドウが枯渇します。

トークン圧縮アダプター (ts-lsp-mcp)

同梱の examples/agent-mcp/mcp-server.mjs は、生の LSP を受け取り、エージェントに必要な要約情報へ圧縮して返却します：

  • ts_get_diagnostics: 行番号・コード・メッセージのみ（1件20トークン）
  • ts_hover_type: Markdown のシグネチャ部のみ抽出
  • ts_get_definition: ファイル名:行:列 に圧縮
ts-lsp-mcp Tool Execution 
Agent ➔ MCP: tools/call (name: "ts_get_diagnostics", file: "index.ts")

# 内部で tsc --lsp の Pull 診断を実行し、最小テキストに要約:

MCP ➔ Agent:
{
  "content": [{
    "type": "text",
    "text": "L4:7 [TS2322] Type 'number' is not assignable to type 'string'.\nL5:7 [TS6133] 'unusedVariable' is declared but its value is never read."
  }]
}

✔ 生の巨大 JSON (1,500 bytes) ➔ わずか 120 bytes (約 30 トークン) に圧縮！

発表者ノート

MCP サーバーを薄いアダプターとして挟むことで、Antigravity や Claude Desktop、Cursor、Orca などあらゆるエージェントから統一的に利用できます。

Limitations 制約とエコシステム

現在の制約・注意点と各ツールの対応状況

1. 埋め込み言語 (Vue / Svelte / Astro) の壁

Volar 等の拡張プラグインは Node.js ランタイム上で動く tsserver.js のプラグインフックに依存していました。Go バイナリである tsc --lsp では直接実行できません。これらのフレームワークを使うリポジトリは TS 6 を維持するか、ハイブリッド運用が必要です。

2. コンパイラ API の一時的不在

ts.createProgram() などの AST 操作プログラマティック API は TS 7.0 では不安定。TS 7.1 での CGO / WebAssembly による再提供が計画されています。

Roadmap 推奨アクション

リポジトリ別移行判断と導入ロードマップ

リポジトリ別の推奨判断

  1. 純粋な TS / TSX リポジトリ:
    ➔ 今すぐ TS 7.0.2 へ移行推奨。エージェント用 LSP に tsc --lsp --stdio を設定し、1ms 診断の高速ループを獲得する。
  2. Vue / Svelte / Astro を含むリポジトリ:
    ➔ TS 6 + typescript-language-server を継続。ビルド高速化のため npm エイリアスで TS 7 をビルド専用に併用するハイブリッド構成を採る。
  3. 深いリファクタリングを行う Bot 開発:
    ➔ examples/agent-mcp/ の骨格を用いて薄い MCP サーバーを構築し、定義・参照・Call Hierarchy をツールとして提供する。

今後の注目ロードマップ (TypeScript 7.1)

  • プログラマティック API の正式復活: AST 操作やトランスパイル API が CGO / Wasm 経由で公開予定。
  • 埋め込み言語用 ContentMapper: SFC（単一ファイルコンポーネント）の仮想マッピングがネイティブサポート予定。
  • 公式 MCP サーバー標準化: TypeScript チームによるネイティブ MCP サポートの議論が進展中。
