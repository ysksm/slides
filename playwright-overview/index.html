Playwright 概要

テストライブラリとしての Playwright、コマンドラインツール（CLI）、そして AI エージェント向けの Playwright MCP。3 つの利用形態を、利用シーン・メリット/デメリット・要素技術・確実なコード作成手順の観点で整理する。

2026-09-12Playwright / @playwright/test / @playwright/mcpMicrosoft OSS

Summary

結論を先に：3 つの顔を使い分ける

① ライブラリ / テストランナー 本体

Node.js（ほか Python / Java / .NET）から Chromium・Firefox・WebKit を自動操縦する API と、E2E テストランナー @playwright/test。CI で回す回帰テスト の本命。自動待機とリトライ付きアサーションで flaky になりにくい。

書いたコードが資産になる。習得コストはあるが確実性は最も高い。

② CLI 入口と道具箱

npx playwright ...。ブラウザの導入（install）、操作の記録からのコード生成（codegen）、テスト実行（test）、デバッグ（--ui / show-trace）まで。コードを書かずに始めて、書いたコードを検証する ための道具箱。

codegen は雛形生成、UI モードと Trace Viewer は失敗解析の決定打。

③ MCP AI エージェント向け

@playwright/mcp。Claude Code や VS Code 等の AI エージェントに ブラウザ操作ツール を与える MCP サーバー。スクリーンショットではなくアクセシビリティツリーのスナップショットで操作するのが特徴。探索・検証・テスト草案づくりに向く。

対話的で速いが再現性はエージェント依存。最終成果はコードに落とす。

確実にテストコードを作るなら：MCP / codegen で探索 → ロケータを堅牢化 → @playwright/test のコードに固定 → Trace で検証 → CI へ（詳細は後半）。

What it is

Playwright とは何か

  • Microsoft が 2020 年に公開した ブラウザ自動化フレームワーク（OSS, Apache-2.0）。Puppeteer の開発チームが移籍して開発した後継的存在。
  • Chromium・Firefox・WebKit（= Safari 系）の 3 エンジンを単一 API で操作。Google Chrome / Microsoft Edge の branded ブラウザやモバイルエミュレーションにも対応。
  • 言語バインディングは TypeScript / JavaScript が第一級。Python・Java・.NET (C#) も公式サポート。
  • E2E テストランナー @playwright/test を同梱：並列実行・fixture・リトライ・レポート・トレース収集まで一体。
  • 用途はテストに限らない：スクレイピング、スクリーンショット / PDF 生成、業務の自動操作、AI エージェントのブラウザ操作基盤（MCP）。

類似ツールとの位置づけ

SeleniumWebDriver 標準準拠・言語/実ブラウザの網羅性重視。歴史が長い分、待機処理は自前になりがち
Cypressブラウザ内で実行する開発者体験重視。マルチタブ・マルチオリジンや WebKit に制約
PuppeteerChromium 特化の操作ライブラリ。テストランナーは別途必要

ブラウザコンテキスト

Cookie・ストレージが分離された「シークレットウィンドウ」相当を数十 ms で生成。テストごとの完全独立 と並列実行を安価に実現する。認証状態は storageState で保存・再利用。

プロセス外 (out-of-process)

Cypress と違いブラウザの外から制御するため、マルチタブ・マルチオリジン・複数ブラウザ同時操作・iframe を自然に扱える。ネットワークの傍受・改変（route）も可能。

イベント駆動の待機

ポーリングではなくブラウザ内部のイベントを購読して「操作可能になった瞬間」に実行。これが次スライドの auto-waiting の土台。

Core concepts · 要素技術 ②

確実性を支える中核概念：Locator・Auto-waiting・Web-first assertion

Locator（遅延評価される要素参照）

セレクタを即座に解決せず、操作の瞬間に毎回探し直す。推奨は利用者視点のロケータ：getByRole（アクセシビリティロール）・getByLabel・getByText・getByTestId。CSS/XPath は DOM 構造依存で壊れやすいため最終手段。strict mode により 1 件に絞れない操作はエラーになる。

Auto-waiting（自動待機）

click() 等は対象が「表示されている・安定している・イベントを受け取れる・有効」になるまで自動で待つ。sleep / 手書き wait を書かない のが Playwright 流で、flaky テストの主因を設計で潰している。

Web-first assertion（リトライ付き検証）

await expect(locator).toHaveText(...) は条件を満たすまでタイムアウト内で再評価する。非同期描画の SPA でも「いつ検証するか」を人間が調整しなくてよい。

// 利用者視点のロケータ + 自動待機 + リトライ付き検証 import { test, expect } from '@playwright/test'; test('ログインできる', async ({ page }) => { await page.goto('/login'); await page.getByLabel('メールアドレス').fill('a@example.com'); await page.getByLabel('パスワード').fill('secret'); await page.getByRole('button', { name: 'ログイン' }).click(); // ↑ ボタンが可視・有効・安定になるまで自動で待つ await expect(page.getByRole('heading', { name: 'ダッシュボード' })) .toBeVisible(); // ← 描画完了までリトライ });

その他の要素技術

  • アクセシビリティツリー：getByRole と MCP のスナップショットの共通基盤
  • Trace：実行の全記録（スクリーンショット・DOM・ネットワーク・ソース）を 1 ファイルに
  • fixture / project：前提条件の合成と、ブラウザ×設定のマトリクス実行
  • ネットワークモック（page.route）・デバイスエミュレーション・ビジュアル比較（toHaveScreenshot）

① Library / test runner · 利用シーン

通常の Playwright：どこで使うか

E2E 回帰テスト 本命

リリース前の主要導線（ログイン・購入・検索など）を CI で毎回検証。並列・シャーディング・リトライ・トレース収集が揃い、大規模スイートの運用に耐える。

クロスブラウザ検証

同じテストを Chromium / Firefox / WebKit の project として実行。Safari 系（WebKit）を Linux CI 上で回せるのは大きい。モバイルは viewport / UA / タッチのエミュレーション。

API + UI の複合テスト

request フィクスチャで API を直接叩き、テストデータ準備や事後検証を API で、操作だけ UI で行う。セットアップの高速化と安定化に効く。

ビジュアルリグレッション

toHaveScreenshot() でスクリーンショット比較。CSS 崩れやデザイン差分の検出。閾値・マスク指定あり。

スクレイピング・RPA 的自動化

テスト以外でも、ログインが必要なサイトからのデータ取得、定型業務のブラウザ操作、スクリーンショット / PDF の定期生成などに library として利用。

モック駆動のフロント開発

page.route() でバックエンド未完成でも UI テストを先行。障害系（500・遅延・オフライン）の再現にも。

① Library / test runner · 評価

通常の Playwright：メリット / デメリット

メリット

  • flaky になりにくい設計：auto-waiting + リトライ付きアサーションで待機バグを構造的に排除
  • 3 エンジン対応：WebKit 含むクロスブラウザを単一 API・単一 CI で
  • 実行が速い：ブラウザコンテキストによる軽量分離 + ワーカー並列 + シャーディング
  • デバッグ体験：Trace Viewer / UI モード / Inspector が標準装備。CI の失敗もトレースで事後解析できる
  • 一体型：ランナー・レポート・モック・スクリーンショット比較まで公式で完結し、組み合わせ選定が不要
  • 多言語 + 活発な開発：TS/JS・Python・Java・.NET。月次リリースで改善が速い

デメリット / 注意点

  • 学習コスト：locator の考え方、fixture、非同期 API（await 忘れ）など、正しく書くための前提知識が要る
  • ブラウザバイナリの管理：バージョンごとに専用ビルドをダウンロード（数百 MB）。CI キャッシュや --with-deps の運用が必要
  • 「本物のブラウザ」との差：WebKit は Safari そのものではなく、branded Chrome も別途指定が要る。実機検証の完全代替ではない
  • E2E 自体のコスト：どのツールでも E2E は遅く壊れやすい層。テストピラミッドの上位に薄く置く設計判断は依然必要
  • 古い IE や実デバイス群は対象外：その領域は Selenium ベースのクラウド（BrowserStack 等）と併用

② CLI · 利用シーンと評価

CLI：利用シーンとメリット / デメリット

利用シーン

  • 導入初日：codegen で操作を記録し、動く雛形を数分で得る
  • ロケータ調査：codegen / open の Pick locator で、推奨ロケータを対話的に確認
  • テスト開発中：UI モードでウォッチ実行しながら書く
  • CI 失敗の解析：trace.zip を手元で再生（スクリーンショット・DOM・ネットワーク・コンソールを時系列で）
  • 単発作業：screenshot / pdf をシェルスクリプトから

メリット

  • コードを書かずに始められる：codegen が locator のベストプラクティス（getByRole 優先）に沿ったコードを吐く
  • デバッグの決定打：Trace Viewer は「CI でだけ落ちる」問題の再現手段として他ツールにない強み
  • 学習教材になる：生成コードを読むことが API の学習になる
  • 追加インストール不要（本体に同梱）

デメリット / 注意点

  • codegen は雛形止まり：アサーションはほぼ手書き。重複・冗長な操作、脆いロケータが混ざることもあり、そのまま資産化しない
  • 記録できるのは単線的な操作のみ：条件分岐・データ駆動・fixture 設計は人間の仕事
  • UI モード・Trace Viewer は GUI 前提。ヘッドレスサーバーでは trace.zip を手元に持ち出す運用になる

位置づけ：CLI は「①ライブラリを速く正しく使うための補助輪と計器」。単独で完結する形態ではない。

③ MCP · what & how

Playwright MCP：AI エージェントにブラウザを渡す

  • MCP (Model Context Protocol)：LLM アプリに外部ツールを標準形式で提供するプロトコル（Anthropic 発、2024〜）。@playwright/mcp は Microsoft 公式の MCP サーバー。
  • Claude Code / Claude Desktop / VS Code (Copilot) / Cursor などの MCP クライアントに登録すると、エージェントが browser_navigate・browser_click・browser_type 等のツールでブラウザを操作できる。
  • 核心は スナップショットモード：ページを画像ではなくアクセシビリティツリー（役割・名前・状態 + 要素参照 ref）として LLM に渡す。ビジョンモデル不要・軽量・構造的で、操作対象の指定が曖昧にならない。
  • 座標ベースで操作するビジョンモード（--caps=vision）、トレース保存、デバイス指定、ヘッドレス切替などのオプションあり。
# Claude Code への登録例 $ claude mcp add playwright -- npx @playwright/mcp@latest # VS Code 等では mcp.json に: { "servers": { "playwright": { "command": "npx", "args": ["@playwright/mcp@latest"] } } }
# エージェントが受け取るスナップショット（抜粋） - banner: - heading "Example Domain" [level=1] [ref=e2] - paragraph [ref=e3]: This domain is for use in … - link "More information..." [ref=e4] - /url: https://www.iana.org/domains/example # エージェントのツール呼び出し browser_click({ element: "More information リンク", ref: "e4" })

主なツール群

browser_navigate / browser_snapshot / browser_click / browser_type / browser_fill_form / browser_select_option / browser_take_screenshot / browser_evaluate / browser_console_messages / browser_network_requests / タブ操作 など。

裏側は同じ Playwright

auto-waiting やロケータ解決など①と同じエンジンが動く。「LLM がクライアントになった Playwright」と捉えるのが正確。

③ MCP · 利用シーン

MCP：どこで使うか

実装の動作確認 日常使い

AI エージェントにコードを書かせた後、そのエージェント自身がブラウザで動作確認し、コンソールエラーやレイアウト崩れを見て自己修正する。「書く→動かす→直す」ループが 1 エージェントで閉じる。

探索的テスト

「この画面で入力値の境界を試して、おかしい挙動を報告して」のような自由探索。人間の探索的テストの下調べや、バグの再現手順の特定に。

テストコードの草案生成

エージェントが実際に画面を操作して実在するロケータと画面遷移を確認しながら @playwright/test のコードを書く。想像で書くより格段に正確（後述の手順の中核）。公式の Playwright Agents（planner / generator / healer）もこの発想。

Web 操作の自動化

「このサイトから◯◯を調べて表にして」のような非定型の調査・操作。毎回コードを書くほどでもない作業を自然言語で。

失敗テストの自己修復

落ちたテストのエラーとトレースをエージェントに渡し、MCP で実画面を確認させて修正案を出させる（healer パターン）。UI 変更でロケータが壊れた類の修正に有効。

向かないこと

CI での回帰テスト実行（遅い・非決定的・トークン費用）。検証の本番は常に①のコードで行い、MCP は探索と生成に使う。

③ MCP · 評価

MCP：メリット / デメリット

メリット

  • コード不要・自然言語で即操作：非エンジニアでも「ブラウザで◯◯して」が通る
  • アクセシビリティツリー方式が LLM と相性抜群：画像認識より速く・安く・曖昧さがなく、要素参照（ref）で操作が外れにくい
  • 実画面に接地したコード生成：エージェントが実在の DOM を見て書くため、幻覚ロケータが激減する
  • 公式サポート：Playwright 本体と同じチームが開発。エンジン・待機戦略をそのまま継承
  • エコシステム：Claude Code / VS Code / Cursor 等、主要な AI コーディング環境がそのまま接続先になる

デメリット / 注意点

  • 非決定的：同じ指示でも操作手順が揺れる。回帰テストの実行手段にはならない
  • トークン消費と遅さ：巨大なページのスナップショットはコンテキストを圧迫。1 操作ごとに LLM の往復が入る
  • セキュリティ：Web ページ内のテキストによるプロンプトインジェクションの経路になる。認証情報を扱うサイト・書き込み操作は権限設計と人間の確認が必須
  • 複雑 UI の限界：canvas 描画・独自ウィジェット等、アクセシビリティツリーに乗らない UI は苦手（ビジョンモードで補完）
  • 実行環境の管理：ブラウザ常駐・セッション状態・並行利用など、運用の考慮点は通常の Playwright と同様に残る

3
ロケータの堅牢化 手作業 / レビュー
getByRole / getByLabel / getByTestId へ寄せ、CSS / XPath / nth() を排除する。1 意に定まらないものは data-testid をアプリ側に追加。壊れないテストはロケータで決まる。
4
検証の設計 web-first assertion
「操作できた」ではなく「ユーザーに見える結果」を expect(locator).toBeVisible() / toHaveText() / toHaveURL() で検証。waitForTimeout（sleep）は使わない。前提データは fixture / API で用意し、テスト間の依存をなくす。
5
安定性の証明 CLI
npx playwright test --repeat-each=5 と --project 全ブラウザで flaky を炙り出し、--trace on-first-retry で原因を特定して潰す。初回から安定して通るまでがコード作成。
6
CI へ固定・保守 test ランナー healer
CI に組み込み（install --with-deps・シャーディング・レポート）、以後の失敗はトレースで解析。UI 変更で壊れたら、エラー + MCP で実画面をエージェントに見せて修正させる（自己修復）。

Wrap-up

まとめと参考資料

要点

  • Playwright は 1 つのエンジンに 3 つの入口：コード（①）・人間の手（②）・AI エージェント（③）。
  • 確実性の源泉は Locator + auto-waiting + web-first assertion。どの入口を使ってもこの土台の上に乗る。
  • MCP は「探索と生成」、CLI は「導入とデバッグ」、テストランナーが「検証の本番」。探索は柔らかく、資産は固く。
  • AI 時代のワークフロー：MCP で実画面に接地させてコードを書かせ、人間がロケータとアサーションをレビューし、CI で決定的に回す。

  • claude mcp add playwright -- npx @playwright/mcp@latest でエージェントにブラウザを渡してみる
