tsc --lsp 調査報告

TypeScript 7 のネイティブ言語サーバーで何ができるか、どこで使うか、そして AI エージェントにコードを読ませる手段としてどう評価するか。

2026-09-12TypeScript 7.0.2 / typescript-go実機検証: macOS arm64

Summary

結論を先に

何か

TypeScript 7 (2026-07-08 GA) では tsc の Go 製バイナリ自体が LSP サーバー。tsc --lsp --stdio で起動し、Node も tsserver.js も typescript-language-server も不要。

初期化 7 ms、起動時 RSS 18 MB。標準 LSP のほぼ全機能を提供。

どこで使うか

エディタ統合が本命だが、プロセスを長く抱えて何度も問い合わせる 用途すべてに向く。AI エージェント、リファクタ用バッチ、モノレポの解析ツール、省メモリな CI/クラウド環境。

AI エージェント向け評価

実測で TS6 系より 診断 8〜17 倍、シンボル検索 30 倍 速く、メモリは 1/2.7。「編集→即診断→修正」ループに最適。ただし Claude Code 公式プラグインは TS6 系前提のため、カスタム LSP 設定か薄い MCP ラッパー が必要。

What it is

tsc --lsp とは何か

  • TypeScript 7.0 でコンパイラと言語サービスが Go に移植された (typescript-go, 通称 tsgo)。npm の typescript@7 は bin/tsc が Node の薄いシムで、実体は @typescript/typescript-<os>-<arch>/lib/tsc のネイティブバイナリ。
  • 第 1 引数が --lsp なら LSP サーバー、--api なら内部 API サーバー、それ以外は従来のコンパイル CLI。
  • 旧 tsserver (独自 JSON プロトコル) は廃止。パッケージに tsserver.js は含まれない。
  • VS Code はビルトイン化が進行中。他エディタは LSP 準拠なら「そのまま動く」設計。

起動オプション (tsc --lsp --help の実出力)

-stdio標準入出力で通信 (現状これのみ動作)
-pipe / -socket宣言はあるが未実装。指定すると "only stdio is supported" で終了
-clientProcessId親プロセス監視。クライアントが死ぬと 5 秒周期の watchdog が自動終了
-pprofDirGo の CPU/メモリプロファイルを出力

診断はプル型

textDocument/diagnostic を呼ぶと即座に結果が返る (interFileDependencies: true)。従来のプッシュ配信 (publishDiagnostics) も併用され、disablePushDiagnostics で止められる。ワークスペース全体のプル (workspaceDiagnostics) は false。

設定の取り方

初期化直後に workspace/configuration で js/ts・typescript・javascript・editor セクションを要求。VS Code の設定キー体系がそのまま流用できる。initializationOptions.userPreferences でも渡せる。

ログと厳密さ

ログは window/logMessage と stderr。JSON-RPC の検証が厳密で、shutdown に params: null を付けると InvalidParams (実測)。省略が正解。

Vue 等のエディタ支援は TS 6 に残し、ビルドだけ TS 7 に寄せる構成が公式に案内されている。

既定値の変更が診断内容を変える

strict: true、rootDir: "./"、types: [] が既定に。TS 6 では出なかったエラーが LSP からも返るので、エージェントに「新規エラー」として見せる際は基準を揃える。

Use cases

目的別の利用ケース

エディタ統合 本命

VS Code (拡張 → ビルトイン化)、Visual Studio、Zed、Neovim、Emacs eglot、Helix。設定は tsc --lsp --stdio を指すだけ。

AI コーディングエージェント 本調査の主題

編集直後の診断、定義・参照・型情報の取得。次スライド以降で詳述。

リポジトリ横断のバッチ解析

workspace/symbol → references → callHierarchy を機械的に回して依存グラフや影響範囲表を作る。7.0 では公開 API が無いので、LSP が唯一の安定した機械向け入口。

自動リファクタリング Bot

rename と willRenameFiles が WorkspaceEdit を返すので、大量の改名・ファイル移動を型情報付きで安全に適用できる。source.organizeImports 等の一括適用も。

省メモリな常駐環境

起動 18 MB、Node 不要の単一バイナリ。コンテナ内のクラウド IDE、開発サーバー、MCP サーバーのサイドカーに向く。親プロセス監視で孤児化もしない。

CI の差分診断

変更ファイルだけ didOpen → diagnostic で PR 単位の指摘を数十 ms で得る。全体検査は従来通り tsc --noEmit (それ自体も 8〜10 倍高速)。

AI agents · why LSP

エージェントにコードを「読ませる」とは何か

grep とファイル読み込みだけのエージェントは、名前の一致 しか見えない。LSP は型検査器の理解をそのまま問い合わせられる。

エージェントの問いgrep でtsc --lsp で
この変更で壊れた箇所は？テスト or 全体ビルドを回すdiagnostic 33 ms
この関数はどこから呼ばれる？同名の文字列を全部拾う (誤検出多)references / incomingCalls
この値の型は？宣言を辿って推論を手で追うhover が推論後の型を返す
このインターフェースの実装は？難しいimplementation
ファイル全体の構造は？全文をコンテキストに載せるdocumentSymbol で目次だけ
名前だけ知っている API はどこ？find + grepworkspace/symbol 6 ms

トークン節約の観点

5,265 行の schemas.ts を丸ごと読ませる代わりに、documentSymbol (432 シンボル) と必要な箇所の hover だけを渡せる。読む対象を絞れるほど、コンテキスト消費と誤読が減る。

「編集 → 即診断 → 修正」ループ

エージェントが書いた直後に didChange + diagnostic を回すと、同じターン内で型エラーに気づいて直せる。TS 6 系の 578 ms でも成立するが、TS 7 の 33 ms なら 1 文字単位の試行錯誤 にも耐える。

既に LSP を前提にしている周辺

Claude Code の LSP ツール (2025-12 〜)、OpenCode の内蔵 LSP、Serena MCP、typescript-mcp (Go 製、tsgo 直結)。TS 7 対応は各所で issue が立っている段階。

AI agents · 組み込み方 ①

Claude Code に tsc --lsp を直接つなぐ

Claude Code のプラグインは .lsp.json で任意の LSP サーバーを登録できる。公式 typescript-lsp は typescript-language-server 前提なので、TS 7 プロジェクトでは 自前プラグインに差し替える。同じ拡張子を複数サーバーが取り合うと先勝ちなので、公式側は無効化する。

// my-ts7-lsp/.lsp.json { "typescript": { "command": "tsc", // npm -g か PATH 上の 7.x "args": ["--lsp", "--stdio"], "extensionToLanguage": { ".ts": "typescript", ".tsx": "typescriptreact", ".mts": "typescript", ".cts": "typescript", ".js": "javascript", ".jsx": "javascriptreact" }, "initializationOptions": { "disablePushDiagnostics": true }, "restartOnCrash": true, "maxRestarts": 3, "diagnostics": true } }

雛形: tsc-lsp/examples/claude-code-plugin/。ロードは claude --plugin-dir ./my-ts7-lsp または自前マーケットプレイス。

これで Claude が得るもの

  • 編集ごとの自動診断: Edit 後に型エラー・未使用・import 漏れがコンテキストに入る
  • LSP ツール: goToDefinition / findReferences / hover / documentSymbol / workspaceSymbol / goToImplementation / incomingCalls / outgoingCalls
  • 上記はすべて tsc --lsp が initialize で広告している機能と一致

確認すべき点

  • stdout は プロトコル専用。tsc はログを stderr と window/logMessage に出すので要件を満たす
  • プッシュ診断を切るとログが減り、プル (diagnostic) だけで動く。両方来ても害はない
  • プロジェクトの typescript が 7 でないと既定値差 (strict 等) で診断がズレる。command を node_modules/.bin/tsc に固定するのが安全
  • クラウド版 Claude Code ではプラグイン LSP は起動しない

薄い LSP クライアントを MCP / ツールとして持つ

設計上の勘所

  • ワークスペースごとに 1 プロセス を使い回す (再起動は 100 ms 未満だが、スナップショットを捨てるのは無駄)
  • エージェントが触るファイルだけ didOpen。workspace/configuration と client/registerCapability には空応答でよい
  • 返却 JSON をそのまま LLM に渡さず、位置 + 1 行要約 に圧縮する (references 451 件をそのまま渡すと数千トークン)
  • ファイル横断の全件検査は tsc --noEmit -p を別途叩く (workspaceDiagnostics 非対応)

Caveats

制約と落とし穴 (実測・一次情報ベース)

stdio のみ

-pipe / -socket はヘルプに出るが、指定すると "only stdio is supported" で終了する (cmd/tsgo/lsp.go)。複数クライアントで 1 プロセスを共有したい場合は自前でプロキシする。

JSON-RPC が厳密

shutdown / exit に params: null を送ると InvalidParams。params は省略するか object/array にする。一部の既存クライアントライブラリは null を送るので要確認。

ワークスペース全体の診断は無い

workspaceDiagnostics: false。開いていないファイルのエラーは LSP からは取れない。全体検査は tsc --noEmit を併用 (zod で 0.35 秒)。

既定値の差で「新しいエラー」が増える

TS 7 は strict、rootDir、types の既定が変わった。TS 6 の tsconfig をそのまま読むと LSP 診断が増え、エージェントが自分のせいだと誤認しうる。tsconfig を明示して基準を固定する。

inlayHint / codeAction は設定依存

実測で inlayHint は既定 0 件 (VS Code の設定キーで有効化)。codeAction は診断に quickfix が存在する場合のみ返る。エージェントに「修正案を求める」用途では過信しない。

API は 7.1 まで待つ

7.0.2 のパッケージには typescript/unstable/sync|async と tsc --api (MessagePack / JSON-RPC) が同梱されているが名前の通り不安定。型・シンボルを直接触る解析は当面 LSP 経由か TS 6 API で。

Recommendation

推奨と次のアクション

  1. TS 7 で書かれたリポジトリ では、エージェントの LSP を tsc --lsp --stdio に切り替える。Claude Code は examples/claude-code-plugin の雛形をそのまま使える。
  2. Vue / Svelte / Astro を含むリポジトリ は TS 6 + typescript-language-server (または vtsls) を残し、npm エイリアスで TS 7 をビルド専用に併用する。
  3. 影響範囲分析やリファクタ Bot など深い問い合わせが要る用途は、examples/lsp-probe.mjs を骨格に薄い MCP サーバーを書く。返却は位置 + 要約に圧縮する。
  4. 全体検査は引き続き tsc --noEmit。LSP は「今触っているファイル」の高速ループ担当と割り切る。
  5. 7.1 の API 公開と、公式 typescript-lsp プラグイン / Serena / typescript-language-server 側の TS 7 対応を追う。
