Redmine の UI を
SPA で作るための技術

Rails 製の Redmine を「API サーバー」として扱い、UI を自前の SPA に置き換える方法、間に別の Web サーバー（BFF / リバースプロキシ）を挟む方法、そしてデスクトップアプリ化する方法を、制約と実装パターンの観点で整理する。

2026-09-14Redmine 5.x / 6.x · REST APIIssue #26

Summary

結論を先に：3 つの問いへの答え

① UI の置き換え SPA

Redmine の REST API（JSON）を使えば、チケット・プロジェクト・時間記録・Wiki など主要機能は SPA から操作できる。置き換えの粒度は 3 段階：テーマ / プラグインで一部を差し替える → プラグイン内に SPA を同梱 → 完全分離した SPA。

API に無い機能（ワークフロー・管理画面・リポジトリ閲覧など）は「Redmine 本体に飛ばす」か「プラグインで API を足す」。

② 別 Web サーバー経由 BFF / Proxy

ブラウザから Redmine の API を直接叩くと CORS・API キーの扱い・N+1 呼び出し で行き詰まる。同一オリジンに見せる リバースプロキシ を最低限、認証の変換・集約・キャッシュ・SSO まで担うなら BFF（Backend for Frontend） を置く。

Redmine 自体は改造しない。管理者キーと X-Redmine-Switch-User でユーザー代理も可能。

③ デスクトップ化 Tauri / Electron

①で作った SPA をそのまま Tauri（v2） か Electron に載せる。ネイティブ側の HTTP クライアントは CORS の制約を受けないため Redmine に直接接続 でき、BFF 無しでも成立する。通知・トレイ・資格情報の安全な保存・自動更新が主な追加設計。

まず PWA で足りないかを確認。Redmine の画面をそのまま包む「ガワアプリ」も最小コストの選択肢。

推奨する段階: SPA + リバースプロキシ（同一オリジン） で開始 → 認証・集約が必要になったら BFF → 同じ SPA を Tauri でデスクトップ配布（詳細はスライド 15）。

Baseline

前提：Redmine のアーキテクチャと「置き換え可能な面」

  • Redmine は Ruby on Rails のモノリス（GPLv2）。5.x は Rails 6.1、6.0（2024-11）は Rails 7.2 ベース。
  • 画面は ERB テンプレート + jQuery / jQuery UI のサーバーサイド描画。SPA フレームワークは使っておらず、フロントの状態管理・ルーティングは持たない。
  • 拡張点は プラグイン（Rails エンジン相当：ルート・コントローラ・モデルパッチ・view hook）と テーマ（CSS + theme.js）。

  • 参考：フォークの OpenProject は Rails バックエンド + Angular SPA + API v3（HAL+JSON）へ全面移行した実例。「Rails を API 化して UI を分離する」道の到達点として参照できる。

置き換えの 3 つの面

A 画面の一部テーマの JS / プラグインの view hook で特定画面に SPA 部品を注入
B 同居 SPAプラグインが /app/* のような経路で SPA を配信。Redmine のセッション・認証をそのまま使える

# 自分のチケット（未完了）を更新日時の新しい順に GET /issues.json?assigned_to_id=me&status_id=open &sort=updated_on:desc&limit=100 # 1 件 + 履歴・添付・関連 GET /issues/123.json?include=journals,attachments # 更新（コメント付き） PUT /issues/123.json { "issue": { "status_id": 3, "notes": "対応済み" } } # 差分同期のための増分取得 GET /issues.json?updated_on=%3E%3D2026-09-14T00:00Z # ログイン中ユーザーと API キー（Basic 認証で呼ぶ） GET /users/current.json → {"user": {"api_key": …}}

重要な仕様：API 呼び出しにセッションは使われない

.json / .xml の要求は API リクエスト として扱われ、ログイン Cookie ではなく API キー / Basic 認証で認証される。つまり「Redmine にログイン済みのブラウザから fetch」はそのままでは通らない。SPA は必ず API キーをどこで持つか を設計する必要がある。

Foundation · Coverage

REST API のカバレッジ：SPA で作れる範囲を先に把握する

資源読み書き備考
Issues（チケット）○○CRUD・ウォッチャー・関連・添付。一括編集は無い（1 件ずつ PUT）
Projects / Memberships / Versions○○アーカイブ・閉鎖・再開は 5.0 以降

Wiki pages / News / Files○○Wiki は本文が生テキスト（下段の整形問題）

足りない部分の埋め方（優先順）

  1. SPA 側で計算する：ガント・カレンダー・集計は issues / versions から描ける。
  2. プラグインで API を足す：Rails コントローラに accept_api_auth を宣言し .api.rsb テンプレートで JSON を返す。Redmine 本体の textilizable を呼べば整形済み HTML の API も作れる。
  3. Redmine 本体へ遷移する：管理画面・ワークフローは SPA から本体の URL にリンクするだけにする。
  4. HTML をスクレイピングする：CSRF・レイアウト変更に弱い。最後の手段。

型と API 定義

公式の OpenAPI 定義は無い。コミュニティ製の定義や TypeScript クライアントはあるが版ずれに注意。実務では 使う資源だけ zod 等でスキーマを書き、応答を実行時検証 する方が安全。カスタムフィールド（custom_fields: [{id, name, value}]）は動的なので特に。

① Replace the UI · Overview

UI 置き換えの 3 方式：どこまで Redmine から離れるか

A 部分注入（テーマ / プラグイン）

既存画面はそのまま。テーマの javascripts/theme.js や プラグインの view hook（view_layouts_base_html_head / …_body_bottom）で JS を読み込み、特定の要素に React / Vue / Svelte の小さな島（Islands）をマウントする。

  • ログイン・権限・CSRF は Redmine のまま。導入が最も軽い
  • 1 画面ずつ段階的に改善できる
  • Redmine の DOM / jQuery と共存。本体更新で壊れやすい
  • API 呼び出しには結局 API キーが要る（後述）

B プラグイン同居 SPA

プラグインがルート（例 /app/*）とコントローラを持ち、ビルド済み SPA の index.html を返す。SPA は同一オリジンで動くので CORS 無し。プラグイン側にセッション認証で動く独自 JSON エンドポイントを足せば API キー問題も消える。

  • Redmine のログイン・SSO・権限をそのまま利用
  • 不足 API を同じプラグインで補える
  • Ruby / Rails の知識と Redmine 更新への追従が必要
  • 配布・デプロイが Redmine 本体と一体になる

C 完全分離 SPA

SPA は別リポジトリ・別ホスティング（静的配信）。Redmine とは REST API のみで会話する。Redmine 側は無改造で、複数の Redmine インスタンスにも接続できる。デスクトップ化（③）と最も相性がよい。

  • フロント技術を自由に選べる。Redmine 更新の影響が最小
  • 同じ SPA を Web / デスクトップ / モバイルへ展開
  • CORS・認証・API の穴を 自分で解決する → ② の BFF が必要になりがち
  • API に無い機能は作れない、または本体へ飛ばす

選び方：既存運用を壊さず改善 → A。Redmine 管理者 = 開発者 で Ruby も書ける → B。SaaS 的に配布 / 複数 Redmine / デスクトップ → C（+ BFF）。

Redmine 固有の設計上の注意

  • ID とマスタの解決：API は status: {id, name} のように ID 中心。トラッカー・ステータス・優先度・カスタムフィールドの定義を起動時に取得してキャッシュする。
  • プロジェクトごとの差：使えるトラッカー・カスタムフィールド・モジュールがプロジェクト単位で違う。GET /projects/:id.json?include=trackers,issue_custom_fields,enabled_modules。
  • 遷移可能ステータス：ワークフロー API は無いので include=allowed_statuses（5.0 以降）で本人視点の選択肢を得る。
  • 100 件上限：一覧・エクスポートは offset ループ。大量なら BFF 側で並列化とキャッシュ。
  • 添付：2 段階アップロード。ダウンロードにも認証が要るので <img src> で直接参照できない → BFF 経由か Blob 化。

① Replace the UI · Pitfalls

ブラウザから直結したときに必ず当たる 4 つの壁

1. CORS

Redmine は Access-Control-Allow-* ヘッダーを返さない。別オリジンの SPA からの fetch はプリフライトで失敗する。

対処: 同一オリジンにする（リバースプロキシ / 方式 B）、または Redmine 側に rack-cors を導入するプラグイン。JSONP（GET 限定・レガシー）は使わない。

2. API キーの置き場

API はセッションを見ないので SPA はキーを持つ必要がある。ブラウザの localStorage に置くと XSS で漏れる。

対処: BFF が Redmine の Basic 認証で /users/current.json を叩き、返る api_key をサーバー側セッションに保持。ブラウザは HttpOnly Cookie だけ持つ。

3. テキスト整形

説明・コメント・Wiki は Textile / Markdown の生テキストで返る。#123・[[Wiki]]・{{macro}}・添付画像の展開は Redmine 独自。

対処: 近似レンダラで妥協するか、プラグイン / BFF に「整形 API」を作る。書き込みは生テキストのままで問題ない。

4. N+1 と 100 件上限

かんばん 1 画面で「プロジェクト → ステータス → チケット → 担当者アバター」と往復が増える。limit は 100 まで。

対処: include の活用、マスタのキャッシュ、BFF での集約と並列取得、updated_on による差分更新。

この 4 つはどれも Redmine と SPA の間に「自分のサーバー」を置くと解ける。それが ②「別 Web サーバー経由」の動機であり、①C を選ぶなら②はほぼ必須になる。逆に ①A / ①B（同一オリジン + セッション）なら 1・2 は最初から発生しない。

# L1: nginx で同一オリジン化する最小構成 server { listen 443 ssl; server_name tracker.example.com; location / { # SPA root /srv/spa/dist; try_files $uri /index.html; } location /api/ { # Redmine へ転送 proxy_pass https://redmine.internal/; proxy_set_header Host redmine.internal; # L2 以降はここでキーを付与する # proxy_set_header X-Redmine-API-Key $key; } }

Redmine 側で追加する設定は「ほぼ無し」

REST API を有効化するだけ。Switch-User を使うなら管理者ユーザーの API キーを 1 つ発行して BFF に渡す。Redmine 本体のコードは触らない。Redmine 更新に対する耐性が ② の最大の利点。

パターン 1：本人の API キーを預かる 推奨

  1. SPA のログイン画面で Redmine の ID / パスワードを受け取る。
  2. BFF が Basic 認証で GET /users/current.json → 成功なら api_key を得る。
  3. API キーだけを暗号化してサーバー側セッションに保存。パスワードは捨てる。
  4. 以後の呼び出しは X-Redmine-API-Key を付けて転送。権限は本人のまま。

Redmine の LDAP 認証もそのまま効く（Basic → User.try_to_login）。二要素認証を有効にしたユーザーは Basic でのパスワード認証が通らないため、API キー入力の経路も用意する。

パターン 2：SSO + 管理者キーで代理 Switch-User

  1. BFF が OIDC / SAML で社内 IdP にログインさせる（Redmine には無い機能）。
  2. IdP のユーザー ID → Redmine のログイン名を対応付け。無ければ POST /users.json で自動作成。
  3. 管理者キー + X-Redmine-Switch-User: <login> で そのユーザーとして API を呼ぶ。

管理者キーは BFF だけが持つ最重要秘密。漏れると全ユーザーになりすませるため、シークレット管理・監査ログ・IP 制限を必須にする。存在しない / ロック中ユーザーを指定すると 412 が返る。

② Via another web server · BFF design

BFF が担う「Redmine に無いもの」：集約・整形・更新検知

画面単位の集約 API

かんばん 1 画面 = GET /bff/projects/:id/board。BFF が Redmine へ 並列に issues（ステータス別・100 件ずつ）、memberships、issue_statuses を取り、SPA が欲しい形に整えて 1 応答で返す。

// Hono の例 app.get('/bff/projects/:id/board', async c => { const rm = redmineFor(c); // セッションのキー付き const id = c.req.param('id'); const [statuses, issues, members] = await Promise.all([ rm.get('/issue_statuses.json'), rm.pages('/issues.json', { project_id: id, status_id: 'open' }), rm.get(`/projects/${id}/memberships.json`), ]); return c.json(toBoard(statuses, issues, members)) })

整形 API とファイル中継

  • 整形：markdown-it + Redmine 風の拡張（#123 リンク、[[page]]、添付画像 URL の書き換え）。厳密さが要るならプラグイン側で textilizable を公開し BFF から呼ぶ。
  • 添付：/bff/attachments/:id が API キー付きで取得しストリーム返却。<img> から直接参照できる。アップロードは /uploads.json へ中継。
  • キャッシュ：マスタ（トラッカー・ステータス・ユーザー）は数分〜数十分。ETag は BFF が付ける。

更新検知（Webhook は無い）

  • ポーリング：BFF が updated_on=>=前回 で定期取得し、変更を SSE / WebSocket で SPA に配る。ユーザー数によらず Redmine への負荷は一定。
  • Webhook プラグイン：サードパーティ製を Redmine に入れ、BFF が受ける。即時だが Redmine 側改造が発生。
  • 削除は更新日時で拾えない。定期的な ID 突き合わせが必要。

DB 直読みは権限ロジック（Issue.visible）の再実装になるため、書き込みは絶対に、読み取りも原則避ける。

③ Desktop · Options

デスクトップ化の選択肢：PWA・ガワアプリ・Electron・Tauri

方式仕組み配布物向く場面注意点
PWASPA に manifest + Service Worker を追加。ブラウザの「インストール」でウィンドウアプリ化なし（URL）まず試す価値がある。オフライン閲覧・ホーム画面起動だけなら十分OS 通知・トレイ・ファイル連携は限定的。Redmine に直結する場合 CORS は残る
ガワアプリElectron / Tauri のウィンドウで Redmine 本体の URL を開くだけ数 MB〜150 MBSPA を作らずに「専用アプリ感」「通知」「ログイン維持」が欲しいUI は Redmine のまま。JS 注入で多少の改善は可能
ElectronChromium + Node.js を同梱。SPA を file:// / 内蔵サーバーから読み込む150 MB 前後〜実績・情報量最大。Node のライブラリ資産をそのまま使いたいサイズとメモリ。Chromium 追従のための定期更新。セキュリティ設定（contextIsolation）を誤らない
Tauri v2Rust 製コア + OS の WebView（WebView2 / WKWebView / WebKitGTK）。バックエンド処理は Rust か JS プラグイン数 MB〜十数 MB軽量・省メモリ・署名や更新の仕組みが公式。iOS / Android も同コードでWebView が OS 依存で描画差が出る（特に Linux）。Rust を少し書く場面がある

決め方

①C の SPA がある前提なら Tauri が第一候補：バイナリが小さく、@tauri-apps/plugin-http により CORS を気にせず Redmine に直結できるので、デスクトップ版だけは BFF 無しでも成立する。Node 依存のライブラリが必須、または既存 Electron 資産がある場合のみ Electron。

Web 版と共通化する構成

SPA は RedmineClient のような 抽象化層を 1 つ持ち、Web ビルドでは fetch → BFF、デスクトップビルドでは Tauri http → Redmine 直 に差し替える。画面コードは共通。接続先 URL と資格情報の入力画面だけがデスクトップ固有。

Roadmap

推奨構成と段階的な進め方

0
API の棚卸し 1〜2 日
対象 Redmine で REST API を有効化し、作りたい画面ごとに「必要な資源 → API の有無」を表にする（スライド 5）。API に無い機能が主目的なら SPA 化の前に方式 B（プラグイン）を検討する。
1
SPA + リバースプロキシ ①C ②L1
Vite + 任意のフレームワーク + TanStack Query。nginx で同一オリジン化し、開発中は Vite の server.proxy で同じ形にする。認証はいったん「API キーを貼る」で進め、1 画面（自分のチケット一覧 / かんばん）を最後まで作る。
2
BFF を導入 ②L2〜L3
ログイン（本人キー預かり）→ 添付中継 → 集約 API → 整形 API の順に足す。Node（Hono / Fastify）か既存チームの言語。Redmine は無改造のまま。
3
不足 API をプラグインで補完 ①B の技法
整形の厳密さ・ワークフロー情報・一括更新など BFF では埋まらないものだけ、小さな Redmine プラグインで accept_api_auth 付きエンドポイントを追加。プラグインは「API を足す」役割に限定し UI は持たせない。
4
デスクトップ配布 ③ Tauri
同じ SPA を Tauri に載せる。RedmineClient の実装を Tauri http に差し替え、資格情報はキーチェーンへ。通知・トレイ・ディープリンク・自動更新の順に追加。署名の準備（Apple Developer / コードサイニング証明書）は早めに着手。

やらないこと：Redmine の DB 直接参照、Redmine 本体コードの改造、ブラウザ localStorage への API キー保存、管理者キーのクライアント配布。

Wrap-up

まとめと参考資料

要点

  • Redmine は REST API を持つ Rails モノリス。主要機能はヘッドレスに使えるが、API に無い機能とテキスト整形の再現が SPA 化の限界を決める。
  • UI 置き換えは A 部分注入 / B プラグイン同居 / C 完全分離。Redmine からの距離と引き換えに、認証・CORS・API の穴を自分で埋めることになる。
  • API 呼び出しはセッションを使わない。API キーをブラウザに置かないために、C を選ぶなら 別 Web サーバー（BFF） が事実上必須。まずはリバースプロキシで同一オリジン化。
  • デスクトップは 同じ SPA を Tauri に載せる。ネイティブ HTTP で CORS を回避でき、資格情報はキーチェーンへ。PWA やガワアプリで足りるかを先に確認。

判断の軸

  • Ruby を書ける & Redmine を管理している → B が最短
  • 複数 Redmine / 社外配布 / デスクトップ → C + BFF + Tauri
  • 既存画面を少し良くしたいだけ → A（テーマ + Islands）
  • Redmine REST API — 認証・形式・資源一覧と成熟度・JSONP・User Impersonation
  • Rest_Issues / Attaching files — フィルタ・include・添付の 2 段階アップロード
  • Plugin Tutorial / Hooks / Themes — 方式 A・B の拡張点
  • redmine/redmine — app/controllers/application_controller.rb（find_current_user / api_request? / accept_api_auth）が認証仕様の一次情報
  • rack-cors — Rails に CORS ヘッダーを足す標準的な手段
  • TanStack Query / Vite — SPA 側の中核ツール
  • Tauri v2 / Electron — デスクトップ化。プラグイン（http / notification / updater / deep-link / stronghold）
  • OpenProject — Redmine フォークが Rails + Angular SPA に移行した実例

本スライドは 2026-09-14 時点の公式ドキュメント・ソースに基づく。Redmine の API 仕様は版により差があるため、対象インスタンスの版で /issues.json 等を実際に叩いて確認すること。
