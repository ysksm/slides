結論

推奨案：共通の生成定義を挟む

TypeSpec と手動入力を同じ形式に正規化し、選択した対象だけを生成する。

  • AI：不足情報の抽出、設定案、生成対象、例外実装の提案。
  • 生成器：入力検証、依存解決、差分計画、テンプレート展開。
  • 人：業務ルール・生成範囲・変更差分の判断。

最初は 1 Entity の一覧・詳細画面で、再生成の安全性を確かめる。

前提

要件と、まだ決まっていないこと

Issue で指定済み本資料の仮定 / 要確認
React・Hooks・Redux、TypeSpec実装言語は TypeScript と仮定
ドメイン中心 / ID・VO を厳密に管理ID 形式・採番主体・業務上の不変条件
Repository と DI、テスト用 backendDI ライブラリ・UI 部品・backend 起動方法
IDL が先の場合も、後の場合もある代表機能は Product の一覧・詳細と仮定

「Reduxl」は Redux と解釈。既存アプリの構成は未調査。

検討記録

生成できる情報と、追加で必要な情報

入力確定できること追加定義が必要なこと
TypeSpec / API 契約通信上の型・操作・応答集約境界、ID の意味、業務ルール
ドメイン定義Entity・VO・Repository の責務HTTP 操作との対応、DTO 変換
画面要件表示項目・操作・画面遷移権限、空状態、エラー、状態管理

DTO と Entity は別のモデル。 同じプロパティ名でも同一視しない。

公式資料：Rails generators：引数・オプション・テンプレート

代替案 A

A：小さなテンプレート CLI

scaffold entity Product --id ProductId
scaffold repository Product --methods findById,list
scaffold view Product --screen list
  • 導入が軽い。レイヤーごとの命名規則をすぐ固定できる。
  • 引数が増えると、業務ルールや DTO 対応を表現しにくい。
  • 部分生成の整合性・再生成の所有権は、別途実装が必要。

採用条件：対象が少なく、まず雛形の共通化を検証したい。

代替案 B

B：TypeSpec を中心に拡張

独自 decorator で UI / ドメインの補助情報を付け、独自 emitter がコードを出力する。

  • API 定義との参照関係を一か所で管理しやすい。
  • IDL が未確定だと先行作業が難しい。UI 都合の変更が契約に入り込みやすい。
  • compiler API への追従と、独自拡張の保守が必要。

採用条件：IDL を必須の入口にでき、契約と画面の対応が安定している。

公式資料：TypeSpec Emitters：独自 emitter の仕組み

代替案 C

C：入力経路と生成器を分ける

TypeSpec → OpenAPI → contract adapter ─┐
                                     ├→ Feature Spec → plan → apply
手動入力 / AI の設定案 ────────────────┘
                        ↑
             domain / UI / mapping の補助定義

Feature Spec は、この提案で導入する共通の生成定義。公式の TypeSpec 機能名ではない。

正規化のコストは増えるが、IDL の有無と生成対象を独立に選べる。

推奨構成

レイヤーと依存の方向

Presentation（React / Hooks / Redux）
    ↓ import
Application（UseCase）
    ↓ import
Domain（Entity / VO / Repository interface）
    ↑ implements / import
Infrastructure（HTTP Repository / DTO mapper）

Composition Root → 各レイヤーを組み立てて DI

実行時は UseCase → Repository 実装を呼ぶ。ソースの依存は interface 側へ向ける。

責務

Controller は画面操作の窓口に置く

責務配置例持たせない責務
ユーザー操作 / loading / errorPresentation の Hook / ControllerHTTP DTO の直接操作
ユースケースの実行Application の UseCaseReact / Redux への依存
業務上の判定と状態変更Domain の Entity / VO画面表示や HTTP 通信
Repository 実装・通信変換Infrastructure業務ルールの代行

Rails の Controller をそのまま再現せず、frontend の Hook / Controller と UseCase に役割を分ける。

入力仕様（提案）

Feature Spec の設定例

schemaVersion: 1
feature: product
entity: Product
id: { type: ProductId, value: uuid, assignedBy: server }
valueObjects: { name: ProductName }
contract: { source: openapi, model: ProductDto }
operations: { list: listProducts, detail: getProduct }
mapping: { id: ProductId.parse, name: ProductName.parse }
ui: { screens: [list, detail], state: redux }
targets: [domain, repository-port, application, infra, ui]
existing: {}

構造の説明用 YAML。正式 schema・parser・コマンドは今後実装する。

入力の順序

IDL が未確定でも進められる

段階入力と生成保留するもの
1. 業務要件が先手動定義 → Domain / port / UseCase / fakeHTTP client と DTO mapper
2. 画面を先行fake を DI → 一覧・詳細 UIAPI 接続の完了判定
3. TypeSpec が確定契約を取り込み、明示 mapping を追加破壊的差分は自動適用しない
4. 接続を検証HTTP 実装 → テスト用 backendfake の成功だけで完了扱いしない

各プロパティに由来を記録。契約由来の型と手動の意味定義が競合したら停止する。

生成範囲

部分生成は依存関係を検証する

指定対象必要な依存不足した場合
domainID / VO のルール未決定として入力に戻す
infra契約・port・Entity・mapper必要な定義 / 実装を列挙
applicationDomain / Repository port生成追加または既存参照を要求
uiUseCase / ViewModel / DI既存 binding の指定を要求

plan は「生成するもの」「既存を使うもの」「不足」を分けて表示する。

既存参照は名前だけで判定せず、解決可能性と型の整合性を検査する。

CLI（提案）

plan と apply の契約

# 将来実装する CLI の利用イメージ
scaffold plan --spec product.yaml --targets domain,repository-port
# → plan.json / diff / missing dependencies
scaffold apply --plan plan.json
scaffold verify --spec product.yaml
  • plan：入力・ツール・テンプレート・対象ファイルの hash を保存。
  • apply：同じ hash を再確認し、変更があれば再計画を要求。
  • verify：再生成差分、型、レイヤー依存、指定テストを確認。

AI が考えるのは構造化された引数。任意の shell 文字列を実行しない。

再現性

決定論の対象を明確にする

同じ確定入力とツール一式なら、生成ファイルの bytes が一致する。

  • Node・依存 lockfile・TypeSpec・emitter・formatter・template を固定。
  • 列挙順・改行・文字コードを固定。日時、乱数、絶対パスを出力に含めない。
  • 生成時の外部通信を避け、契約と補助定義をローカル入力にする。
  • CI は固定入力で 2 回生成し、所有ファイル集合と内容を比較する。

AI の提案そのものは非決定的。確定した Feature Spec を保存して再現境界にする。

更新戦略

再生成と手書きコードの所有権

領域方針変更時の挙動
generated/生成器が所有旧 manifest hash と不一致なら停止
domain / UI の雛形最初だけ生成、その後は人が所有再生成では上書きせず差分候補を出す
拡張実装 / DI root手書きの接続点生成側の interface 変更を型検査で検出
不要になった生成ファイルmanifest の所有一覧で管理削除も plan に明示し、手編集なら停止

MVP は手書きファイルへの AST パッチを行わない。途中失敗は元の状態へ戻せる構成にする。

ドメイン

ID と Value Object の厳密さ

  • ID：ProductId と UserId を別の型にし、混用を型検査で拒否する。
  • 実行時：API・URL・保存データの境界で parse。brand の型付けだけで検証済みにしない。
  • 採番：server 採番なら作成入力に ID を要求せず、応答から検証して Entity を復元。
  • VO：ProductName の空文字・長さ等は確定した業務ルールから実装する。

Entity の同一性は ID、VO の等価性は値で扱う。未知の業務ルールを生成器が補完しない。

インフラ

DTO と Entity の変換を境界に置く

unknown HTTP response
  → DTO の実行時検証
  → mapper：ProductId.parse / ProductName.parse
  → Product の復元
  → UseCase の出力 / ViewModel
  → React へ表示

404・通信失敗・契約違反を Repository の結果型へ対応付ける。HTTP status をドメインに流さない。

復元時の検証と、新規作成時の業務判断を区別する。enum 追加・null・日時変換も明示する。

プレゼンテーション

React / Hooks / Redux の生成範囲

生成する定型部分定義から選ぶ部分個別設計する部分
一覧・詳細の画面骨格列、ラベル、表示形式情報設計・複雑な操作
loading / empty / errorUseCase と画面の対応権限と業務フロー
Hook / Controller 接続Redux を使う状態楽観更新と競合解決

Redux にはシリアライズ可能な状態を保存。Entity インスタンスや Repository は DI 側で管理する。

公式資料：Redux Style Guide：非シリアライズ値を state / action に入れない

テスト構成

DI とテスト用 backend

Composition Root
  本番 / 結合テスト → HttpProductRepository(client)
  単体 / 画面試作   → FakeProductRepository(fixtures)
                  ↓
        GetProduct / ListProducts → Hook → UI

同じ port の契約テストを fake と HTTP 実装に適用。HTTP 実装はテスト用 backend に接続して検証する。

seed・reset・URL・起動待機をテスト設定に固定し、ID・日時・失敗応答の fixture を管理する。

受け入れ基準

失敗ケースを完了条件に含める

ケース期待する挙動
同じ定義で再生成差分ゼロ。既存の手書き拡張を保持
UI の依存がない不足を表示し、書き込みゼロ
plan 作成後に手編集apply を拒否。再 plan を要求
ID 混用 / 不正な API 応答型検査 / 実行時検証で検出
DTO の破壊的変更mapping / contract test が失敗
途中の書き込み失敗部分更新を残さず、復旧を検証
実施計画

段階的な実施計画

段階成果物次へ進む条件
P0：規約を確定代表機能・命名・所有権・port 定義既存の 1 機能と対応が取れる
P1：生成の中核schema / validator / plan / apply同一入力差分ゼロ・競合時停止
P2：縦に 1 機能Product 一覧・詳細・DI・backend 接続型 / 契約 / E2E が成功
P3：入口を増やすTypeSpec adapter / AI 設定提案手動入力と同じ生成結果
P4：拡張を判断作成・更新・削除 / schema 移行再生成の運用結果を評価

期間は既存コード調査後に見積もる。最初の完了単位は P2。

評価

PoC で判断すること

  • 一覧・詳細の追加に必要だった手修正を、規約不足と業務固有に分類する。
  • 生成を 2 回行い、生成物の一致と手書きコードの保持を確認する。
  • IDL 先行と後追いの両方で、同じ Feature Spec に到達できるか確認する。
  • 部分生成で依存不足を検出できるか、テスト用 backend で接続が成立するか確認する。

採用判断：再生成の安全性が通ったうえで、同種の 2 機能目でも定型作業が減ること。

生成率や速度改善は未測定。作成・更新・削除への拡張は結果を見て決める。
