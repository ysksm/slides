Playwright 活用方法

テストランナーとしてではなく 「実物のブラウザから資料と安全網を作る道具」 として Playwright を使う。React アプリの画面一覧・実キャプチャ付き画面遷移図・リファクタのデグレを止めるスポット UI テスト・ローカライズ用の UI 資料までを、ヘッドレス実行で回す手順をまとめる。

Summary

結論を先に：4 つの成果物を「1 本の探索コード」から作る

① 画面一覧

React Router の ルート定義を機械的に平坦化して routes.json に。手で数えない、漏れない、差分が取れる。

静的抽出 + 実測クロールの突き合わせで「定義はあるが到達できない画面」も見つかる。

② 実キャプチャ付き遷移図

各画面を決定的にスクリーンショットし、遷移を実測して graph.json に。図は Graphviz でツリー＋補助線として描く。

「ネスト（Outlet）＝縦の木」「横断リンク＝破線の補助線」が読みやすさの鍵。

③ スポット UI テスト

リファクタ前に触る範囲だけの金型（ベースライン）を撮り、後で差分ゼロを確認。全面 E2E を書かずにデグレを止める。

ピクセル・ARIA 構造・振る舞いの 3 層を使い分ける。

④ ローカライズ UI 資料

同じ探索コードを locale だけ変えて回し、言語別キャプチャとはみ出し検出を自動化。翻訳者向けの文脈資料にもなる。

擬似ローカライズで翻訳前に崩れを見つけられる。

共通の土台は 「到達性」×「決定性」×「ヘッドレス実行」。ログイン状態とシードデータで全画面に到達でき、時刻・API・アニメーションを固定できれば、上の 4 つは同じスクリプトの出力先を変えるだけで手に入る。

Pipeline

全体像：ルート定義 → 実測 → 中間 JSON → 成果物

① ルート抽出
routes.tsx / routes.ts
ネストを平坦化してフルパス化。params のプレースホルダを列挙
→routes.json
② 到達 & 実測
Playwright で全画面を巡回
storageState で認証済み・シードデータで安定した中身。遷移とパラメータを記録
→shots/*.png
graph.json
③ 成果物生成
遷移図 / 一覧表 / 資料
Graphviz・Markdown・HTML。CI の artifact として配布

なぜ中間 JSON を挟むか

ブラウザ操作（重い・不安定）と図の生成（軽い・何度でもやり直せる）を分離できる。図のレイアウトを試行錯誤するたびにブラウザを起動しなくて済み、描画ツールも後から差し替えられる。

テストと資料生成を分ける

資料生成は「落ちてはいけない回帰テスト」ではない。playwright.config.ts の別 project（例 capture / l10n-*）にして、CI のジョブも分ける。通常の PR では走らせない。

成果物の置き場所

キャプチャ全量はリポジトリに入れず CI の artifact へ。リポジトリにコミットするのはスポットテストのベースラインだけにすると、差分レビューが実用的な大きさに収まる。

「画面」の単位を決める：ルート × 状態バリアント

URL が同じでも見た目と意味が変わるものがある。ここを決めないと、キャプチャが「代表 1 枚」になって資料としても安全網としても使えない。

ずれの原因扱い
Outlet のネスト（レイアウト / ページ）レイアウトは画面にしない。葉のルートだけを画面にし、ネストは図の親子に使う
データ状態（空 / 1 件 / 大量 / エラー / 読み込み中）状態バリアントとして別画面 ID。API スタブで作り分ける
権限・フィーチャーフラグによる出し分けロール軸（@admin / @viewer）を掛ける
モーダル・ドロワー・タブURL に出るなら画面、出ないなら親画面のバリアント
レスポンシブviewport 軸。資料に必要な幅だけに絞る（例 1280 / 390）

画面 ID の付け方

orders.detail@empty#admin$1280 │ │ │ └ viewport │ │ └ ロール │ └ 状態バリアント └ ルート（ネストを . でつないだ安定キー）

この ID をそのままファイル名（shots/orders.detail@empty.png）とグラフのノード ID、スナップショット名に使う。ID が安定していれば、図・テスト・資料が自動的に同じ語彙で揃う。

最初から全バリアントを撮らない。 まずは各ルートの代表 1 枚（正常系・admin・1280）だけで一覧と遷移図を完成させ、バリアントは「レビューで質問が出た画面」「リファクタで触る画面」から足す。組み合わせ爆発はこの順序で防ぐ。

図の前にデータを決める：graph.json

描画ツールに直接吐かせると、レイアウトを変えたいだけでブラウザを回し直すことになる。「実測の結果」と「図の表現」を JSON で切り離す。

ノードが持つもの

  • id（スライド 5 の画面 ID）・title（h1 や document.title の実測値）
  • route / params / query
  • shot（キャプチャのパス）・parent（Outlet の親）
  • reached（実測で到達できたか）・roles

エッジが持つもの

  • from / to / kind（nest | link | navigate | redirect | submit）
  • trigger（押した要素の名前）・params（受け渡す値）
  • source（static | runtime | both）＝信頼度

この JSON があれば、遷移図のほかに「画面一覧の Markdown 表」「到達できなかった画面のレポート」「パラメータ一覧」も同じ入力から生成できる。

Diagram · 2/3

カスケード構造：メインは木、横断は補助線

画面遷移図が読めなくなる原因は、すべての遷移を同格の矢印で描くこと。階層（Outlet のネストと主動線）だけでトーナメント状の木を作り、それ以外の横断遷移を破線の補助線として重ねると、全体像と細部の両方が読める。

縦＝ネストと主動線

ルートの親子（parent）と「その画面に入る正規の入口」だけを実線で描き、ランクを固定する。トーナメント表と同じで、深さがそのまま「何回クリックして到達するか」になる。

破線＝補助線

系統をまたぐリンク・ショートカット・戻り導線。レイアウトに影響させない（Graphviz なら constraint=false）のが要点。入れても木の形が崩れない。

読み手への効果

「主要導線は木を上から下に追う」「例外は破線だけ見る」と読み方を宣言できる。レビュー・引き継ぎ・障害調査で同じ図を使い回せる。

Refactoring safety · 1/2

リファクタのデグレ防止：スポット UI テスト

考え方： 網羅的な E2E を先に整備するのではなく、これから触る範囲の周囲だけを数本だけ固める。リファクタ（＝振る舞いを変えない変更）なら 「差分ゼロ」が仕様 なので、期待値を書かずにベースラインとの比較でテストが成立する。
層使う道具強い / 弱い
① ピクセルexpect(page).toHaveScreenshot()○ 見た目の崩れを丸ごと検出
△ 環境差に弱く、差分の原因が読みにくい
② 構造expect(loc).toMatchAriaSnapshot()
v1.49+		○ テキスト差分でレビューできる・CSS の微差で落ちない
△ 見た目の崩れは検出しない
③ 振る舞い通常の操作テスト（数本）○ 壊れたら原因が明確
△ 書くコストが最も高い

選び方： CSS / マークアップのリファクタ → ①、コンポーネント分割・状態管理の入れ替え → ②、ルーティングやデータ取得の変更 → ③。迷ったら ② を基本線にし、代表画面だけ ① を足す。

どの画面を選ぶか

  • 変更するコンポーネントを含む画面（遷移図の graph.json から逆引きできる）
  • 共有 UI（ヘッダ・テーブル・フォーム・空状態）を含む代表 1〜2 画面
  • 崩れが業務に直結する画面（フォーム・帳票・列幅）

合計 5〜15 本。毎回全部見る気になる本数に抑えることが継続の条件。

Refactoring safety · 2/2

金型を先に撮る：before / after の回し方

# 0. リファクタ前のコミットで作業ブランチを切る $ git switch -c refactor/orders-table # 1. 金型（ベースライン）を作ってコミットする $ npx playwright test tests/spot --update-snapshots $ git add tests/spot/__screenshots__ && git commit -m "スポットテストの金型を追加" # 2. リファクタする（ここでは金型を更新しない） # 3. 差分ゼロを確認する $ npx playwright test tests/spot ✓ 12 passed ← 振る舞い不変を証明できた ✗ 1 failed ← 退行か、意図した変更か # 4. 落ちたらレポートの expected / actual / diff を見る $ npx playwright show-report # 5. 意図した変更なら金型を更新し、PR の画像差分としてレビューする $ npx playwright test tests/spot --update-snapshots
手順 1 を飛ばさない。 リファクタ後に金型を撮ると、壊れた状態が正解として固定される。「先に撮る」ことだけがこの手法の価値であり、それ以外はすべて後から取り返せる。

落ちたときの読み方

  • 全画面が少しずつ違う → 環境差（OS・フォント・ブラウザ更新）。金型を撮った環境と実行環境を揃える
  • 1 画面だけ大きく違う → 退行の可能性が高い。diff の赤い領域から当たりを付ける
  • 実行ごとに違う → 決定化の漏れ（スライド 8 に戻る）。mask か固定値で潰す

運用の勘どころ

  • しきい値は maxDiffPixelRatio で「面積比」で持つ。threshold（色差）を緩めるより意図が明確
  • 金型は撮った環境の名前で分かれる（プロジェクト名 / プラットフォーム）。CI と同じ Docker で撮る
  • 時間のかかる比較は PR 全部では回さず、refactor ラベルや手動実行に紐づける
  • リファクタが終わったら金型を消してよい。残すのは価値が続くものだけ

Linux の依存install --with-deps chromium。Xvfb はヘッドレスには不要（ヘッドありを CI で回すときだけ）
公式 Docker イメージmcr.microsoft.com/playwright:v<版>-noble。ブラウザとフォント同梱。環境差をなくす決定打
並列と分割workers と --shard=1/3。分割時は blob レポーターで出し merge-reports で 1 つに戻す
キャプチャを撮る環境は 1 つに固定する。 フォントとレンダリングが違えば同じページでも画像は変わり、ローカル macOS で撮った金型は Linux の CI では必ず落ちる。撮影も比較も Docker の中で行う。
# ローカルでも CI と同じイメージで撮る $ docker run --rm -v $PWD:/w -w /w --ipc=host \ mcr.microsoft.com/playwright:v1.56.0-noble \ npx playwright test --project=capture
# .github/workflows/screens.yml jobs: capture: runs-on: ubuntu-latest container: image: mcr.microsoft.com/playwright:v1.56.0-noble options: --ipc=host steps: - uses: actions/checkout@v4 - run: npm ci - run: npx playwright test --project=capture - run: npx tsx scripts/to-dot.ts | dot -Tsvg > screens.svg - uses: actions/upload-artifact@v4 with: { name: screens, path: screens.svg }

--ipc=host は Chromium のメモリ不足クラッシュを防ぐ推奨設定。CI でだけ落ちる失敗の定番原因なので最初から付けておく。イメージのタグは、プロジェクトが使う Playwright と同じバージョンに合わせる。

Localization

ローカライズ時の UI 資料を作る

ほしいもの作り方
言語別キャプチャprojects を言語ごとに定義して test.use({ locale, timezoneId })。同じ探索コードを --project=l10n-de で回すだけ
はみ出し検出各画面で scrollWidth > clientWidth の要素を走査。翻訳が長い言語（ドイツ語・フランス語）で崩れる箇所が機械的に出る
翻訳前の予防擬似ローカライズ：翻訳リソースを page.route で差し替え、文字列を 1.5 倍に伸ばす（[Ｓｅｔｔｉｎｇｓ～～～]）。翻訳を待たずにレイアウト耐性を検証できる
翻訳者向け文脈資料画面キャプチャ + その画面に出ている文字列 + i18n キーを 1 枚の HTML に。「どこに出る文言か」が分かるだけで訳の質が変わる
RTLlocale: 'ar-EG' と dir="rtl" でミラーリングの崩れを確認。アイコンの向き・余白の左右が典型的な落とし穴
形式差日付・数値・通貨は timezoneId を固定した上で言語ごとに比較。桁区切りと通貨記号の位置が変わる
言語軸は 画面数 × 言語数 で一気に増える。全画面 × 全言語ではなく、「文字量の多い画面 × 最長言語 1 つ」を常時、残りはリリース前に 1 回、という頻度の設計にする。
// playwright.config.ts projects: [ { name: 'l10n-ja', use: { locale: 'ja-JP', timezoneId: 'Asia/Tokyo' } }, { name: 'l10n-de', use: { locale: 'de-DE', timezoneId: 'Europe/Berlin' } }, { name: 'l10n-ar', use: { locale: 'ar-EG' } }, ] // はみ出し検出（キャプチャの直前に実行） const over = await page.evaluate(() => [...document.querySelectorAll('*')] .filter(el => el.scrollWidth > el.clientWidth + 1) .map(el => ({ cls: el.className, text: el.textContent?.slice(0, 40), px: el.scrollWidth - el.clientWidth }))); expect.soft(over, 'はみ出し').toEqual([]); // 擬似ローカライズ（翻訳を待たずに崩れを出す） await page.route('**/locales/*.json', async r => { const j = await (await r.fetch()).json(); for (const k in j) j[k] = `[${j[k]}${'～'.repeat(j[k].length / 2)}]`; await r.fulfill({ json: j }); });

Best practices

ベストプラクティス：資料を作る使い方でも外せない基本

ロケータと待機

  • 役割ベース（getByRole / getByLabel）を第一選択に。CSS セレクタ依存はリファクタで真っ先に壊れる
  • どうしても必要なら data-testid。キャプチャ用のマスク対象にも同じ属性を使うと一石二鳥
  • waitForTimeout を書かない。期待（expect）で待つのが自動待機の正しい使い方
  • networkidle に依存しない。ポーリングや常時接続があると永遠に来ない

テストの作り

  • 1 テスト 1 目的・テスト間で状態を共有しない。並列実行と再実行が安全になる
  • 認証は storageState を作って使い回す。毎回ログイン画面を通らない
  • Page Object は薄く。ロケータの置き場に留め、アサーションはテスト側に書く
  • trace: 'on-first-retry'。失敗したときだけ Trace Viewer で操作を巻き戻せる

資料生成ならではの作法

  • テストと資料生成を別 project に分ける。資料の失敗で PR を止めない
  • 生成物にコミットハッシュと日時を焼き込む。古い図が独り歩きするのを防ぐ
  • キャプチャ全量はコミットしない（artifact へ）。コミットするのはベースラインだけ
  • 入力（routes.json / params.json）はコミットする。差分が仕様変更の記録になる
  • MCP や codegen は探索に使い、成果物はコードに固定する
「落ちるテスト」と「作る道具」を混ぜないこと が、この使い方を続けられるかどうかの分かれ目。資料生成は壊れても業務は止まらないが、CI を赤くし続ければ必ず無視されるようになる。ジョブ・レポート・通知先をはじめから分けておく。

Roadmap

進め方：5 ステップで立ち上げる

1
ルート定義を 1 か所に半日
ルート定義を src/routes.tsx に集約して export し、scripts/dump-routes.ts で routes.json を吐く。この時点で「画面一覧」という成果物が 1 つ完成する。CI で差分を見れば、以降のルート追加も自動的に追える。
2
到達性を作る1〜2 日
認証（storageState）とシードデータ、パラメータ辞書（fixtures/params.json）を整える。ここが最も泥臭く、最も効く。全画面に到達できること自体が調査結果で、到達できない画面のリストがそのまま課題一覧になる。
3
決定化してキャプチャ1 日
時刻・API・アニメーション・フォントを固定し（スライド 8）、Docker 上で全画面を撮る。遷移とパラメータの実測を同じ実行で記録し、shots/ と graph.json を artifact に上げる。
4
図と資料を生成1 日
graph.json → Graphviz で遷移図（メイン＝木、補助線＝破線）。同じ JSON から画面一覧の Markdown 表と、到達できなかった画面のレポートも出す。ブラウザを回さずに図だけ作り直せる状態にしておく。
5
安全網と言語軸を足す継続
リファクタの前にスポットテストの金型を撮る運用（スライド 13）を回し始める。ローカライズが必要になったら projects に locale を足すだけで言語別資料とはみ出し検出が手に入る。1〜4 の投資がそのまま再利用されるのがこの構成の狙い。

Wrap-up

まとめと参考資料

要点

  • Playwright はテストの道具である前に、実物のブラウザから事実を取り出す道具。画面一覧・遷移図・ローカライズ資料は、同じ探索コードの出力先を変えただけで手に入る。
  • 土台は 到達性（認証・シード・パラメータ辞書）と 決定性（時刻・API・アニメ・フォント）。ここを先に作らないと、どの成果物も信用されない。
  • 図は メイン＝ネストと主動線の木、補助線＝横断遷移の破線。レイアウトに影響しない補助線（constraint=false）が可読性を守る。
  • リファクタのデグレ防止は「先に金型を撮る」だけで成立する。ピクセル・ARIA 構造・振る舞いの 3 層を対象に応じて使い分ける。
  • 撮影環境は Docker で固定する。環境差はスナップショット運用が破綻する最大の原因。
最初の一歩は「全画面を撮るスクリプトを 1 本書く」こと。動くキャプチャの山ができた時点で、残りの成果物はすべてその加工になる。
  • Screenshots — fullPage / mask / animations / caret などの撮影オプション
  • Visual comparisons — toHaveScreenshot と --update-snapshots、しきい値
  • Aria snapshots — 構造をテキストで固定する（v1.49+）
  • Emulation — locale / timezoneId / viewport / colorScheme
  • Clock — 時刻の固定（v1.45+）
  • Mock APIs — page.route でのスタブと改変
  • Browsers — Chromium Headless Shell と channel: 'chromium'
  • Docker / CI — 公式イメージ・--ipc=host・シャーディング
  • Best Practices — ロケータ・テスト分離・待機の指針
  • React Router — ルート定義・Outlet・loader / action・useSearchParams
  • Graphviz attributes — rank / constraint / image

本スライドは 2026-09-15 時点の公式ドキュメントに基づく。バージョン依存の挙動（ヘッドレスの実装・スナップショット関連のオプション）は各リンク先で最新を確認のこと。
