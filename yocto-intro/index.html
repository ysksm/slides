Summary

結論を先に：押さえるのは 3 つだけ

① Yocto は「ディストロを作る工場」 考え方

Yocto は OS イメージそのものではなく、ソースから OS を組み立てるビルドシステム。bitbake が レシピ（何をどう作るか）を レイヤー 単位で読み、クロスコンパイルして root filesystem とブートイメージを出力する。

Raspberry Pi OS のような「配られた OS」を使うのではなく、必要な物だけを載せた OS を毎回生成する。

② ビルドホストは Linux 必須 環境

macOS では直接ビルドできない（大文字小文字を区別しないファイルシステム・GNU ツール前提）。M4 Mac 上の VMware Fusion に Ubuntu を立てて、その中でビルドするのが現実解。Fusion on Apple Silicon の VM は arm64 だが、Yocto はクロスコンパイルなので x86_64 向けイメージも作れる。

要るのは CPU コア・メモリ・そして何より ディスク（100〜250 GB）。

③ 作り分けは 2 変数 + レイヤー 応用

ターゲットの違いは MACHINE（Raspberry Pi / x86_64 …）、見た目と機能の違いは イメージレシピ（GUI なし / Weston / ルーター用）。BSP や機能はレイヤーを bblayers.conf に足すだけで増える。

MACHINE を変えても sstate-cache と DL_DIR は共有 できるので、2 台目以降は劇的に速い。

本スライドの流れ：仕組み（3–5）→ M4 Mac + Fusion の環境構築（6–9）→ イメージの作り分け（10–14）→ 実務の型（15–19）。

What it is

Yocto Project とは何か — Poky・BitBake・OpenEmbedded

  • Yocto Project：Linux Foundation 傘下の、組み込み向け Linux ディストリビューションを作るためのツール・メタデータ・ドキュメントの集合体。2010 年開始。
  • BitBake：タスク実行エンジン。.bb / .bbappend / .bbclass / .conf に書かれた依存関係を解決し、数千タスクを並列実行する。
  • OpenEmbedded-Core (oe-core)：BitBake が読む基礎レシピ群。Yocto と OpenEmbedded が共同保守している共有レイヤー。
  • Poky：上記をまとめたリファレンス実装。bitbake + oe-core + meta-poky（参照ディストロ）+ meta-yocto-bsp（参照 BSP）。入門はここから始める。
  • リリースは年 2 回（4 月・10 月）。長期利用には LTS（例：5.0 “Scarthgap”、2024-04 リリース）を選ぶ。コードネームでブランチを切るのが慣習。

「ディストロを作る」とは？

Debian / Raspberry Pi OS はできあがった OSを配る。Yocto は「どの CPU 向けに、どのパッケージを、どの設定で、どのライセンスで」を宣言すると、その通りの OS を毎回再現可能に生成する。だから不要な物が入らないし、製品ごとに違う OS を量産できる。

meta-myproduct自作レイヤー：製品固有の設定・アプリ・イメージレシピ
meta-networkingルーター機能（nftables / hostapd / dnsmasq …）
meta-oe, meta-python …OpenEmbedded の追加パッケージ群
meta-raspberrypiBSP：カーネル・ブートローダー・MACHINE 定義
meta-intelBSP：x86_64（NUC 等）向け
meta-poky参照ディストロ定義（DISTRO = "poky"）
meta (oe-core)基礎レシピ・クラス・ツールチェーン
bitbakeタスク実行エンジン本体

レイヤーは上書き可能な積み木。上の層が .bbappend で下の層のレシピを部分的に書き換えられるので、上流を fork せずに製品差分を足せる。これが Yocto の最大の設計思想。

1 レシピあたりの標準タスク（抜粋）

Build host · ①

なぜ macOS では直接ビルドできないのか

macOS が落ちる主な理由

  • ファイルシステムが大文字小文字を区別しない（APFS の既定）。Makefile と makefile、linux/String.h 等が衝突してソース展開の時点で壊れる。
  • GNU ツール前提：sed・tar・find・readlink などが BSD 版で挙動が違う。ホストツールのビルドも glibc/Linux ヘッダを前提にしている。
  • pseudo（fakeroot 相当）が Linux 固有の仕組みで root 権限なしに rootfs の所有者・パーミッションを再現している。macOS には移植されていない。
  • 公式のサポート対象ホストは Linux ディストリビューションのみ（Ubuntu / Debian / Fedora / AlmaLinux / openSUSE など）。それ以外は「動いたらラッキー」の世界。

大文字小文字を区別する APFS ボリュームを切っても、上の 2 番目・3 番目が残るため実用にならない。素直に Linux を用意する。

M4 Mac での選択肢

方法評価
VMware Fusion + Ubuntu本命。仮想ディスクを大きく取れ、スナップショットで失敗から戻せる。GUI も使えるので runqemu の画面確認が楽
UTM / Parallels同等。要は「arm64 Linux VM が立てば何でもよい」
Docker (CROPS 等)手軽だが macOS の Docker も結局 Linux VM。bind mount 上にビルドすると致命的に遅いので VM 内ボリュームに置く必要があり、結局 VM 管理が要る
Linux マシン / クラウド最速。CI や共有 sstate を置くなら結局ここに行き着く

Apple Silicon ならではの前提

Fusion on Apple Silicon の VM は aarch64 のみ（x86 は動かせない）。しかし Yocto は元々クロスコンパイルなので、aarch64 ホストから x86_64 のイメージを作ることは普通にできる。影響するのは「作った x86_64 バイナリをその場で実行できない」点だけ（後述）。

Build host · ②

VMware Fusion に Ubuntu を立てる — スペックと落とし穴

VM の推奨スペック

OSUbuntu arm64 LTS（24.04 / 22.04）
CPU物理コアの 1/2〜3/4（M4 なら 6〜8 vCPU）。Yocto は全コアを使い切る
メモリ最低 8 GB、16 GB 以上推奨。リンク時に数 GB 食うことがある
ディスク200 GB 以上を強く推奨（最小構成でも 100 GB 弱は消える）
スワップ8 GB 程度。OOM で数時間のビルドが飛ぶのを防ぐ

踏みやすい落とし穴

  • 共有フォルダ（HGFS）の上でビルドしない。 macOS 側は大文字小文字を区別せず、しかも遅い。~/yocto は必ずVM の仮想ディスク内へ。
  • ソース取得のため VM からインターネットに出られること（NAT で可）。プロキシがあるなら ~/.bashrc と local.conf の両方に設定。
  • ディスクは後から拡張できるがゲスト側の LV 拡張も要る。最初から大きく取る。長時間ビルド中は caffeinate -i で Mac のスリープを抑止。

Configuration

local.conf と bblayers.conf — 最初に触る 2 ファイル

# build/conf/local.conf MACHINE ?= "raspberrypi5" # ★ 全ビルドで共有 = 2 台目以降が速い DL_DIR ?= "${TOPDIR}/../downloads" SSTATE_DIR ?= "${TOPDIR}/../sstate-cache" # 並列度：コア数に合わせる BB_NUMBER_THREADS ?= "8" PARALLEL_MAKE ?= "-j 8" # ディスク節約：成功したレシピの work/ を消す INHERIT += "rm_work" # 開発用の追加（本番イメージでは外す） EXTRA_IMAGE_FEATURES ?= "debug-tweaks ssh-server-openssh" # パッケージを足す（先頭の空白が必須） IMAGE_INSTALL:append = " vim htop nano" # 出力形式 IMAGE_FSTYPES ?= "wic wic.bz2 wic.bmap tar.bz2"
# build/conf/bblayers.conf（編集はコマンドで） $ bitbake-layers add-layer ../meta-raspberrypi $ bitbake-layers show-layers

覚えておきたい変数の作法

VAR = "x"即時代入。強制的に上書き
VAR ?= "x"未設定なら設定（デフォルト値）
VAR ??= "x"より弱いデフォルト。最後に評価される
VAR:append = " x"末尾に追記。先頭に空白が要る
VAR:remove = "x"要素を取り除く
VAR:rpi = "x"OVERRIDES による条件分岐（MACHINE 名など）

旧記法 VAR_append は 3.4 以降 VAR:append に変更済み。古い記事のコピペは要注意。

local.conf に書いてよいもの・いけないもの

  • その人・そのマシン固有の設定：並列度、キャッシュのパス、一時的な実験
  • 製品の構成：入れるパッケージ、DISTRO_FEATURES、イメージの中身。これらは自作レイヤーのイメージレシピと distro conf に書く。local.conf は git 管理外になりがちで、再現性が失われる

目安：「他人の環境でも同じ物ができてほしい」設定はレイヤーへ。kas のような設定管理ツールを使うと、この分離が自然に守られる。

Images · ① CUI

GUI なしの Linux — 標準イメージの選び方

イメージレシピ中身目安
core-image-minimal起動してシェルが出るだけの最小構成。BusyBox + 必要最低限〜十数 MB
core-image-baseminimal + ハードウェアサポート一式（MACHINE_ESSENTIAL_*、無線・USB 等）。実機の入門はここから数十 MB
core-image-full-cmdlineBusyBox ではなくフル機能の CUI ユーティリティ群。使い慣れたコマンドが揃う百数十 MB
core-image-tiny-initramfsRAM 上で完結する超小型 initramfs数 MB

どれを選ぶか

  • まず動かすなら core-image-base、製品の土台なら core-image-minimal から足していく。
  • 「デバッグしやすさ」は EXTRA_IMAGE_FEATURES で足す：ssh-server-openssh（SSH）、debug-tweaks（root パスワードなし＝開発専用）、tools-debug（gdb 等）、package-management（実機で dnf / opkg を使う）。
  • 製品では debug-tweaks を必ず外し、read-only-rootfs や IMAGE_FEATURES を明示する。
# 自作イメージレシピ（推奨） # meta-myproduct/recipes-core/images/ # my-image-cui.bb SUMMARY = "CUI base image for my product" LICENSE = "MIT" require recipes-core/images/core-image-minimal.bb IMAGE_FEATURES += "ssh-server-openssh" IMAGE_INSTALL:append = " \ openssh-sftp-server \ systemd-analyze \ curl \ tzdata \ my-app \ " # root パスワードを設定（debug-tweaks の代わり） inherit extrausers EXTRA_USERS_PARAMS = "usermod -P secret root;" $ bitbake my-image-cui

require で既存イメージを取り込み差分だけ書くのが定石。IMAGE_INSTALL:append の各行末の \ と、閉じ引用符の前の空白に注意（よくある構文エラー源）。

Images · ② GUI

GUI ありの Linux — Wayland / X11 / Qt

core-image-weston 既定はこれ

Wayland コンポジタ Weston を載せた最小デスクトップ。現在の組み込み GUI の主流。X サーバーを持たないぶん軽く、GPU のダイレクトスキャンアウトと相性がよい。

  • 必要 DISTRO_FEATURES：wayland（poky では既定で有効）
  • GPU ドライバ（Raspberry Pi なら VC4/V3D の DRM ドライバ）が要る
  • キオスク端末・計器パネルの土台に向く

core-image-sato X11 の参照

Matchbox ウィンドウマネージャによるモバイル風 X11 デスクトップ。Yocto の伝統的なデモイメージで、ドキュメントの例に頻出。

  • 必要 DISTRO_FEATURES：x11
  • ビルドは重く時間もかかる（初回は数時間規模）
  • 新規案件で X11 を選ぶ理由は減っている。動作確認・学習用と割り切る

アプリ用フレームワーク 実務

実際の製品 UI は「デスクトップ」ではなく単一アプリのフルスクリーン表示にすることが多い。

  • meta-qt6：Qt 6 / QML。組み込み GUI の定番。qtbase を Weston 上や eglfs で直接描画
  • meta-browser / Chromium：Web 技術で UI を作りキオスク起動
  • LVGL・GTK：軽量 GUI やフレームバッファ直描き
  • デスクトップ環境（GNOME 等）を載せる選択肢もあるが、Yocto の利点（小ささ・再現性）とは方向が逆
# GUI ありイメージをビルドする $ bitbake core-image-weston # local.conf で機能を明示したい場合 DISTRO_FEATURES:append = " wayland opengl" # Raspberry Pi で VC4 グラフィックスを有効化（meta-raspberrypi） MACHINE_FEATURES:append = " vc4graphics"

GUI を足す前に考えること

GUI はビルド時間・イメージサイズ・依存の複雑さを一段跳ね上げる（グラフィックススタック、フォント、入力、フレームワーク）。まず CUI イメージで実機が安定して起動することを確認し、そのうえで GUI を重ねるのが事故が少ない。

Raspberry Pi 固有の設定（local.conf）

ENABLE_UART = "1"シリアルコンソールを有効化。初回の起動確認に必須級
RPI_USE_U_BOOT = "1"U-Boot 経由で起動（A/B 更新などで使う）
MACHINE_FEATURES:append
 = " vc4graphics"		VC4/V3D の DRM ドライバを使う（Wayland/Weston 用）

config.txt への追記は RPI_EXTRA_CONFIG や .bbappend 経由で行い、焼いた後の手編集に頼らない（再現性のため）。

ブートの流れ：Pi のファーム（EEPROM）→ config.txt → カーネル + DTB → rootfs。.wic は FAT のブート領域と ext4 の rootfs を 1 ファイルに収めたもの。

Target · ② x86_64

Intel NUC など x86_64 向けイメージ

2 つの選択肢

MACHINE提供レイヤー用途
genericx86-64meta-yocto-bsp
(Poky 同梱)		汎用 PC / NUC 向け。追加レイヤー不要で試せるので最初はこれ
intel-corei7-64meta-intelIntel 公式 BSP。世代別の最適化、グラフィックス・メディア系のファームやドライバ（linux-intel カーネル）が揃う

meta-intel には intel-skylake-64 など世代別の MACHINE もあるが、汎用性のある intel-corei7-64 が事実上の標準。対応一覧はレイヤーの README を参照。

ARM ホストから x86_64 を作るときの注意

  • ビルドは問題なくできる。 Yocto は常にクロスコンパイルで、ツールチェーンも自前で作るため。
  • runqemu qemux86-64 は KVM が使えず遅い。 aarch64 ホストでは命令エミュレーションになる。動作確認は実機で行う。
  • uninative（ホスト glibc 差を吸収する仕組み）や sstate ミラーはホストアーキ別。x86_64 の共有 sstate を aarch64 VM では使えない＝毎回フルビルドになりやすい。
  • x86_64 ホスト（Linux マシン / クラウド）を用意できるなら、x86_64 ターゲットはそちらで回すほうが総合的に速い。
# genericx86-64 で作る（Poky だけで完結） $ source poky/oe-init-build-env build-x86 $ echo 'MACHINE = "genericx86-64"' >> conf/local.conf $ bitbake core-image-base # meta-intel を使う場合 $ git clone -b scarthgap git://git.yoctoproject.org/meta-intel $ bitbake-layers add-layer ../meta-intel $ echo 'MACHINE = "intel-corei7-64"' >> conf/local.conf $ bitbake core-image-base # USB メモリに書いて NUC で起動（UEFI） $ sudo bmaptool copy core-image-base-*.wic /dev/sdX

x86_64 ならではの点

  • 起動は UEFI + GRUB（または systemd-boot）。.wic に EFI システムパーティションが含まれる。NUC の BIOS で Secure Boot を切るか、署名の仕組みを用意する。
  • デバイスツリーは使わず ACPI でハードを認識するため、ARM 系より「挿せば動く」寄り。
  • ディスク・NIC・Wi-Fi のファームウェア（linux-firmware-*）の追加が必要になりがち。
  • 実機で試す前に、同じイメージを Fusion の x86 VM… は Apple Silicon では不可。Intel Mac や別 PC がある場合のみ有効な手。

ルーター用 Linux を作る

meta-networking は meta-openembedded の一部。meta-oe / meta-python も併せて登録する。

ルーターだからこそ効く設定

  • IMAGE_FEATURES += "read-only-rootfs"：rootfs を読み取り専用にし、設定は別パーティションや overlayfs へ逃がす。停電での破損に強い。
  • 攻撃面を削る：debug-tweaks を外し、パッケージマネージャを入れず、不要なサービスを止める。
  • 更新の仕組みを先に決める：A/B 二面更新（RAUC / SWUpdate / Mender）。ネットワーク機器は文鎮化＝現地復旧になる。
# meta-myrouter/recipes-core/images/router-image.bb SUMMARY = "Minimal router image" LICENSE = "MIT" require recipes-core/images/core-image-minimal.bb IMAGE_FEATURES += "read-only-rootfs" IMAGE_INSTALL:append = " \ kernel-modules \ nftables dnsmasq hostapd wpa-supplicant \ iproute2 iw ethtool tcpdump \ wireguard-tools openssh-sshd \ my-router-config \ " # カーネルに netfilter/bridge/VLAN を確実に入れる # → meta-myrouter/recipes-kernel/linux/linux-yocto_%.bbappend # SRC_URI += "file://router.cfg"（fragment で config 追加）

ハード面：Raspberry Pi は NIC が 1 本なので USB Ethernet か VLAN 対応スイッチを併用する。NIC を 2 本以上持てる x86_64 の小型機（NUC 等）のほうがルーター用途には素直。

既製品との比較：家庭用ルーターが欲しいだけなら OpenWrt が近道。Yocto を選ぶのは「同じ基盤で自社製品を複数機種ぶん作りたい」ときの判断。

Multi-target

1 つの作業ツリーで 4 機種を回す

原則：DL_DIR と SSTATE_DIR は共有、TMPDIR は分ける

ダウンロード済みソースとsstate キャッシュは機種をまたいで再利用できる（アーキ非依存のタスクや、同じ aarch64 同士の成果物が効く）。一方 tmp/ は MACHINE ごとに作り直されるため、ビルドディレクトリを機種別に分けると切り替えが一瞬で済む。

# 機種ごとにビルドディレクトリを分ける $ source poky/oe-init-build-env build-rpi # raspberrypi5 $ source poky/oe-init-build-env build-x86 # genericx86-64 $ source poky/oe-init-build-env build-router# router-image # それぞれの conf/local.conf で共通行を site.conf に括り出す # build-*/conf/site.conf（または BB_ENV で共有） DL_DIR = "/home/user/yocto/downloads" SSTATE_DIR = "/home/user/yocto/sstate-cache" # 1 つのビルドディレクトリで切り替えることも可能 $ MACHINE=genericx86-64 bitbake core-image-base

後者は tmp/ が上書きされるため、直前の成果物が消える点に注意。CI や複数機種の日常開発ではビルドディレクトリ分割が扱いやすい。

構成をコード化する — kas

「どのレイヤーをどのリビジョンで、どの local.conf で」を YAML 1 枚に固定するツール。新しいマシンでも kas build rpi5.yml だけで同じ物が作れる。手順書と local.conf の口伝から卒業できる。

同種のものに Google の repo ツールや、各社独自の init スクリプトがある。チーム開発では早めに導入したい。

Customize · ①

自作レイヤーとレシピを作る

# レイヤーの雛形を作って登録する $ bitbake-layers create-layer ../meta-myproduct $ bitbake-layers add-layer ../meta-myproduct ../meta-myproduct/ ├── conf/layer.conf # 優先度・対象リリース ├── COPYING.MIT / README └── recipes-example/example/example_0.1.bb # 既存レシピに差分を当てる（.bbappend） # meta-myproduct/recipes-kernel/linux/linux-yocto_%.bbappend FILESEXTRAPATHS:prepend := "${THISDIR}/${PN}:" SRC_URI += "file://my-feature.cfg file://0001-fix.patch" # 自作アプリのレシピを自動生成する $ recipetool create -o myapp_1.0.bb https://example.com/myapp-1.0.tar.gz $ devtool add myapp https://github.com/me/myapp.git

layer.conf の LAYERSERIES_COMPAT_* に対象リリース名（scarthgap 等）が入っていないと、そのリリースで警告・エラーになる。他人のレイヤーを新リリースで使うときの定番の詰まりどころ。

# 最小のレシピ（CMake のアプリ） SUMMARY = "My application" LICENSE = "MIT" LIC_FILES_CHKSUM = "file://LICENSE;md5=xxxxxxxx…" SRC_URI = "git://github.com/me/myapp.git;branch=main;protocol=https" SRCREV = "a1b2c3d4…" # ★ 固定する（再現性） S = "${WORKDIR}/git" DEPENDS = "zlib openssl" # ビルド時の依存 RDEPENDS:${PN} = "bash" # 実行時の依存 inherit cmake systemd SYSTEMD_SERVICE:${PN} = "myapp.service"

レシピを書くときの原則

  • SRCREV は必ず固定。${AUTOREV} は再現性を壊す（開発中の一時利用に留める）。
  • LICENSE と LIC_FILES_CHKSUM は必須。ライセンス文が変わると検査で落ちるが、これは「上流のライセンスが変わった」検知機構でもある。
  • DEPENDS（ビルド時）と RDEPENDS（実行時）は別物。実機で「コマンドはあるのにライブラリが無い」の多くは RDEPENDS 漏れ。
  • 上流をいじりたくなったら fork ではなく .bbappend + パッチ。更新時の差分が追える。

Customize · ②

日々の開発ループ — devtool と SDK

アプリを 1 行直すたびに bitbake image は重すぎる

devtool は「レシピの外の作業ツリー」を作り、普通の git リポジトリとして編集 → 差分ビルド → 実機へ配置のループを回せるようにする。変更は最後にパッチとしてレイヤーへ書き戻す。

$ devtool modify myapp # workspace/sources/myapp を作る $ vim workspace/sources/myapp/src/main.c $ devtool build myapp # そのレシピだけ再ビルド # 動いている実機へ直接配置（SSH） $ devtool deploy-target myapp root@192.168.1.50 $ devtool undeploy-target myapp root@192.168.1.50 # 変更をレイヤーに書き戻す（パッチとして生成される） $ devtool finish myapp ../meta-myproduct # 上流の新バージョンへ追従する $ devtool upgrade myapp -V 1.2.0

SDK：アプリ開発者に Yocto を触らせない

SDK を配れば、アプリ担当はクロスツールチェーンとターゲットのヘッダ・ライブラリ一式だけで開発できる。Yocto の知識もビルドマシンも要らない。

# SDK を作る $ bitbake core-image-base -c populate_sdk # 配布先で（Yocto 不要） $ ./poky-…-toolchain-5.0.sh $ source /opt/poky/5.0/environment-setup-… $ $CC main.c -o myapp

-c populate_sdk_ext は devtool 込みの拡張 SDK。

デバッグに効く小技

  • bitbake -e <recipe> | less — 変数の最終値と設定元が全部見える。迷ったらまずこれ
  • bitbake -c devshell <recipe> — ビルド環境のシェルに入って手で make を試す
  • oe-pkgdata-util find-path /usr/bin/foo — ファイルの出自パッケージを逆引き
  • buildhistory を有効化 — イメージ間の差分を git で追える

Reality check

時間とディスクの現実解

覚悟すべき数字 初回

初回ビルドcore-image-minimal で 1〜2 時間、core-image-weston / sato なら数時間（8 コア級）
ダウンロード数 GB〜十数 GB。回線が細いと律速になる
ディスク1 ビルドツリーで 50〜120 GB。tmp/work が大半
2 回目以降sstate が効けば数分。変更した 1 レシピとその依存だけが再実行される

数字は構成・ホスト性能で大きく変わる目安。「初回は寝ている間に回す」前提で計画する。

速くする 効く順

  • SSTATE_DIR / DL_DIR の共有（機種間・チーム間・CI 間）。最も効く。
  • コアとメモリ：BB_NUMBER_THREADS（同時タスク数）と PARALLEL_MAKE（1 タスク内の make -j）。掛け算になるので上げすぎると OOM。
  • 不要なものを作らない：GUI・SDK・不要な IMAGE_FSTYPES を外す。core-image-sato の常用をやめるだけで大きい。
  • ハッシュ等価性（BB_HASHSERVE）：無関係な変更による再ビルドの連鎖を抑える。
  • ビルド専用マシン：最終的にはこれが一番効く。VM は開発・実験、重いビルドは Linux 実機 / クラウドへ。

ディスクを守る VM 必須

  • INHERIT += "rm_work"：成功したレシピの tmp/work を都度削除。数十 GB 単位で効く。代わりにそのレシピのデバッグはしづらくなる。
  • sstate-cache-management.sh で古い sstate を整理。
  • tmp/ は消してよい（sstate があれば復元できる）。空き容量が尽きたらまずここ。
  • VM の仮想ディスクは「ゲストで消してもホストのファイルは縮まない」。定期的に fstrim + Fusion のディスク圧縮を。
  • ビルド中にディスクが尽きると中途半端な状態で失敗する。 BB_DISKMON_DIRS で閾値を切って停止させると安全。

実務の落としどころ：M4 Mac + Fusion の VM は「学習と構成の試行錯誤」、CI か Linux 実機を「正のビルド」にして sstate を共有する。ローカルで全部やろうとすると、ディスクと待ち時間の戦いになる。

Pitfalls

初心者が必ず踏むところ

症状原因と対処
レイヤーのブランチ不一致Poky が scarthgap なのに BSP が master 等。LAYERSERIES_COMPAT の警告を無視しない。全レイヤーを同じコードネームのブランチで揃える
:append の空白忘れIMAGE_INSTALL:append = "vim" は直前の語と連結して壊れる。必ず " vim"
古い記法のコピペVAR_append / do_install_append() は 3.4 以降 : 記法。ネット記事は年代を確認
ディスク枯渇で謎の失敗途中で空きが尽きるとエラーが原因不明に見える。df -h を先に疑う
共有フォルダ上でビルド大文字小文字を区別しない／遅い。VM の内蔵ディスクへ移す
do_fetch が失敗し続ける上流の消滅・プロキシ。DL_DIR を共有し、製品ではソースミラー（SOURCE_MIRROR_URL / PREMIRRORS）を自前で持つ

考え方でハマるところ

  • 実機に SSH して直したものは、次のビルドで消える。 変更は必ずレシピ・レイヤーに戻す。「イメージが唯一の真実」に慣れるまでが山。
  • local.conf に何でも書いてしまう。 動くが再現しない。製品構成は自作レイヤーへ。
  • エラーメッセージが長い。 実際に読むのは ERROR: の行と、示された log.do_compile のファイルだけ。まずそこを開く。
  • 何でも自作しようとする。 目的のパッケージは大抵 meta-openembedded にある。bitbake-layers show-recipes や layers.openembedded.org で先に探す。

製品化で必ず来る宿題

  • ソフトウェア更新：RAUC / SWUpdate / Mender による A/B 更新。後付けはパーティション設計からやり直しになるので最初に決める
  • ライセンスコンプライアンス：tmp/deploy/licenses/ と archiver クラスでソース開示の準備
  • CVE 対応：cve-check クラスで既知脆弱性を検出し、LTS ブランチの更新に追従する運用を決める
  • 再現ビルド：レイヤーのリビジョン固定（kas）+ CI + sstate ミラー

Wrap-up

まとめと参考資料

要点

  • Yocto はディストロを作る工場。レシピ × レイヤー × MACHINE の組み合わせで、必要な物だけの OS を再現可能に生成する。
  • M4 Mac では VMware Fusion の arm64 Linux VM の中でビルドする。共有フォルダを避け、ディスクは 200 GB 取る。
  • Raspberry Pi・ルーター・Intel NUC の違いは、レイヤー・MACHINE・イメージレシピの 3 点だけ。手順は共通。
  • GUI なし → core-image-base、GUI あり → core-image-weston。まず CUI で起動を確認してから GUI を重ねる。
  • 実機で手直ししない。変更は必ずレイヤーへ戻す。再現性こそが Yocto を使う理由。
