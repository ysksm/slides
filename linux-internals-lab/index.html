Summary

結論を先に：Linux がやっていることは「多重化・隔離・階層化」の 3 つ

多重化 CPU · デバイス

物理的に 4 個しかない CPU を、数百のプロセスに「自分専用」に見せる。スケジューラが数ミリ秒ごとに実行するプロセスを入れ替える（実験: 1 CPU に 2 プロセスで経過時間が 2 倍）。デバイスも同じで、1 本のディスクへの I/O をブロック層が並べ替えて渡す。

1 CPU を 2 プロセスで共有経過 2.5 s → 4.2 s
nice 19 の相手がいるときほぼ独占
強制的な交代約 120 回/秒

→ スライド 6–7, 15

隔離 メモリ · 名前空間

各プロセスは自分だけのアドレス空間を持つ（仮想メモリ）。同じアドレス 0x1000 でも中身は別。この「見せかけの独立」を、プロセス ID・マウント・ネットワークにも広げたものが namespace、つまりコンテナ。CPU を丸ごと見せかけると仮想マシンになる。

1 GiB を mmap しただけRSS +0.4 MiB
256 MiB の親を fork物理 +0 MiB
子が全ページに書く物理 +256 MiB

→ スライド 8–9, 16–17

階層化 記憶 · ファイル

速いが小さいレジスタ・キャッシュと、遅いが大きいディスクの間を ページキャッシュが埋める（実験: 同じ 512 MiB の読み込みが 2 回目は 2 倍速い）。VFS は ext4 も tmpfs も /proc も同じ「ファイル」に見せる階層。

512 MiB を読む: 1 回目2.9 GB/s
同じものを 2 回目6.0 GB/s
Cached の増加+512 MiB

→ スライド 11–14

3 つの手口はすべて カーネルがハードウェアとプロセスの間に入る ことで成り立つ。その境界がシステムコール（次の次のスライド）。cgroup は「多重化の配分」を人間が指定する仕組み（スライド 18）。

Boundary · system call

境界：プログラムはカーネルに「頼んで」しか外の世界に触れない

cat /etc/hostname はファイルをどうやって読んでいる？

$ strace -e trace=execve,openat,read,write,exit_group cat /etc/hostname execve("/usr/bin/cat", ["cat", "/etc/hostname"], …) = 0 openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3 openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", …) = 3 read(3, "\177ELF\2\1\1\3"…, 832) = 832 openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3 ← FD 3 を得る read(3, "vm\n", 131072) = 3 ← 3 バイト読めた write(1, "vm\n", 3) = 3 ← 標準出力へ read(3, "", 131072) = 0 ← EOF exit_group(0) = ?

strace -c ls / では mmap 17 回・close 9 回・fstat 8 回など、たった 1 コマンドで数十回のシステムコールが発生する。

ユーザー空間
アプリ + ライブラリ（libc）。CPU はユーザーモードで、メモリもデバイスも直接は触れない
⇅syscall 命令でモード切替（ここが境界）

システムコールの実装。プロセス・メモリ・VFS・ネットワーク・ドライバ。CPU はカーネルモード
ハードウェア
CPU（MMU・タイマ）、メモリ、ディスク、NIC。割り込みでカーネルに通知する

仕組み

  • 「読む」の正体は read(fd, buf, n) というカーネルへの依頼。CPU の特権レベルが切り替わり、カーネルの関数が実行されて戻ってくる。
  • アプリは普通 libc の関数（fopen, printf）を呼び、libc が内部でシステムコールを発行する。ld.so.cache や libc.so.6 を開いているのはその準備。
  • 境界があるから、プロセスが暴走してもカーネルと他プロセスは守られる。この境界の上に以降の全機能が乗る。

Process · lifecycle

プロセスの一生：fork で増え、execve で入れ替わり、wait で看取られる

fork()
自分の複製を作る。親は子の PID を、子は 0 を受け取る。メモリは共有したまま（スライド 9）
→
execve()
子の中身を別プログラムに丸ごと差し替える。PID はそのまま。シェルが ls を実行するときの手順
→
exit()
終了コードを残して資源を返す。親が受け取るまで ゾンビ (Z) として PID だけ残る
→
wait()
親が終了コードを回収して初めてプロセス表から消える。親が先に死ねば init（PID 1）が引き取る

プロセスを 1 つ作るコストはどのくらい？

$ time (for i in $(seq 200); do /bin/true; done) real 0.320s user 0.238s sys 0.091s # fork+execve+exit+wait × 200 → 約 1.6 ms/回。sys はカーネル内の時間 $ grep -E '^(State|PPid|Threads)' /proc/self/status State: R (running) PPid: 1523 Threads: 1

症状から読む

  • Z が溜まる: 親が wait していない。ゾンビは CPU もメモリも使わないが PID を食う。親を直すか親を止める。
  • D が多い: ディスクや NFS の応答待ち。kill -9 も効かない。I/O 側を疑う（スライド 15）。
  • スレッドを見る: ps -L / top -H。/proc/PID/task/ に 1 つずつ並ぶ。

仕組み：カーネルから見たプロセス

  • カーネルはプロセスごとに task_struct（PID・状態・開いているファイル・メモリマップ・親子関係）を持ち、/proc/PID/ はそれを覗く窓。
  • 状態は R（実行中/実行可能）、S（イベント待ち）、D（I/O 待ち、割り込み不可）、T（停止）、Z（ゾンビ）。ps の STAT 列がこれ。
  • スレッドはカーネルから見ると「メモリ空間を共有するプロセス」。Threads: がその数。
  • 全プロセスは PID 1 を根とする木。ps --forest で親子が見える。

出典: fork(2), execve(2), wait(2), proc(5)

Scheduler · experiment

実験：CPU を分け合うと「経過時間」だけが伸びる

1 つの CPU に 2 つの計算プロセスを載せると何が起きる？

# loop.py: 3,000 万回の足し算をして、経過時間と CPU 時間を出す $ taskset -c 0 python3 loop.py 経過 2.52s CPU 2.52s # 1 プロセス / 1 CPU $ taskset -c 0 python3 loop.py & taskset -c 0 python3 loop.py 経過 4.19s CPU 2.10s # 2 プロセス / 同じ 1 CPU 経過 4.35s CPU 2.24s $ taskset -c 0 python3 loop.py & taskset -c 1 python3 loop.py 経過 2.10s CPU 2.10s # 2 プロセス / 別々の CPU 経過 2.16s CPU 2.16s
1 プロセス / 1 CPU
2.52 s
2 プロセス / 1 CPU（各）
4.2–4.4 s
2 プロセス / 2 CPU（各）
2.1–2.2 s
$ vmstat 1 # 2 プロセス / 1 CPU の最中（4 CPU 機） r b … us sy id wa in cs 2 0 … 25 1 74 0 644 699 # r=実行待ち 2、us=25%（4 CPU 中 1 つ分） 2 0 … 25 0 75 0 537 544 # cs=毎秒のコンテキストスイッチ

読み方

  • CPU 時間（プロセスが実際に CPU を使った時間）は 3 条件でほぼ同じ 2.1–2.5 s。仕事の量は変わらない。
  • 経過時間だけが 1 CPU 共有で 2 倍。CPU を「半分ずつ」使っているから。
  • CPU が別なら並列に走り、経過時間は 1 プロセスのときと同じ。マルチコアの効果は、プロセス（スレッド）が複数あって初めて出る。
  • 1 プロセス単独より共有時の CPU 時間が少し短いのは、ターボや周波数の揺れ。この程度のばらつきは常にある。

道具

taskset -c N は CPU アフィニティ（実行を許す CPU の集合）を固定する。time の real / user / sys がそれぞれ経過・ユーザーモード・カーネルモードの時間。Python では time.perf_counter() と time.process_time() の差で同じことが測れる。

Scheduler · mechanism

仕組み：タイムスライスで切り替え、nice で配分を偏らせる

2 つのうち片方だけ「遠慮」させられる？

$ taskset -c 0 nice -n 19 python3 loop.py & \ taskset -c 0 python3 loop.py 経過 2.11s CPU 2.08s # nice 0 : ほぼ独占 経過 4.11s CPU 2.34s # nice 19 : 相手が終わるまで待たされた # /proc/PID/status の *_ctxt_switches に交代回数が残る
# 自分が何回「強制交代」させられたかを終了時に読む $ taskset -c 0 python3 ctx.py # 単独 経過 2.21s voluntary=0 nonvoluntary=2 $ taskset -c 0 python3 ctx.py & taskset -c 0 python3 ctx.py 経過 4.27s voluntary=1 nonvoluntary=527 # 相手がいると 経過 4.34s voluntary=1 nonvoluntary=528 # 約 120 回/秒 = 数 ms ごと

スループットとレイテンシの綱引き

切り替え間隔を短くすると反応（レイテンシ）は良くなるが、切り替えのたびにレジスタ退避とキャッシュの入れ替えが起きて総仕事量（スループット）が落ちる。カーネルは実行可能プロセス数に応じてスライス長を伸縮させる。

スケジューラの要点

  • コンテキストスイッチ: タイマ割り込みや I/O 待ちを契機に、実行中プロセスのレジスタを保存し、次のプロセスのものを復元する。数マイクロ秒。
  • 公平さの基準は「使った CPU 時間」: 一番使っていないプロセスを次に選ぶ（仮想実行時間）。Linux 6.6 以降の既定は EEVDF（それ以前は CFS）。
  • nice 値 −20〜19 は CPU 時間の重み。nice 19 は nice 0 に対しておよそ 1/70 の重みで、実験のとおり相手がいる間はほぼ動けない。
  • I/O 待ちのプロセスは対象外: 状態 S/D は CPU を要求していない。CPU 100% の犯人は R 状態のプロセス。
  • 負荷分散: CPU ごとに実行キューを持ち、偏りを定期的に均す。taskset はそれを禁じる指示。

出典: sched(7), nice(1), Documentation/scheduler/sched-eevdf.rst

仮想メモリ：全プロセスが「自分だけのアドレス空間」を持つ

2 つのプロセスが同じアドレス 0x5560… を使っても衝突しないのはなぜ？

仮想アドレス
プロセスが見る番地。/proc/PID/maps の範囲。各プロセスで独立
→ページ
テーブル

→

仮想化で得られるもの

  • 隔離: 表にない番地に触ると MMU が例外を上げ、カーネルが SIGSEGV を送る。他人のメモリは表に載っていないので原理的に見えない。
  • 断片化の解消: 物理的に飛び飛びのページを、仮想的に連続した 1 GiB に見せられる。
  • 共有: libc のコードは物理 1 か所を全プロセスの表が指す。fork 後の親子も同様（次スライド）。
  • 遅延: 表に「まだ物理ページなし」と書いておき、触られた瞬間に割り当てる（デマンドページング）。

ハードウェアとの分担

変換そのものは CPU の MMU と TLB（変換結果のキャッシュ）が行い、カーネルは表を書くだけ。表に無い番地へのアクセスがページフォルトという例外になり、カーネルが「割り当てる」「共有をコピーする」「本当に不正」を判断する。

出典: proc(5) の /proc/[pid]/maps、mmap(2)

Memory · experiment

実験：確保しただけでは減らない、書いた瞬間に減る

1 GiB を確保したらメモリは 1 GiB 減る？

# mmap で 1 GiB を確保 → 1 ページごとに 1 バイト書く 確保前 VmSize 13956 kB VmRSS 7760 kB 1 GiB 確保直後 VmSize 1062532 kB VmRSS 8148 kB ← 増えない 全ページに書込後 VmSize 1062532 kB VmRSS 1056724 kB ← ここで 1 GiB

デマンドページング

mmap / malloc は「表に領域を予約」しただけ（VmSize = 仮想サイズ）。物理ページは最初のアクセスで起きるページフォルトの中で割り当てられ、VmRSS（常駐サイズ）が増える。だから top の VIRT と RES は別物で、使用量は RES を見る。

fork した子はメモリのコピーを持つ？

# 親が 256 MiB を確保して触る → fork → 子が全ページに書く 起動直後 AnonPages = 237 MiB (システム全体) 親: 256MiB 確保 AnonPages = 493 MiB 子: fork 直後 AnonPages = 493 MiB ← +0：コピーなし 子: 全ページ書込後 AnonPages = 749 MiB ← +256：書いた分だけ 親: 子の終了後 AnonPages = 493 MiB

Copy on Write（書き込み時コピー）

fork は親子の表を「同じ物理ページを書き込み禁止で指す」状態にするだけ。どちらかが書くとページフォルトが起き、カーネルがそのページだけ複製して書き込みを許す。だから fork は巨大プロセスでも速く、直後に execve する慣用句が成り立つ。

子の VmRSS は fork 直後から 256 MiB を示す（共有ページも数えるため）。実体を見るにはシステム全体の AnonPages や /proc/PID/smaps_rollup の Private/Shared を見る。

# 左の実験（Python, 3 行） buf = mmap.mmap(-1, 1 << 30) # 予約だけ rss() for off in range(0, 1 << 30, 4096): buf[off] = 1 # 各ページに触る
# 右の実験（Python, 4 行） data = bytearray(256 << 20); anon('親') if os.fork() == 0: # 子だけがここへ for i in range(0, len(data), 4096): data[i] = 1 anon('子'); os._exit(0)

Memory · pressure

メモリが足りなくなると：回収 → スワップ → OOM killer の順に手荒くなる

free の「free が少ない」は本当に危険？

$ free -h total used free shared buff/cache available Mem: 15Gi 500Mi 15Gi 11Mi 355Mi 15Gi Swap: 0B 0B 0B $ grep -E '^(MemAvailable|Cached|Dirty|AnonPages)' /proc/meminfo MemAvailable: 15.4 GiB # 回収できる分を含めた「実質の空き」 Cached: 149 MiB # ページキャッシュ（捨てられる） Dirty: 0 kB # まだディスクに書いていない分 AnonPages: 237 MiB # プロセスのヒープ・スタック（捨てられない）

読み方

free は「誰も使っていない」量で、健全なサーバーほど小さい（空きはキャッシュに使うのが正しい）。危険度は available で判断する。buff/cache はファイルのキャッシュで、必要ならすぐ回収される。

vmstat 1 の列意味こうなったら
si / soスワップイン / アウト (KiB/s)0 でなければ段階 2 に入っている
cache ↓ + wa ↑キャッシュが縮み I/O 待ちが増加段階 1 が効かなくなりつつある
dmesg の "Out of memory"OOM killer 発動段階 3。上限設定か負荷の見直し

不足時にカーネルがすること（軽い順）

  1. ページキャッシュの回収: ディスクに同じ内容があるページ（Cached）を捨てる。Dirty なら先に書き出す。ほぼ無料。
  2. スワップアウト: 捨てられない匿名ページ（AnonPages）をスワップ領域に退避。ここから性能が急落する。スワップなし構成では省略。
  3. OOM killer: それでも足りなければ、消費量とスコア（oom_score_adj）からプロセスを選んで SIGKILL。dmesg に "Out of memory: Killed process" が残る。

関係する設定・現象

  • vm.swappiness: 1 と 2 のどちらを優先するかの傾き。
  • vm.overcommit_memory: 物理より多い予約を許すか。デマンドページングがあるから通常は許す。
  • Transparent Huge Pages: 2 MiB ページで TLB ミスを減らす。DB では無効化推奨が多い。

なぜ効くか：参照の局所性

プログラムは「さっき触ったデータの近く」を「またすぐ」触る。だから上の階層に最近使った分だけ置けば、ほとんどのアクセスが速い層で済む。CPU キャッシュはハードウェアが、ページキャッシュはカーネルが、同じ発想で動く。

同じファイルを 2 回読むと 2 回目は速い？

$ dd if=/dev/urandom of=big.bin bs=1M count=512; sync $ grep Cached /proc/meminfo Cached: 149056 kB $ dd if=big.bin of=/dev/null bs=1M # 1 回目 536870912 bytes copied, 0.188 s, 2.9 GB/s $ grep Cached /proc/meminfo Cached: 673632 kB ← +512 MiB $ dd if=big.bin of=/dev/null bs=1M # 2 回目 536870912 bytes copied, 0.089 s, 6.0 GB/s ← 2 倍

ページキャッシュ

ディスクから読んだデータをカーネルがメモリに残しておく領域。2 回目はディスクに行かずメモリから read が返るので速い。この環境では 1 回目も速い（ホスト側にもキャッシュがある）が、Cached が正確に 512 MiB 増えている。echo 3 > /proc/sys/vm/drop_caches で捨てられる（root）。

Page cache · write side

書き込みも遅延する：write が返ってもディスクにはまだ無い

write() が成功したら停電しても安全？

write()
ページキャッシュに書いて即座に返る。ページは Dirty 印付き
→数秒後 or
閾値超過
ライトバック
カーネルのスレッドが Dirty ページをまとめてブロック層へ流す
→
デバイス
ここに届いて初めて永続。デバイス内キャッシュはさらに別

答え：安全ではない

既定では最長 dirty_expire_centisecs（30 秒）まで、あるいは Dirty が dirty_background_ratio（10 %）に達するまでメモリに留まる。停電すればその分は消える。永続を保証したい箇所では fsync()（DB・エディタ・git はやっている）か sync。

$ grep -E '^(Dirty|Writeback)' /proc/meminfo Dirty: 0 kB # 書き込み直後に見ると増えている Writeback: 0 kB # いままさにデバイスへ送っている分 $ sysctl vm.dirty_background_ratio vm.dirty_ratio \ vm.dirty_expire_centisecs vm.dirty_background_ratio = 10 # 背景で書き出し開始 vm.dirty_ratio = 20 # 超えると write() 自体を待たせる vm.dirty_expire_centisecs = 3000 # 30 秒で必ず書き出す

遅延のご利益と代償

  • 同じページに何度書いてもディスクへは 1 回。小さな write をまとめて大きな I/O にできる。アプリの体感は劇的に速い。
  • 代償は耐障害性。しかも Dirty が溜まりすぎると dirty_ratio で write() が突然遅くなる（コピー中に固まる現象の正体の一つ）。
  • O_DIRECT はキャッシュを迂回する（DB が自前でキャッシュを持つとき）。

出典: fsync(2), open(2), Documentation/admin-guide/sysctl/vm.rst

Device access

デバイス：カーネルは「ファイル」に見せかけ、割り込みで話を聞く

なぜ echo hi > /dev/ttyS0 でシリアルに文字が出る？

$ ls -l /dev/vda /dev/null /dev/tty0 brw-rw---- 1 root disk 254, 0 … /dev/vda # b = ブロック crw-rw-rw- 1 root root 1, 3 … /dev/null # c = キャラクタ crw--w---- 1 root tty 4, 0 … /dev/tty0 # 番号 (major, minor) がドライバとデバイスの対応表のキー $ ls /sys/block/vda/ # sysfs: デバイスの属性を覗く dev queue/ size stat … $ cat /proc/interrupts | head # CPU ごとの割り込み回数
/dev/null · /dev/zero捨てる · 0 を無限に返す。ドライバの中身は数十行
/dev/urandomカーネルの乱数プール。スライド 11 の実験データ源

/dev/tty* · /dev/pts/*端末。シェルの標準入出力の正体

デバイスファイルの正体

アプリからは open / read / write / ioctl だけ。カーネルは major/minor 番号でデバイスドライバを引き、ドライバがレジスタや DMA でハードを叩く。キャラクタデバイス（端末・乱数・GPU 制御）はバイト列を順に、ブロックデバイス（ディスク）は固定長ブロックをランダムに扱い、後者だけがブロック層（スライド 15）を通る。

デバイスからの通知：割り込み

  • 「読み込み完了」をカーネルがずっと聞き続ける（ポーリング）と CPU が無駄。代わりにデバイスが 割り込みで CPU の実行を横取りし、カーネルの割り込みハンドラが短時間で後処理を予約して戻る。
  • 重い処理は後回し（softirq / ワークキュー）にして、ハンドラは最短で終える。ネットワークの受信が典型。
  • 高速 NIC / NVMe では逆に、割り込みの嵐を避けて一定期間ポーリングに切り替える（NAPI、io_uring のポーリング）。

DMA とドライバ

大きなデータは CPU を介さず、デバイスが直接メモリへ書く（DMA）。ドライバの仕事は「DMA の準備 → デバイスに指示 → 割り込みで結果回収」。ドライバはカーネル本体に組み込むか カーネルモジュール（lsmod）として後から読み込む。

出典: mknod(1), sysfs(5), Documentation/admin-guide/sysfs-rules.rst

File system · VFS

ファイルシステム：VFS が「ファイル」という 1 つの顔を作る

ext4 のファイルも /proc/meminfo も同じ cat で読めるのはなぜ？

$ cat /proc/mounts # 種類の違う FS が同じ木に刺さっている /dev/vda / ext4 rw,relatime … # ディスク上 /dev/vdb /opt/rclone squashfs ro … # 圧縮・読み専用 proc /proc proc rw … # カーネル情報 sysfs /sys sysfs rw … # デバイス情報 tmpfs /dev/shm tmpfs rw … # メモリ上 devpts /dev/pts devpts rw … # 端末 $ grep -vE 'nodev' /proc/filesystems # ブロックデバイスを要する FS ext2 ext3 ext4 squashfs erofs fuseblk

VFS（仮想ファイルシステム）

open / read / write / stat / readdir をカーネル内の共通インターフェースとして定義し、ext4・XFS・Btrfs・NFS・tmpfs・procfs が同じ関数表を実装する。cat は相手が何かを知らずに済み、mount はその関数表を木のある枝に接ぎ木する操作。

ディスク上の構造（ext4 の場合）

  • inode: ファイルの実体。サイズ・権限・時刻・データブロックの位置。名前は持たない。
  • ディレクトリ: 「名前 → inode 番号」の表が入った特殊なファイル。ハードリンクは同じ inode を指す別の名前。
  • ジャーナル: 変更をまず日誌に書き、成功後に本体へ反映。クラッシュ時に日誌から復旧し、fsck の長時間走査を避ける。

XFS大容量・並列 I/O に強い、縮小不可大規模データ、RHEL 既定
BtrfsCopy on Write、スナップショット、チェックサムロールバック、自己修復

Block layer

ブロック層：I/O を並べ替え・まとめ・先読みしてからデバイスへ

同じ SSD なのに順次読みとランダム読みで速度が桁違いなのは誰のせい？

$ cat /sys/block/vda/queue/scheduler none [mq-deadline] kyber bfq # [ ] が現在の I/O スケジューラ $ cat /sys/block/vda/queue/rotational 1 # 1 = 回転ディスク扱い（仮想ディスクの既定） $ cat /sys/block/vda/queue/read_ahead_kb 8192 # 先読みの最大量 $ lsblk NAME MAJ:MIN SIZE RO TYPE MOUNTPOINTS vda 254:0 256G 0 disk / vdb 254:16 9.6M 1 disk /opt/rclone

目安の桁。公称値はメーカー資料、実測は fio で。

ブロック層の仕事

  • マージ: 隣接するブロックへの要求を 1 つの大きな I/O にまとめる。
  • I/O スケジューラ: 要求の順序を決める。mq-deadline（締切つき並べ替え、汎用）、bfq（プロセス間の公平さ、デスクトップ）、kyber（レイテンシ目標、高速 SSD）、none（並べ替えなし、NVMe 向け）。
  • 先読み: 順次アクセスを検出したら要求より先まで読んでページキャッシュへ。順次読みが速い理由の半分はこれ。
  • マルチキュー (blk-mq): CPU ごとにキューを持ち、NVMe の並列性を活かす。

HDD と SSD で正解が変わる

HDD はヘッドの移動（シーク）が数 ms かかるので、並べ替えとマージの効果が絶大。SSD / NVMe はシークが無く並列に強いので、並べ替えるより素早く投げる方がよく（none）、代わりに書き込み寿命と GC を意識する。答え：デバイスの物理特性が主因で、ブロック層はそれを緩和する側。

出典: Documentation/block/, Documentation/admin-guide/blockdev/

Virtualization · KVM

仮想化：CPU の「見せかけ」をハードウェアに手伝わせる

この実験環境自体が VM。ゲスト OS はなぜ自分がゲストだと気づかずに動ける？

ゲスト内プロセス
ゲストのユーザーモード。ゲストカーネルにシステムコール
ゲストカーネル
普通の Linux。ページテーブルを書き、デバイスを叩いているつもり
KVM + QEMU
KVM（ホストカーネルのモジュール）が CPU の仮想化支援で VM を走らせ、QEMU（ホストのプロセス）がデバイスを模倣
ホスト CPU
Intel VT-x / AMD-V。ゲストが特権命令を実行するとVM Exit でホストへ制御が戻る

この環境の /proc/cpuinfo は "Intel Xeon Processor @ 2.80GHz" とだけ名乗り、ディスクは /dev/vda（virtio-blk）。両方とも VM の典型的な痕跡。

3 つの要素

  • CPU: ゲストの通常命令はホスト CPU でそのまま実行される（ソフトウェアで解釈しない）。特権命令だけ VM Exit で KVM が肩代わりする。だからほぼネイティブ速度。
  • メモリ: ゲスト仮想 → ゲスト物理 → ホスト物理の2 段変換を、CPU の EPT / NPT が一度に引く。ゲストが「物理」だと思うアドレスも、ホストにとっては仮想。
  • デバイス: 実機を模倣すると VM Exit が多発して遅い。virtio はゲストのドライバが「自分は VM にいる」と知った上で、共有メモリのリングでホストとまとめてやり取りする準仮想化。

ゲストは Linux をそのまま使う

ゲストカーネルは本資料のスライド 4〜15 の仕組みをすべてそのまま持つ。違いは「その下にもう 1 枚 Linux がいる」こと。ホストから見た VM は QEMU という 1 プロセスで、vCPU はそのスレッド。だからホストの top に VM は普通のプロセスとして出る。

出典: Documentation/virt/kvm/, virtio 仕様 (OASIS)

Containers · namespaces

コンテナ：カーネルは 1 つのまま、「見える範囲」だけを切り分ける

Docker コンテナの中で ps をすると自分しか見えないのはなぜ？

namespace（名前空間）

プロセスが見る「PID の表」「マウントの木」「ネットワーク I/F」「ホスト名」「ユーザー ID」「IPC」「cgroup」「時計」を、プロセスごとに別の写しに差し替えるカーネル機能。仮想メモリが番地を隔離したのと同じ発想を、他の資源名に広げたもの。

コンテナ = 3 つの既存機能の組み合わせ

cgroup v2

cgroup：プロセスの集まりに「使ってよい量」を割り当てる

Kubernetes の limits.cpu: 500m はカーネルのどこに届く？

# cgroup v2 はディレクトリ木。作れば設定ファイルが生える（root） $ mkdir /sys/fs/cgroup/lab $ echo "50000 100000" > /sys/fs/cgroup/lab/cpu.max # 100 ms ごとに最大 50 ms → CPU 0.5 個分（= 500m） $ echo "256M" > /sys/fs/cgroup/lab/memory.max $ echo $$ > /sys/fs/cgroup/lab/cgroup.procs # このシェルを所属させる $ python3 loop.py 経過 ≈ 5.0s CPU ≈ 2.5s # 半分の時間しか CPU を貰えない $ cat /sys/fs/cgroup/lab/memory.events # 超過時の記録 oom_kill 1 # 256M を超えると殺される

本環境は cgroup v1/v2 混在のハイブリッド構成で root 権限が要るため、この操作は手順と期待値を示している。cat /proc/self/cgroup で自分の所属を確認できる。

cgroup v1cgroup v2（2016〜、現在の既定）
木コントローラごとに別の木単一の木にすべてのコントローラ
見分け方/sys/fs/cgroup/cpu/ などが並ぶ/sys/fs/cgroup/cgroup.controllers がある
設定例cpu.cfs_quota_uscpu.max

仕組み

  • 単一の木（v2）にプロセスを振り分け、各ノードにコントローラの設定を書く。子は親の制限を超えられない。
  • cpu: cpu.max（上限、期間内の割当）と cpu.weight（競合時の比率。nice の集団版）。スケジューラの配分に直接効く。
  • memory: memory.max（超えたら回収 → OOM）、memory.high（超えたら減速）。スライド 10 の挙動を集団単位で起こす。
  • io: デバイスごとの帯域・IOPS 上限（io.max）。pids: fork 爆弾対策の上限。

誰が使っているか

systemd はサービスごとに cgroup を作る（systemd-cgls で木が見える）。MemoryMax= / CPUQuota= はそのまま上のファイルへの書き込み。コンテナランタイムはコンテナごとに作り、Kubernetes の requests / limits は cpu.weight / cpu.max / memory.max に翻訳される。

出典: cgroups(7), Documentation/admin-guide/cgroup-v2.rst, systemd.resource-control(5)

待っている間に起きること

デバイス待ちのプロセスは D 状態になり、スケジューラは別のプロセスを走らせる (6–7)。割り込みで完了が届くと R に戻り、次のタイムスライスで read から帰る。「I/O の遅さを CPU の多重化で隠す」のが OS の基本動作。

データの置き場所

読めたデータはページキャッシュ（カーネル）からアプリのバッファ（ユーザー空間の物理ページ）へコピーされる。バッファが初アクセスならここでページフォルトが起きて割り当てられる (8–9)。mmap ならコピー自体を省ける。

コンテナと VM はどこに挟まる？

コンテナ: VFS の手前で「見えるマウント木」が差し替わり、ブロック層の手前で cgroup の io 制限が効く (17–18)。VM: デバイスの先が virtio で、その向こうにホスト Linux の同じ道がもう 1 本ある (16)。

Wrap-up

まとめ・次の一歩・参考資料

持ち帰り 5 点

  1. OS の仕事は多重化・隔離・階層化。CPU・メモリ・I/O のどれもこの 3 語で説明がつく。
  2. 性能の数字は経過時間と CPU 時間、VIRT と RES、free と available を区別して読む。
  3. 「確保」「fork」「write」はどれも遅延している。実体が動くのは触った瞬間・書いた瞬間・書き出しの瞬間。
  4. ページキャッシュは速さの源泉であり、停電時の損失範囲でもある。fsync の意味を知る。
  5. コンテナは namespace + cgroup + overlayfs、VM は KVM + 2 段ページテーブル + virtio。どちらも既存機能の組み合わせ。

次に手を動かすなら

  • perf stat / perf top でコンテキストスイッチとキャッシュミスを数える。
  • fio で順次 / ランダム、キャッシュあり / --direct=1 の 4 通りを比べる。
  • unshare + pivot_root + cgroup で 50 行のコンテナランタイムを書く。
  • bpftrace でシステムコールやページフォルトをプロセス別に集計する。
